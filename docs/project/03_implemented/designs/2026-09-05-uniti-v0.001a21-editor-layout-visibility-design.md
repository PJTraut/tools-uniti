# UNITI v0.001a21 Editor Layout and Visibility Design

Date: 2026-09-05
Status: implemented
Milestone: [`v0.001a21` — Cross-Platform Alpha](../milestones/2026-09-05-uniti-v0.001a21-cross-platform-alpha.md)

## Goal

Make the existing multi-window and split-pane architecture directly usable, let the one global Find/Replace surface attach to an editor window or float, add bounded whitespace visualization, and separate theme appearance from contrast.

This is an inserted A21 workstream before Cross-Platform Alpha Task 4. After it is implemented and verified, A21 resumes at the existing Task 4 checkpoint. The work must preserve one UNITI service, one authoritative `Document` per source identity, one global Find/Replace surface, bounded custom-viewport rendering, durable session recovery, and explicit Save/Discard/Cancel Quit behavior.

## Approved decisions

1. Extend the existing binary pane tree and service-owned window model; do not replace documents or panes with per-document dock widgets.
2. Splitting immediately creates a second independent view of the active document.
3. Every pane exposes document assignment, split, and active-view Dock/Undock controls on its tab/title row.
4. Undocking records the source window, pane, and tab position. Docking returns the view there when possible and uses a safe fallback when it is not.
5. Find/Replace remains one service-owned surface. Attached mode occupies the full bottom width of the active editor window and follows active-window focus; detached mode is a floating topmost tool window.
6. Whitespace visualization is a global, persisted, display-only choice: Off, EOL, Spaces & Tabs, Invisible Unicode, or All.
7. Spaces & Tabs includes ASCII space and tab. Invisible Unicode includes non-ASCII whitespace and Unicode format controls, including NBSP variants and zero-width controls.
8. Theme appearance and contrast are independent: System, Light, or Dark appearance plus Standard or High Contrast.
9. Theme definitions own whitespace, invalid-byte, match, selection, and ordinary application colors.
10. Rendering remains limited to bounded visible slices. Pathological zero-width runs aggregate visibly instead of causing unbounded paint operations.
11. Existing settings and durable sessions migrate forward without discarding compatible state.
12. LOWDISK behavior remains injection-tested only. No test fills or reserves the real volume.

## Existing baseline and design gap

A20 already implemented the structural foundation:

- one process-lifetime `UNITIService` and one `QApplication` instance;
- multiple service-owned `UNITIMainWindow` shells;
- a binary horizontal/vertical `EditorPaneTree` whose leaves are tab groups;
- independent views over one registry-owned authoritative document;
- persisted windows, pane topology, tabs, active view, and per-view cursor/presentation state;
- tab drag detachment and service-level transfer into a new window;
- one service-owned floating `FindReplaceWindow` with persisted content, options, geometry, visibility, report state, target, and bounded field Undo/Redo histories; and
- a custom virtual `UNITITextView` that paints bounded visible text without a Qt document store.

The baseline exposes split and move-to-window commands only through menus and outside-tab dragging. It has no explicit per-pane assignment surface, no reversible return anchor for detached views, and no title-row Dock/Undock control. Find/Replace cannot attach to a main window. Themes have one System/Light/Dark axis and no editor-specific color tokens. Whitespace visualization is absent.

## Scope

This workstream includes:

- per-pane title-row controls with accessible names and keyboard-reachable menus;
- Split Right and Split Down from the active pane;
- assignment of any open document to a pane through an independent view;
- reversible view undocking and docking with persisted return anchors;
- transactional view transfer and deterministic fallbacks;
- one attachable/detachable Find/Replace dock that follows the active window while attached;
- persisted Find/Replace placement and detached geometry;
- bounded EOL, ASCII space/tab, and invisible-Unicode markers;
- separate appearance and contrast theme settings;
- theme-owned editor overlay colors;
- settings and session-schema migration; and
- focused, acceptance, rendering-bound, and inherited regression tests.

## Outside this workstream

This workstream does not add:

- project/workspace discovery or project-level state;
- multiple Find/Replace panels or per-window Find/Replace state;
- arbitrary user-authored themes or a general theme editor;
- syntax highlighting;
- a minimap, toolbar, or IDE-style sidebars;
- whole-document whitespace indexing or persistent marker caches;
- changes to document text, save format, regex semantics, or history budgets; or
- real-volume low-disk manufacture.

## Approaches considered

### Selected: extend the pane tree and use one movable dock

`EditorPaneTree` remains the layout authority. Each leaf adds a compact control surface to the existing tab row. The service transfers existing view widgets between leaves and windows. One bottom-only `QDockWidget` presentation hosts the existing Find/Replace controller and content. Whitespace markers extend the current visible-slice paint pass, and theme/settings types evolve at their existing seams.

This approach reuses tested ownership, recovery, and scale boundaries. It introduces no competing document or window model.

### Rejected: one Qt dock widget per document

Native document docks would make basic floating straightforward, but they would replace the established binary split/tab topology, complicate same-document independent views, and expand Qt layout serialization into an alternate session authority.

### Rejected: a custom workspace manager

A new workspace canvas could control every placement detail, but it would duplicate Qt focus, accessibility, drag, docking, and layout behavior. The requested behavior does not justify another layout subsystem.

## Ownership and component boundaries

The existing ownership graph remains authoritative:

```text
QApplication
  -> one UNITIService
     -> one DocumentRegistry
     -> one WindowManager
        -> zero or more UNITIMainWindow shells
           -> one EditorPaneTree per window
              -> PaneLeaf tab groups
                 -> independent UNITITextView instances
     -> one FindReplace dock/controller/content surface
```

The affected responsibilities are:

- `ui.panes`: pane title-row controls, pane destination descriptions, and view movement inside one tree;
- `ui.main_window`: command routing, view creation in a selected pane, transfer acceptance at an exact pane/tab position, theme propagation, and user-visible failure reporting;
- `app.service`: cross-window undock/dock transactions, return-anchor fallbacks, active-window Find/Replace placement, and rollback;
- `app.window_manager`: stable lookup of windows/panes needed for transfer without introducing a privileged permanent main window;
- `ui.find_replace`: one dockable/floating presentation and unchanged search/history authority;
- `ui.whitespace`: Qt-independent display grammar and bounded classification helpers with no document mutation;
- `ui.theme`: application palette plus editor-specific theme tokens;
- `ui.text_view`: visible-only marker geometry and painting;
- `app.settings`: global whitespace and contrast preferences; and
- `app.session` and session orchestration: optional per-view return anchors and global Find/Replace placement.

Core document and regex ownership do not move into Qt. A small bounded `Document` query may expose a line's exact terminator without materializing the full line; it remains Qt-free and read-only.

## Pane title row and document assignment

Each `PaneLeaf` retains its native movable, closable tabs. A compact corner control on the same row as the document titles provides:

- Dock or Undock for the selected view;
- Split Right;
- Split Down; and
- a document-assignment menu.

Controls operate on stable view and pane IDs, never tab indexes captured before a mutation. Their accessible names and tooltips state the full action. Disabled state explains the relevant structural limit where Qt permits a status tip.

Split Right creates a horizontal branch; Split Down creates a vertical branch. The new leaf immediately receives a new `UNITITextView` over the same authoritative document. The new view starts from the current view's logical cursor and selection while retaining its own subsequent cursor, selection, preferred column, scroll, wrap viewport, soft-wrap, and zoom state. Text edits and document Undo/Redo remain shared because the `Document` remains singular.

The assignment menu lists open authoritative documents in registry activation order with disambiguating paths when basenames collide. Choosing a document behaves as follows:

1. if that pane already contains a view of the document, select its first matching tab in current tab order;
2. otherwise create a new independent view in that pane and select it; and
3. never close, replace, or silently move another view as a side effect.

This keeps assignment non-destructive. Existing tabs remain available until the user closes or explicitly moves them.

## Reversible document docking

Docking moves one view, not a `Document`. Multiple views of the same document may therefore have different docking states.

An undocked view receives a `DockReturnRecord` containing:

- source window ID;
- source pane ID; and
- source tab position.

The service creates a new editor window, removes the live view from the source leaf, installs it in the new window, preserves its view ID and `EditorState`, and leaves the registry binding unchanged. The source window remains open, including when it becomes temporarily empty, so the return destination remains usable.

The title-row button, Move Tab to New Window command, and existing outside-tab drag all invoke this same undock transaction. There is no second detach path with weaker return or rollback behavior.

Dock resolves the destination in this order:

1. the recorded source pane in the recorded source window;
2. the active pane of the recorded source window;
3. the active pane of the most recently active other window; or
4. a newly created service-owned window when no other editor window exists.

The saved tab position is clamped to the destination's current tab count. A successful Dock clears the return record. If the source window or pane disappeared, the successful fallback is the new stable placement; UNITI does not retain a stale anchor.

Every transfer is transactional. The service resolves and validates the destination before taking the source view where possible. If acceptance fails, it reinstalls the view in its exact source position and selection state, restores the prior return record, preserves the registry binding, and reports the failure. A transfer never closes or saves a document.

After a view docks elsewhere, an empty window that was created by that view's undock operation closes automatically. Other empty windows and the original source window are not inferred to be disposable. Explicit window-close and Quit rules remain unchanged.

## One attached or detached Find/Replace surface

The current Find/Replace logic becomes a service-owned bottom-only dock surface. It remains one object graph with one pair of inputs, one set of options, one match/report state, one target provider, and one pair of bounded input histories.

Detached mode preserves current behavior:

- modeless floating tool window;
- system topmost behavior;
- native resizing and size grip where applicable;
- detached geometry persisted independently; and
- active target determined by the service's most recently focused live editor view.

Attached mode behaves as follows:

- the dock occupies the full bottom dock area of the active `UNITIMainWindow`;
- side docking is disabled;
- activating another UNITI editor window moves the same dock to that window;
- moving the presentation alone does not cancel work, clear inputs, reset histories, or replace results; and
- an actual target-view change retains the existing revision/generation cancellation rules.

The dock title row exposes Attach/Detach and Close. Find and Replace commands show the one surface in its current placement and focus the correct field. When the service owns no editor windows, the surface hides and the service continues running. The next editor activation restores attached placement to that window or shows the detached surface according to saved placement.

## Whitespace display grammar

`WhitespaceMode` has five persisted values:

| Mode | Markers |
|---|---|
| `off` | none |
| `eol` | actual logical line terminators only |
| `spaces_tabs` | U+0020 SPACE and U+0009 TAB |
| `invisible_unicode` | non-ASCII whitespace plus Unicode `Cf` format controls |
| `all` | union of EOL, Spaces & Tabs, and Invisible Unicode |

Markers are presentation overlays. They do not enter the laid-out text, document coordinates, selection, clipboard, IME surrounding text, search, replacement, Undo/Redo, recovery, or save bytes.

The initial marker grammar is:

- ASCII space: `·` centered in its occupied advance;
- tab: `→` at the tab start, with geometry stopping at the resolved tab advance;
- line ending: compact `LF`, `CRLF`, or `CR` after the content end;
- known invisible controls: compact names such as `NBSP`, `NNBSP`, `ZWSP`, `ZWNJ`, `ZWJ`, `WJ`, and `BOM`; and
- other qualifying characters: `U+XXXX` or the required longer Unicode form.

The EOL marker comes from the exact current logical terminator, not the configured output policy or the document-wide source EOL report. A final line without a terminator receives no EOL marker. CRLF is one marker. Only committed document text is classified; active IME preedit text is not.

Invisible Unicode includes every character other than CR, LF, ASCII space, and tab for which `str.isspace()` is true, plus characters whose Unicode general category is `Cf`. This intentionally surfaces non-breaking spacing, zero-width join/control characters, and bidirectional format controls. Invalid-byte annotations retain their separate existing presentation.

## Bounded rendering and marker geometry

Whitespace visualization extends `UNITITextView.paintEvent` and preserves its visible-only contract:

1. request only the already bounded row slice needed by the viewport;
2. classify that slice in one linear pass;
3. use the row's `QTextLayout` geometry for character positions, including tab advances and zero-width positions;
4. clip every marker to the viewport; and
5. discard marker candidates after the paint event.

No whole-document scan, Qt text document, persistent marker index, or document-sized cache is introduced. Exact EOL lookup reads at most the two terminator characters at the line boundary.

At most 4,096 whitespace marker draw operations are admitted per frame. The final admitted operation becomes a visible `+N` aggregate for further qualifying markers. Consecutive zero-width characters at one visual position also aggregate when individual labels would overlap. Classification remains bounded by the editor's existing visible-slice limits; aggregation bounds painter work without hiding that additional invisible characters exist.

Marker painting never changes hit testing. Mouse, keyboard, cursor, selection, and IME coordinates continue to use original document positions and the original text layout.

## Theme model and high contrast

Themes use two independent global settings:

- `ThemeMode`: System, Light, or Dark; and
- `ThemeContrast`: Standard or High Contrast.

The View menu presents System/Light/Dark as one exclusive group and High Contrast as a separate checkable toggle. Changing either applies immediately to all UNITI windows, the Find/Replace surface, and all current views. New views receive the active specification at construction.

A `ThemeSpec` contains the Qt application palette and explicit editor tokens for:

- ordinary text and background;
- gutter text and background;
- selection and selected text;
- match and current-match emphasis;
- invalid-byte annotation;
- space marker;
- tab marker;
- EOL marker; and
- invisible-Unicode marker and label background/border.

Standard Light and Dark preserve the current palette direction. Standard System starts with the current native system palette. High Contrast Light and Dark use deterministic high-contrast palettes. High Contrast System selects a light or dark high-contrast specification from the native base luminance while retaining the System appearance choice for future system changes.

High Contrast specifications require at least 7:1 contrast for primary text against the editor base and at least 4.5:1 for whitespace labels and meaningful marker strokes against their immediate background. Selection and current-match foreground/background pairs must remain readable. Tests calculate these ratios from the resolved `ThemeSpec`; names such as “high contrast” are not accepted as evidence by themselves.

## Settings and session compatibility

Settings remain global preference state. The next settings schema adds:

- `whitespace_mode`, defaulting to `off`; and
- `theme_contrast`, defaulting to `Standard`.

Older settings load with those defaults and are rewritten only through the existing preparation/migration path. Unknown values fall back independently; a bad contrast value does not erase a valid appearance mode or another setting.

Actual runtime topology remains durable session state. The next session schema adds:

- optional `dock_return` on each `ViewRecord`; and
- `placement` (`attached` or `detached`) on the global Find/Replace manifest record.

Detached Find/Replace geometry remains the existing geometry field. Attached placement follows the active window and therefore does not persist a host-window ID.

The decoder accepts schema 1 under its exact schema-1 field grammar, migrates it in memory with no view return anchors and detached Find/Replace placement, and produces the new in-memory record. New publications write only the new schema. Future schemas remain unsupported and preserved under existing evidence rules. Manifest count and 1 MiB decoded limits do not change.

Return records validate bounded nonempty identifiers and a non-negative tab position. They may reference a window or pane that no longer exists because fallback is an explicit part of the docking contract; loading such an anchor is safe and does not allocate the referenced object.

## Failure and safety behavior

- Split or assignment admission failure leaves the existing pane and views unchanged and reports the structural limit.
- A docking destination failure rolls the view back to the exact source placement and prior anchor.
- Closing a target window between validation and transfer is handled as a failed destination, not as permission to drop the view.
- Find/Replace reparenting failure leaves the surface in its prior safe placement or detached and visible; it never creates a second panel.
- Whitespace classification or label lookup failure for an unusual code point falls back to its Unicode code-point label.
- Marker budget exhaustion aggregates visibly and never blocks input or changes content.
- Theme validation falls back to a complete known specification; partial palettes are not applied.
- Malformed older settings use existing safe defaults. Malformed or unsupported session evidence follows existing preservation/recovery behavior.
- Existing external-file hash verification, recovery journaling, document history, session history limits, low-space admission, and Save transactions remain unchanged.

## Accessibility and interaction

Every compact control has a full accessible name, tooltip, and status tip. Pane controls are reachable through the existing View menu even when a platform style makes a corner control difficult to target. Destination menus include unambiguous document and pane labels without exposing internal IDs.

Whitespace markers are supplementary visual information. They are not inserted into the accessibility text stream because doing so would corrupt document reading and offsets. The selected whitespace mode and marker legend are exposed through action names and tooltips. High Contrast is keyboard-operable and does not depend on color alone to distinguish EOL names or invisible-character labels.

## Verification strategy

Pure tests cover:

- whitespace mode validation, character classification, labels, and EOL grammar;
- settings schema migration, independent invalid-value fallback, and round trips;
- session schema-1 migration, new-schema round trips, malformed return records, and unchanged structural bounds;
- destination resolution and rollback decisions without Qt; and
- ThemeSpec contrast ratios and complete token sets.

Offscreen Qt tests cover:

- title-row control presence, accessible names, and enabled state;
- split creation with one document authority and independent view state;
- document assignment selection/creation behavior;
- undock, exact return, missing-pane/window fallback, rollback, and empty detached-window cleanup;
- session capture/restore of pane topology and return anchors;
- exactly one Find/Replace controller/content instance through attach, active-window following, detach, close/show, and restoration;
- preservation of F/R inputs, options, results, target rules, zoom, report state, and field histories during placement changes;
- marker pixels for space, tab, LF, CRLF, CR, NBSP, zero-width controls, and aggregation;
- unchanged cursor/hit-test/selection coordinates with markers enabled;
- unchanged copy/paste, search, replacement, Undo/Redo, recovery, and saved bytes;
- immediate propagation of appearance, contrast, and whitespace settings to existing and new views; and
- bounded paint/read behavior on giant lines and dense invisible-character input.

Inherited gates include the complete A17 text-integrity, A18 resource/performance, A19 regex-intelligence, A20 recovery/session/history/one-service/one-panel/Quit/external-hash suite, plus the implemented A21 tests. Native platform smoke must exercise the controls on supported hosts as A21 proceeds; offscreen tests do not replace the final platform proof.

No test manufactures LOWDISK. Capacity failures and write failures remain injected.

## Acceptance criteria

The workstream is complete when:

1. every pane exposes working split, assignment, and active-view Dock/Undock controls;
2. a split immediately shows a second independent view of the same authoritative document;
3. undocked views return to their recorded pane/tab after live use and restart, with deterministic safe fallback;
4. one and only one Find/Replace surface attaches full-width to the active window, follows focus while attached, and floats while detached without state loss;
5. all five whitespace modes render the approved grammar without modifying document state or bytes;
6. System/Light/Dark and Standard/High Contrast operate as independent persisted settings;
7. theme-owned overlay tokens satisfy the stated high-contrast ratios;
8. visible rendering and persisted state remain within existing plus newly stated hard bounds;
9. old compatible settings and schema-1 sessions migrate without losing their supported state;
10. focused and inherited regression suites pass; and
11. Git history contains focused commits on `main`, with no push, tag, release, package, or real LOWDISK action unless separately authorized.
