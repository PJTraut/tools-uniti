# UNITI v0.001a20 Recovery & Session Alpha Design

Date: 2026-09-04
Status: implemented
Milestone: [`v0.001a20` — Recovery & Session Alpha](../milestones/2026-09-04-uniti-v0.001a20-recovery-session-alpha.md)

## Goal

Make one long-lived UNITI service the safe authority for documents, windows, session state, and recovery. Normal restarts restore saved documents, complete admitted Undo/Redo histories, window/split/tab/view state, and the global Find/Replace surface. Crashes restore compatible unsaved edits and their history without modifying an original file until the user explicitly saves.

a20 must add this continuity without weakening the exact text-integrity, bounded large-file, asynchronous task, regex, or startup guarantees established through a19.

## Existing baseline and design gap

UNITI already has useful foundations:

- a versioned append-only recovery journal that records file-backed edits and output-format metadata;
- an asynchronous `RecoveryManager` that flushes unsaved edits, discovers candidates, replays compatible journals, and restarts durability after recovery;
- exact source identity checks before recovery replay;
- atomic JSON settings and setup-state stores with preservation of malformed input;
- ordered startup phases for schema preparation, recovery discovery, GUI construction, and session restoration;
- bounded cleanup for known UNITI-owned temporary, log, and process-session artifacts;
- one 50-transaction document history and independent 50-state Find and Replace field histories;
- one main window with tabs and one Find/Replace tool window; and
- full a17 text-integrity, a18 resource/performance, and a19 regex-intelligence gates.

The baseline does not persist a restorable workspace. Its process-session record exists only for stale cleanup. A clean restart does not reopen tabs, restore cursor/selection/scroll positions, or preserve Undo/Redo. Recovery journals record applied edit operations rather than transaction, Undo, Redo, and saved-cursor semantics. Malformed journals are skipped silently. The application permits independent processes to reach state paths, has no multi-window or split-pane ownership model, and the Find/Replace field histories exist only in memory.

## Design principles

1. One service owns session and recovery mutation. A secondary invocation forwards work and exits.
2. A `Document` remains the only text, save-state, and Undo/Redo authority, even when many views display it.
3. Views own cursor, selection, scroll, and presentation state; documents never absorb view state.
4. Recovery data and saved-session history have different durability and eviction rules. Convenience history can be pruned; unsaved recovery cannot be silently evicted.
5. Count limits are not byte limits. Every persisted structure has depth, encoded-size, decoded-size, and aggregate admission checks.
6. Startup reads one small manifest first and restores expensive document/history state lazily.
7. Cross-file publication is generation-based. A manifest never references a pack that was not completely written and synced first.
8. File metadata is a fast identity check; SHA-256 over exact saved bytes is the content authority.
9. External changes, corruption, truncation, and degraded durability remain visible and require explicit choices.
10. Session and recovery work never blocks the GUI thread or bypasses the shared resource/task policy.
11. Low-disk behavior is tested with injected capacity readings and controlled write failures. Tests never try to consume the real volume to create a low-disk condition.

## Scope

a20 includes:

- one persistent UNITI service per OS user/application-data identity;
- versioned, user-scoped local IPC for activation and file-open forwarding;
- multiple top-level editor windows in the one service;
- horizontal and vertical editor splits with tab groups at their leaves;
- detachable tabs and multiple synchronized views of one authoritative document;
- one service-owned Find/Replace panel targeting the most recently focused editor view;
- exact restoration of admitted window, pane, tab, view, document-history, and Find/Replace state;
- saved-file SHA-256 validation with explicit external-change choices;
- recovery-journal transaction, Undo/Redo, and save-point semantics;
- one Recovery Center for valid, changed, missing, corrupt, and truncated entries;
- depth-and-byte-bounded history, seven-day closed-history retention, and bounded cleanup;
- atomic generation publication, schema migration, checksums, restrictive local permissions, and safe fallback; and
- correctness, crash, UI, integration, security-boundary, and performance evidence.

## Outside a20

a20 does not add project/workspace semantics, cloud synchronization, collaboration, encrypted vault/key management, a general recent-files database, plugins, LSP, syntax highlighting, file-type profiles, or a permanent background daemon installed outside the running desktop application. The service remains alive with zero editor windows only after UNITI has been launched and exits on explicit Quit, logout, shutdown, or process termination.

a20 does not duplicate every clean document into application state. A clean saved document is reopened from its path only after identity validation. When exact old bytes are unavailable after an external change, UNITI offers the current disk version or preserves/skips the session entry; it never fabricates a retained document version from incomplete history.

Editor whitespace visualization and expanded Unicode inspection remain parked. Cross-platform packaging and platform certification remain a21 work, although a20 interfaces must not intentionally prevent Windows or Linux implementations.

## Approaches considered

### Selected: layered service, session store, and recovery journal

One `UNITIService` owns process lifetime, instance arbitration, documents, windows, the global Find/Replace surface, settings, session publication, and recovery coordination. A `DocumentRegistry` shares authoritative documents between views. A `WindowManager` owns top-level windows and pane trees. A `SessionStore` publishes small manifests and separate bounded history packs. `RecoveryManager` remains focused on crash-durable unsaved edits and evolves its journal format to preserve history semantics.

This keeps state ownership explicit, builds on the current recovery and settings code, lets saved history remain evictable without endangering unsaved recovery, and permits lazy document/history restoration.

### Rejected: one unified application event log

A single log for edits, Undo/Redo, saves, windows, panes, focus, Find/Replace, and settings could provide one total order. It would also make every UI-state change part of the crash-critical replay protocol, complicate compaction and schema migration, and allow a damaged convenience record to endanger document recovery. The coupling and log volume are not justified for this alpha.

### Rejected: periodic whole-application snapshots

Serializing complete application and document contents at intervals is conceptually direct and could reconstruct externally replaced files. It duplicates large documents, creates write and compression spikes, slows startup, and conflicts with the a18 large-file contract. Session continuity must remain metadata/history based, with unsaved content represented as bounded incremental recovery state.

## Architecture

```text
secondary invocation
        |
        v
 instance lease + local IPC -------------------------------+
        |                                                   |
        v                                                   v
  UNITIService --------------------------------------> activation/open request
        |
        +--> DocumentRegistry --> authoritative Document <--+
        |          |                    ^                   |
        |          v                    |                   |
        +--> WindowManager --> pane/tab/view tree -----------+
        |
        +--> global Find/Replace --> active view
        |
        +--> SessionStore --> manifest + immutable history packs
        |
        +--> RecoveryManager --> unsaved recovery WAL/checkpoints
        |
        +--> SettingsStore / ResourceManager / diagnostics
```

The service is the process-lifetime composition root. Qt windows are consumers of service-owned state rather than owners of application services. Refactoring may proceed incrementally, but final ownership must not leave each window with competing settings, resource, recovery, session, or Find/Replace managers.

### Responsibility map

- `src/uniti/app/instance_service.py`: primary lease, local endpoint, bounded protocol, secondary forwarding, activation, and orderly release.
- `src/uniti/app/session.py`: Qt-free schemas, validators, immutable snapshots, generation selection, history-pack encoding, SHA-256 metadata, retention, and cleanup decisions.
- `src/uniti/app/service.py`: process-lifetime `UNITIService`, document registry, active-view routing, window ownership, Quit coordination, and service diagnostics.
- `src/uniti/app/recovery_manager.py`: recovery bindings, ordered asynchronous durability, v1/v2 compatibility, v3 event writing, discovery, replay, and candidate lifecycle.
- `src/uniti/core/history.py`: immutable export/import of validated transaction history, cursor, saved cursor, depth, and byte accounting.
- `src/uniti/core/recovery.py`: Qt-free journal records, integrity validation, transaction/history replay, and compatibility readers.
- `src/uniti/ui/panes.py`: split-tree and tab-group widgets, detach/move/split actions, focus reporting, and immutable layout snapshots.
- `src/uniti/ui/recovery_center.py`: model-backed recovery choices and status explanations.
- `src/uniti/ui/main_window.py`: one service-owned window shell and menu/action routing; no independent application services.
- `src/uniti/ui/find_replace.py` and `src/uniti/ui/bounded_text_edit.py`: service-level target routing and import/export of bounded field state/history.
- `src/uniti/ui/text_view.py`: view-position snapshot/restore and updates from a shared document.

Exact file boundaries may be adjusted when an existing module already has the correct responsibility. The implementation must not create a monolithic session/recovery/window manager or move semantic persistence into Qt widgets.

## Single service and local request protocol

`UNITIService` is the only writer of settings, session manifests, history packs, and recovery candidates for its application-data identity. Startup acquires a cross-platform `QLockFile` lease after application paths and Qt capability exist but before settings migration, recovery discovery, or session publication. `QApplication.setQuitOnLastWindowClosed(False)` keeps the service alive without editor windows.

The primary opens a user-scoped `QLocalServer`. A secondary invocation that cannot acquire the lease connects to that endpoint, sends one length-bounded versioned request, waits for a bounded acknowledgement, and exits. Requests contain only protocol version, activation intent, and normalized requested file paths. The primary validates schema, count, byte length, path representation, and supported commands before acting. A malformed request changes no state.

The endpoint uses current-user access controls where Qt exposes them. Socket/lease names derive from the resolved application-data identity rather than the working directory. A stale endpoint is removed only after the lease is acquired or the recorded owner is proven dead and a bounded retry cannot reach it. A live lease plus unreachable endpoint produces an actionable startup error; it never authorizes a second session writer.

Secondary file requests open in the most recently active window, or create a window if none exists. Activation raises that window. The primary returns per-path outcomes so the secondary can report a safe failure instead of implying success.

## Document, view, window, and pane ownership

`DocumentRegistry` resolves paths canonically and owns at most one live `Document` for one source identity. Opening an already-owned path creates or focuses a view rather than opening a competing document authority. Registry entries retain document-level output format, exact saved identity/hash, shared Undo/Redo, recovery binding, reference counts, and last-active information.

Every `UNITITextView` owns independent cursor, anchor, preferred column, vertical and horizontal scroll positions, soft-wrap viewport position, and zoom/presentation state. Multiple views can display one document in the same pane tree or in different top-level windows. All receive document revision notifications; only the focused view becomes the service-level active target.

Each window contains a binary split tree. Internal nodes record horizontal or vertical orientation and normalized child proportions. Leaf nodes contain one tab group, ordered view references, and one selected tab. Commands provide New Window, Split Right, Split Down, Close Split, and Move Tab to New Window. Dragging a tab outside its group detaches it into a new window. Empty leaves collapse deterministically; the last leaf remains until the window closes.

Closing one view never closes a shared document while another view exists. Closing the final view of a modified document invokes Save/Discard/Cancel. Saved or unmodified closed-document history leaves the active manifest but may remain in the seven-day history cache. Discard deletes unsaved recovery for that document only after the choice is confirmed.

## Global Find/Replace ownership

The service owns one modeless, system-topmost Find/Replace panel for all windows. Focus changes publish one active-view reference. A new target cancels or invalidates document-bound search and capture work under the existing generation/revision seals, but it does not clear global field contents, options, geometry, visibility, zoom, report visibility, or input histories.

The persisted state includes:

- Find and Replace current text;
- each field's cursor, selection, Undo states, Redo states, and current history position;
- Regex, Case, and Whole-word states;
- panel visible/hidden state, geometry, zoom, and Match Report visibility; and
- the last target view identifier for restoration when that view still exists.

Search results, compiled engine objects, captures, snapshots, and task handles are never persisted. After restoration, expressions are reanalyzed through the normal a19 debounce/task path. A restored panel targets the restored active view but does not silently execute Find All or Replace.

## Session manifest and history packs

The durable session root lives under UNITI state storage, distinct from cache-based live-process records and recovery journals. One bounded atomic JSON manifest contains:

- schema and generation;
- service/session identity, build identity, created/updated timestamps, and clean-shutdown state;
- active window, pane, tab, and view identifiers;
- ordered window geometries/states and pane trees;
- ordered document references and per-view state;
- current global Find/Replace values, options, layout state, and its optional field-history-pack reference;
- immutable document/field-history-pack filenames, encoded/decoded sizes, checksums, and owner identities; and
- explicit degradation/truncation records.

The manifest never embeds document histories, Find/Replace Undo/Redo histories, or clean document contents. It has a 1 MiB decoded limit and structural limits of 32 windows, 128 pane leaves, 256 views, and 128 distinct documents. Entries beyond a limit are not allocated or partly restored; they are reported as unavailable session state.

Each immutable per-document pack contains:

- schema, pack generation, and document identifier;
- canonical path and exact saved-file SHA-256;
- fast identity fields: size, modification time, inode/file ID, and device/volume identity where available;
- detected source encoding, selected output encoding, EOL profile, and saved output format;
- ordered `EditTransaction` records with exact operations;
- history cursor, saved cursor, coalescing boundary, and truncation metadata; and
- encoded and decoded size declarations plus checksum.

Packs use a standard-library compressed representation with deterministic encoding. Readers validate the envelope, compressed length, declared decoded length, checksum, schema, collection counts, positions, transaction ordering, and byte budgets before constructing history objects. A checksum is an integrity check, not an authenticity boundary.

One optional immutable Find/Replace history pack contains the two fields' bounded Undo and Redo states plus cursor/selection positions. Current field values and panel layout remain in the manifest so a missing or pruned convenience-history pack cannot erase the visible current state. The field-history pack follows the same write, sync, checksum, decoded-bound, generation-reference, and cleanup rules as document history packs.

## History depth, byte budgets, and retention

The current 50-step depth remains the user-facing contract. It is necessary but not sufficient: one bulk transaction may contain many operations, and Find/Replace snapshots may repeat long expressions.

The admission policy is:

| State | Depth limit | Persisted byte limit |
|---|---:|---:|
| Editor history | newest 50 logical transactions per document | 32 MiB per document |
| Find history | newest 50 field states | shared 4 MiB Find/Replace budget |
| Replace history | newest 50 field states | shared 4 MiB Find/Replace budget |
| Entire saved session/history cache | all admitted entries | 256 MiB total |

Limits apply at the first boundary reached. Byte accounting includes UTF-8 text payload, positions, operation structure, and conservative format overhead; code does not rely on compression ratio to admit decoded content. Find/Replace histories persist deltas between immutable field states rather than fifty complete copies.

Saved-history pruning removes the oldest compatible transactions first, adjusts history/saved cursors explicitly, and records a visible `history_truncated` reason. Current document/view state and current Find/Replace values remain. If one operation alone exceeds the persistence limit, it stays undoable in the live process under existing operation admission but is marked non-persistable; UNITI reports that cross-restart Undo is incomplete.

The saved-session aggregate budget is enforced oldest-closed-document first, then oldest transactions of inactive open documents, then oldest transactions of the active document. Current state is never evicted. Unsaved recovery journals are outside this LRU and never become victims of saved-history cleanup.

History for a document explicitly closed after save is retained for seven days, subject to the 256 MiB aggregate budget. Reopening the exact hashed file during that interval may restore the compatible history. Expired and orphaned saved-history generations are removed by bounded cleanup. Cleanup owns only names and directories created by the session store.

An ordinary save that preserves logical text advances the saved cursor and retains compatible history. A transformation that changes logical character coordinates and cannot safely translate earlier operations establishes a new history root and records an explicit incompatibility truncation; it never imports invalid offsets merely to claim full retention.

## Saved-file identity and external changes

Every durable document pack stores SHA-256 over the exact bytes that established its saved point. Size, modification time, inode/file ID, and device/volume identity provide a fast path. When all available fast fields match, restoration may trust the stored hash association. When any field differs or is unavailable, hashing runs as a cancellable streaming task before history is imported.

If the exact hash matches, history remains compatible even when metadata changed. If bytes differ, the Recovery Center or session-restore conflict surface offers:

- Open Disk: open current bytes with a fresh history root;
- Skip: open nothing and retain the session/history record for the remainder of its seven-day retention; or
- Discard: after confirmation, remove only UNITI-owned session/history state.

Because clean document contents are not duplicated, UNITI does not offer a fictitious retained version when it lacks exact base bytes. A missing file offers Locate Matching File, Skip, or Discard. A located file must pass the expected hash before history imports. No identity decision modifies the current disk file.

## Recovery journal v3

Recovery v1 and v2 remain readable. New journals use v3 records with envelope/schema/integrity fields and semantic events rather than an unstructured stream of applied edits. The document exposes a Qt-free history-event listener so recovery can record:

- complete transaction boundaries and ordered operations;
- Undo and Redo cursor movement;
- save-point advancement and source identity/hash changes;
- output encoding/EOL metadata changes; and
- a clean/discard terminal event.

The saved history pack is the durable base for history before the newest save. The v3 journal contains semantic events after that base. Recovery loads the compatible base, validates the exact source bytes, replays events into the document and history model, restores the saved/current cursors, and starts a fresh durable journal before retiring the candidate.

Recovery payload is proportional to admitted edit/history deltas, not source-file size. At 64 MiB for one document, the manager schedules compaction into a normalized checkpoint plus the minimum event suffix required for admitted Undo/Redo. Compaction publishes a new synced candidate before removing the old one.

Recovery data is not hard-evicted by history budgets. If available space falls below a 512 MiB reserve, an injected capacity policy refuses additional nonessential history writes and attempts recovery compaction. If recovery durability itself cannot continue or any recovery write/fsync fails, the manager retains the last known durable point, marks the document `Recovery degraded`, exposes the exact scope in diagnostics, and keeps warning until a successful durable flush proves recovery again. It never silently reports the latest edits as recoverable.

## Generation publication and save ordering

Session packs are immutable and content-addressed, with their producing generation recorded inside the validated envelope; byte-identical packs may be reused by later manifests. Manifests and pointers are generation-named. The physical union of packs retained for the current and immediately previous complete generations stays inside the 256 MiB saved-session budget. Publication follows this order:

1. Capture immutable document, view, window, and Find/Replace state on the GUI thread without disk I/O.
2. Serialize, compress, checksum, write, and sync new document and Find/Replace history packs on background workers.
3. Write and sync the new manifest referencing only complete packs.
4. Atomically replace the current-manifest pointer and sync its parent directory.
5. Retain the immediately previous complete generation until the next successful publication; clean older or orphaned generations later within bounds.

An interrupted publication therefore leaves either the old complete generation or the new complete generation. Startup selects only a manifest whose referenced packs all pass validation.

In-place Save preserves recovery across the transition:

1. The existing a17 save path stages, verifies, commits, and syncs exact output.
2. Compute or carry forward the exact committed-file SHA-256 and identity.
3. Write and sync the compatible new history pack.
4. Publish the new session manifest generation.
5. Start/sync the new recovery base if unsaved events already followed the captured revision.
6. Only then retire the old recovery candidate.

Revision, document identity, output format, history generation, and save destination seals reject stale completion. Session persistence never writes document content to its source path.

## Runtime session flow

### Primary startup

1. Validate runtime/environment/dependencies and application paths.
2. Initialize Qt capabilities, acquire the instance lease, and open the local endpoint.
3. Prepare settings/session schemas and resources.
4. Discover and validate recovery candidates and the newest complete session generation.
5. Present one Recovery Center when any candidate or conflict needs a decision.
6. Construct window/pane shells from the bounded manifest.
7. Restore the active document/view first; schedule other documents and histories lazily through the shared task coordinator.
8. Reanalyze restored Find/Replace expressions without executing a search or replacement.
9. Reach READY, show/raise the active window, and accept forwarded requests.

Command-line file requests are processed after recovery choices so they cannot obscure a pending recovery decision. Duplicate paths route through `DocumentRegistry`.

### Window close and service lifetime

Closing a window closes or moves only its contained views. A shared document remains open while any view exists. Closing the last view resolves modified state with Save/Discard/Cancel and otherwise moves compatible saved history into the seven-day cache. When no windows remain, the Find/Replace panel hides and the service continues processing activation/IPC without keeping an invisible editor target.

A later launch, OS activation, or New Window command creates or raises an editor window in the existing service. Requested files open in the most recently active window or a new window when none exists.

### Explicit Quit

Quit is service-wide. It enumerates unique modified documents, not views, and prompts Save/Discard/Cancel once per document. Cancel aborts Quit without partially closing windows. After all decisions succeed, UNITI captures and durably publishes the final session, flushes or discards recovery according to the decisions, closes windows/services in reverse ownership order, releases IPC/lease state, and exits.

Only saved/unmodified documents remain in a clean-session manifest. Documents explicitly discarded at Quit do not reappear as recovery candidates.

## Recovery Center

The Recovery Center is one model-backed startup surface listing every discovered entry. It distinguishes:

- compatible recoverable journal;
- saved session ready to restore;
- externally changed source;
- missing source;
- truncated but safely prefix-readable journal;
- invalid/corrupt journal or history pack;
- unsupported future schema; and
- recovery whose durable point is older than the last observed in-memory revision.

Per-entry actions are enabled only when valid:

- Recover replays a compatible candidate into an authoritative document and restores all admitted history/view state.
- Open Disk opens current bytes with fresh history.
- Locate Matching File verifies a replacement path by SHA-256 before import.
- Skip leaves UNITI-owned evidence unchanged.
- Discard requires confirmation and deletes only the selected UNITI-owned candidate/history.

Closing the center is Skip All. Corrupt/unsupported files remain preserved as timestamped `.invalid` evidence and can be revealed in diagnostics. Recovery errors do not prevent unrelated valid entries from opening.

A candidate is not removed after replay alone. UNITI first attaches the recovered document, writes and syncs its new recovery/session state, publishes the manifest, and only then discards the old candidate. A second crash anywhere before publication leaves at least one usable recovery path.

## Settings and schema migration

Global preferences remain in `SettingsStore`; restorable runtime layout moves to `SessionStore`. Settings continue to own theme, resource preference, hotkeys, and default editor/Find behavior. Session state owns actual windows, split trees, tabs, per-view positions, the current global Find/Replace state/history, and document history references.

Schema preparation is explicit and monotonic. Known older schemas migrate through pure Qt-free functions into a new immutable value, which is then written atomically. Malformed data is preserved before safe defaults publish. A future unsupported schema is preserved unchanged and reported rather than overwritten. Unknown fields are ignored only where the schema declares forward-compatible extension points.

Legacy recovery v1/v2 journals remain discoverable and replay into a history that accurately reflects the available semantics; they never claim transaction/Redo state absent from the old format.

## Failure and security behavior

- Invalid paths, counts, offsets, hashes, lengths, compression envelopes, or generation references are rejected before replay.
- Decompression enforces both encoded and decoded bounds incrementally, preventing oversized allocation from a small payload.
- Resolved cleanup targets must remain inside the exact UNITI-owned session/recovery root; symlinks do not broaden ownership.
- Session and recovery files request user-only permissions where supported. Logs never include document, Find, or Replace contents.
- A same-user local IPC request is still untrusted input and receives the same schema/size/path validation as a file.
- One failed pack does not discard another valid pack. One failed recovery candidate does not block the complete Recovery Center.
- All durability failures preserve the previous valid generation and become visible in status and diagnostics.
- Hash cancellation or failure leaves the document unopened and the stored history untouched.
- External source bytes are never overwritten by recovery, session restore, conflict resolution, or hashing.
- No service takeover occurs while a live primary lease remains.

## Resource and responsiveness behavior

GUI handlers capture small immutable state and enqueue work. They do not hash, serialize, compress, fsync, scan recovery directories, or clean generations. Session writes are coalesced; text durability retains recovery priority, while geometry, focus, and scroll updates may debounce.

Restore reads the manifest and active entry first. Inactive tabs may appear as lightweight placeholders until scheduled open/hash/history work completes. Focus or explicit user selection promotes the relevant task. Cancellation closes files and temporary decoded state. Memory pressure may delay inactive saved-history work but never cancels an essential recovery flush already admitted.

History decoding cannot exceed the declared per-document or aggregate decoded budgets. Saved-history packs do not populate document text caches. Hashing and journal compaction use streaming reads/writes and existing task progress/cancellation conventions.

## Verification strategy

Qt-free unit tests cover:

- manifest, history-pack, IPC, and recovery-v3 schemas;
- deterministic history export/import with transaction, cursor, saved-cursor, Undo, Redo, and truncation state;
- 50-step and byte-bound admission, 32 MiB per-document, 4 MiB field-history, and 256 MiB aggregate policy;
- seven-day retention and oldest-first LRU decisions;
- exact SHA-256 and fast-identity decisions;
- encoded/decoded compression bounds, checksum failure, path containment, and malformed collections/offsets;
- v1/v2 recovery compatibility and known schema migrations; and
- immutable generation selection and orphan cleanup.

Failure-injection tests interrupt pack writing, file sync, manifest replacement, pointer publication, recovery compaction, save transition, and cleanup. Every interruption must select the previous or new complete generation and preserve recovery evidence. Low-disk branches use injected capacity values and controlled write/fsync exceptions only. Tests must not allocate files to exhaust or materially reduce real disk space.

Subprocess/integration tests cover:

- primary/secondary races, one-writer ownership, stale-owner recovery, unreachable live service, malformed requests, bounded messages, file forwarding, activation, and acknowledgement;
- simulated abrupt process termination with edits, transaction boundaries, Undo/Redo branches, saved history, metadata changes, and pending debounced session state;
- a second crash during recovery publication;
- truncated-tail recovery, corrupt packs, missing sources, changed sources, matching-content metadata changes, Skip, Discard, and Locate Matching File; and
- Save/Discard/Cancel across unique documents with multiple views.

Offscreen Qt tests cover:

- binary split layout, resizing, leaf collapse, tab movement, and detachment;
- multiple views of one document with independent cursor/selection/scroll and shared edits/history;
- multiple windows with one global active view and one global Find/Replace panel;
- complete Find/Replace state/history export and restoration;
- shell-first and active-document-first lazy restore;
- the Recovery Center action matrix and accessible status text;
- closing all windows while the service stays alive; and
- explicit Quit prompting exactly once per modified document.

Performance tests prove hashing, serialization, compression, fsync, cleanup, and recovery replay do not run on the GUI thread. Active-session restoration must remain within the existing open-to-usable and heartbeat gates. Lazy background restoration must remain cancellable, revision/identity sealed, and governed by the shared resource manager.

Native macOS smoke verifies window activation, split focus, drag detachment, same-document views, global Find/Replace routing, closing the final window without quitting, secondary-launch forwarding, recovery choices, and explicit service-wide Quit.

The complete existing test suite, deep self-check, compileall, offscreen smoke, native smoke, quick performance suite, and inherited a17/a18/a19 integrity/resource/regex gates remain mandatory.

## Milestone acceptance

a20 freezes only when:

1. exactly one UNITI service owns session/recovery mutation and secondary launches safely forward files/activation;
2. the service remains alive without editor windows and explicit Quit terminates it only after complete Save/Discard/Cancel resolution;
3. multiple windows, detachable tabs, horizontal/vertical splits, and multiple views of one document preserve one document authority;
4. restart restores every admitted window, pane, tab, active-view, cursor, selection, scroll, saved-document history, and global Find/Replace state/history exactly;
5. editor and field histories obey the first of their depth or byte limits, seven-day retention, and the 256 MiB aggregate cap with explicit truncation state;
6. SHA-256 validation permits history only for exact saved bytes and every mismatch requires an explicit safe choice;
7. recovery v3 reconstructs compatible unsaved text, output metadata, transaction boundaries, Undo/Redo, and saved cursors without changing original files;
8. partial writes, corrupt/truncated/oversized data, unsupported schemas, failed hashes, low-space signals, and a second crash during recovery preserve the last complete evidence and remain visible;
9. all session/recovery/hash/compression/cleanup work stays off the GUI thread, restores lazily, and passes existing responsiveness/resource gates;
10. low-disk coverage uses injected conditions only and never attempts to fill a real filesystem;
11. the complete ordinary suite, deep self-check, compileall, offscreen/native smoke, quick performance suite, and inherited a19 gates pass with fresh evidence; and
12. no known session race, concurrent writer, silent history loss, unsafe takeover, external-file overwrite, recovery-evidence loss, GUI freeze, unbounded allocation, or text-integrity defect remains.
