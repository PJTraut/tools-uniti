# UNITI v0.001a16 Startup, Bootstrap, and Initialization Milestone

Date: 2026-09-01
Status: implemented
Former roadmap order: 1
Predecessor: `v0.001a15` at `10f419e` plus verified post-tag hotfix `6b81185`

## Goal

Give UNITI an explicit, diagnosable setup and startup lifecycle that uses an existing host Python 3.12+ to create or maintain a UNITI-controlled isolated runtime, validates the application environment, persists startup state, exposes self-checks, and reaches the editor without mutating host/system packages.

Implementation is complete at `v0.001a16` / `0.1a16`. Repository code, a16 acceptance coverage, full-suite verification, compile checks, headless smoke, deep offscreen self-check, and Git history are the completion evidence recorded by the a16 handover.

## Accepted policy

1. An up-to-date host Python 3.12 or newer must already be installed and discoverable.
2. UNITI does not bundle or install host Python during this milestone.
3. Host Python is the bootstrap interpreter used to create a UNITI-owned isolated environment.
4. UNITI never installs dependencies into global, system, user-site, or unrelated active virtual environments.
5. A source checkout uses the repository `.venv`.
6. A normal local installation may use an OS-appropriate UNITI application-local virtual environment.
7. Declared package metadata is canonical for UNITI dependencies; bootstrap logic must not maintain a conflicting informal package list.
8. Normal editor startup requires no account, telemetry, or network service. Network access is a setup concern only when dependency installation is required.

See [ADR-0001](../../05_decisions/ADR-0001-host-python-runtime-policy.md) for the durable policy decision.

## Required bootstrap flow

```text
1. Detect host OS and architecture
2. Discover candidate host Python installations
3. Require Python >= 3.12
4. Determine source-checkout or installed-local mode
5. Resolve the expected UNITI-owned environment
6. Create the environment when absent
7. Prepare packaging bootstrap tools inside that environment
8. Install or repair declared UNITI dependencies inside that environment
9. Validate dependency versions and importability
10. Run startup sanity checks
11. Persist the setup-state snapshot atomically
12. Relaunch or continue under the UNITI runtime
```

Missing or outdated host Python produces an exact actionable failure and stops. Bootstrap never replaces the user's Python or invokes an OS package manager to install it.

## Startup phases

Startup must expose and persist its last reached phase:

```text
BOOT
  01 runtime identity
  02 environment validation
  03 dependency validation
  04 application paths
  05 schema migrations
  06 settings load and validation
  07 resource calibration
  08 stale-state cleanup
  09 recovery discovery
  10 GUI and Qt capability validation
  11 session restore
  12 READY
```

An aborted startup records the phase and a sanitized, actionable failure reason.

## Initialization scope

### Runtime and environment identity

Record the UNITI display/package version, source commit or build identity when available, Python version and executable, host OS/version, architecture, install mode, environment path, and a unique launch/session identifier.

### Dependency validation

Validate declared runtime dependencies from canonical package metadata. This includes exact `regex==2026.5.9` semantics and PySide6 when the desktop UI is installed. A successful fingerprint may take a lightweight path on later launches; changed Python/package identity triggers full validation.

### Paths, settings, and schemas

Ensure OS-native config, state, cache, recovery, temp, and log paths exist and are writable. Version settings, setup, recovery, and session schemas. Migrate known formats explicitly and preserve malformed or unsupported originals before recovery or reset.

### Resource and filesystem calibration

Record physical/available memory, CPU/logical core count, cache budget, worker count, and pressure-policy parameters. Check temp-file creation, directory write access, mmap availability, atomic replacement, fsync behavior where relevant, metadata/xattr support, available disk space, and practical handle limits without adding unbounded startup work.

### Recovery and stale state

Discover unfinished recovery journals, validate source identity before replay, preserve source/output metadata distinctions, and perform bounded cleanup of obsolete completed journals, temporary files, and search spill state. Session identifiers prevent collisions between UNITI processes.

### GUI and platform checks

Record Qt platform backend/plugin readiness, native/fallback monospace font resolution, clipboard availability, IME/input-method availability, and display DPI/scaling. Platform differences are diagnostic capabilities, not universal hard failures unless they prevent the editor from operating safely.

Host locale/default encoding may be recorded for diagnostics but never determines how an existing document is decoded.

## Setup-state contract

Persist setup/startup state atomically in an OS-appropriate state location. The finalized schema must represent:

- schema version;
- UNITI version/build identity;
- startup success and last phase;
- install mode;
- host and runtime Python identity;
- proof that the runtime is UNITI-owned;
- platform identity;
- dependency validation status;
- environment fingerprint;
- settings/recovery schema versions;
- resource budget and worker count;
- last bootstrap time; and
- last successful startup time.

Exact field names and migration behavior are finalized in the technical design before implementation.

## Self-check interface

The preferred command is:

```text
uniti --self-check
uniti --self-check --deep
```

Fast mode validates runtime identity, Python support, environment ownership, dependencies, writable paths, parseable state/settings, basic regex behavior, resource calibration, and Qt availability when the UI is installed.

Deep mode uses temporary data to exercise UTF-8, Windows-1252, UTF-16/32 LE/BE, LF/CRLF/CR, mmap/fallback where practical, regex search/replace, atomic save, recovery journal/replay, and an optional offscreen Qt smoke. Both modes return meaningful process exit codes and avoid sensitive document content.

## Diagnostics integration

Expose startup/setup state through the existing diagnostics surface:

- UNITI version and commit/build identity;
- host/runtime Python and environment mode/path;
- OS and architecture;
- dependency versions;
- last initialization stage/status;
- resource calibration;
- filesystem capabilities;
- Qt platform, font, IME, clipboard, and scaling state; and
- last bootstrap and successful-startup timestamps.

Diagnostic output excludes document contents and secrets.

## Architecture constraints preserved

- Python third-party `regex` remains authoritative.
- PySide6 remains the desktop UI.
- Qt never owns document text; the custom `QAbstractScrollArea` viewport and UNITI document engine remain authoritative.
- Opening and normal large-file work remain bounded; no deliberate 1 GiB ceiling is introduced.
- Encoding, invalid-byte, CR/LF/CRLF, save, recovery, and resource-safety invariants remain intact.
- Normal startup remains local and account-free.
- Packaged `.app`/`.exe` embedded-runtime decisions remain parked rather than being smuggled into this milestone.

## Acceptance direction

At minimum, macOS acceptance must demonstrate:

- a fresh checkout without `.venv` and with supported host Python;
- bootstrap creates the repository `.venv` and installs dependencies from canonical metadata;
- `uniti --self-check` succeeds;
- setup state persists atomically;
- normal `uniti` launches;
- the second startup uses the fingerprint fast path;
- malformed setup/settings state is preserved and handled safely;
- missing/outdated host Python fails actionably without changing system packages; and
- the existing full test suite remains green.

Windows and Linux requirements must be designed into path, executable-discovery, ownership, and relaunch logic even if the first external runtime acceptance is performed on macOS.

## External gates and non-goals

- Automatic host-Python installation is not part of this milestone.
- Embedded Python, signed installers, `.app`/`.exe` packaging, accounts, telemetry, and network services are not part of this milestone.
- Tagging, pushing, or distributing `v0.001a16` occurs only after fresh verification and an explicit integration choice.
