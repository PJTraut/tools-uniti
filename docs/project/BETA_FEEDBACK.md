## BF-012 — Full Unicode case folding misses a match with one-character search windows

- Found: 2026-09-08 during documentation-example verification, on B2; this is an internal finding, not a user report.
- Status: implemented, integrated on `main` (`596c88f`, "1b2 feedback implementation"). Doc note below describes the pre-fix state.
- Reproduction: compile `(?fi)straße` or `(?V1)(?i)straße` and search `STRASSE` through `search_document(..., options=SearchOptions(window_chars=1))`. Direct engine matching returns `(0, 7)`; UNITI returns no matches.
- Evidence boundary: windows of 8 and the default 65,536 characters return the expected match. A default-window probe with 65,531 preceding ASCII characters also passes. A failure with the production default window has not been reproduced; the one-character-window result still requires investigation before claiming complete streaming equivalence for full case folding.
- Root cause and fix: `_iter_engine_matches` (`src/uniti/regex/search.py`) defers any unsafe/partial-match scan until at least `_MIN_UNSAFE_SCAN_CHARS` (8) characters are buffered, specifically because the `regex` engine's `finditer(..., partial=True)` reports an unreliable partial-match start position once the scanned buffer is shorter than a variable-width full-casefold literal's full character range (e.g. `ß` folding to/from `ss`/`SS` under `(?f)`) — see the module docstring comment above `_MIN_UNSAFE_SCAN_CHARS`. - Root cause, confirmed directly: unrelated to the quarter-em inset or gutter scale (both already correctly reduce `self.viewport()`'s actual size, which every layout calculation already reads dynamically). `UNITITextView._visible_line_capacity()` (`src/uniti/ui/text_view.py`) deliberately over-counts by one row (`height // line_height + 1`) so a partial row paints at the bottom during ordinary scrolling — but `_refresh_scrollbars` also used that same padded count to compute the vertical scrollbar's `maximum`, one row short of what a true last row needs. "Only when focused" describes when a user notices (typing places the cursor, and its blinking caret, on that last line), not a focus-coupled code path — the clipping itself is unconditional.
- Fix: a new `_visible_whole_line_capacity()` (floor division, no `+1` pad) is used only for the scrollbar `maximum` in both the wrapped and non-wrapped branches of `_refresh_scrollbars`, once the document/wrap index reports `complete` (i.e., there is no more content to scroll into) — leaving the padded count intact everywhere else (painting, page size) so ordinary mid-document scrolling is unaffected.
- Verification: `tests/ui/test_text_view_contract.py::test_scrolling_to_the_end_fully_reveals_the_last_line` (a viewport height deliberately not a whole multiple of the row height; confirmed to fail by exactly one row-height against the pre-fix code, passes after). Full suite: 1781 passed, 6 platform-only skips.

## BF-034 — "Whole word" malfunctions for non-Latin (CJK/Thai) text

- Reported: 2026-09-11, on B2.
- Status: implemented, integrated on `main`.
- User position: `\b ... \b` malfunctions for non-Latin text — the "Whole word" option fails to do what it claims for these scripts.
- Root cause, verified directly: word-boundary matching (`\b`) is fully supported by the `regex` module and is how this app already implements "Whole word" (`src/uniti/regex/analysis.py:148`, `\b(?:...)\b`, literal/plain-text search mode only — disabled whenever Regex mode is on). The engine call itself does not error or misbehave; the failure is that `\b`'s boundary is defined on a generic Unicode word-character class that only produces useful term isolation when a script is space-delimited. Tested directly: a literal "whole word" search for `中文` matches inside `中文 测试` (space-separated) but not inside `中文测试` (no space) — it can only match at the edges of a punctuation/whitespace-delimited run, never around an individual CJK term embedded in continuous text. The same applies to Thai. Net effect for the user: the feature silently fails to isolate a whole word for CJK/Thai, which is a malfunction from the product's perspective regardless of the underlying mechanism being "as designed" for space-delimited scripts.
- Acceptance to define during implementation: what a corrected, script-aware "whole word" boundary should do for CJK/Thai (e.g. a different boundary rule per detected script) — there is no universal literal-substring definition of "whole word" for scripts without word-delimiting whitespace, so this needs a real design decision, not a one-line fix.
- Design decision: rather than inventing a segmentation-based notion of "word" for these scripts (impossible without a dictionary this engine doesn't have), a literal "Whole word" search skips the `\b` requirement specifically on whichever edge of the search term falls in a script conventionally written without spaces — Han, Hiragana, Katakana, Hangul, Thai, Lao, Khmer, Myanmar (`_NO_SPACE_SCRIPTS`, `src/uniti/regex/analysis.py`) — leaving the requirement unchanged (plain `\b`) for every other script. This directly fixes the reported malfunction: a CJK/Thai term embedded in more of the same script now matches, instead of silently returning zero matches.
- Implementation: `_engine_expression` determines each edge's boundary independently from `expression[0]`/`expression[-1]` (using the `regex` module's own `\p{Script=...}` Unicode property matching, confirmed to support all eight scripts directly) rather than a single generic assertion — so a mixed-script term like `abc中文` still enforces a real boundary on its Latin left edge while relaxing only its Han right edge. Applies only to literal/plain-text "Whole word" search, matching the existing scope (disabled whenever Regex mode is on).
- Verification: `tests/test_regex_analysis.py` — CJK term embedded in continuous CJK text (both with and without a space neighbor), Thai embedded in continuous Thai text, existing Latin word-boundary enforcement unchanged (`cat` still excluded from `category`/`concatenate`), and a mixed-script term relaxing only its CJK edge (all three CJK/Thai cases confirmed to fail against the pre-fix code). Full suite: 1800 passed, 6 platform-only skips.

## BF-040 [P2] — Per-document task-pool fairness and multi-document benchmark foundation

- Reported: 2026-09-13, on B2 (architecture review finding).
- Status: implemented, integrated on `main` (2026-09-17). Scoped and implemented per [Pool 1's task-fairness and schema-flexibility plan](03_implemented/milestones/2026-09-17-pool-1-task-fairness-and-schema-flexibility-plan.md).
- Finding, verified directly: `src/uniti/resources/tasks.py` (`submit`/`_dispatch`) admits work by memory/disk estimate and a global `WorkPriority`, dispatched into one shared worker pool — there is no per-document reservation or round-robin. A document running heavy background search/indexing can starve another document's task-queue-wise (partially mitigated by `foreground=True` bypassing pause, but not by document identity).

Benchmarking first and deciding the mechanism from the data was also rejected — this fix lands first so BF-030/031 can benchmark a corrected pool instead of measuring the starvation this finding already diagnosed.
- Implementation: `PriorityWorkerPool` (`src/uniti/resources/workers.py`) replaced its flat `PriorityQueue` with `{priority tier: {document_key: deque[_WorkItem]}}`; `_pop_next_locked` round-robins across documents with pending work at a tier via `OrderedDict.move_to_end`, so a burst of same-priority tasks from one document can no longer dispatch strictly ahead of another document's task at the same tier. Cross-tier priority ordering is unchanged — only same-tier tie-breaking is now document-aware. `TaskCoordinator._dispatch` threads `TaskSpec.document_key` (already present on the spec, previously unused for scheduling) through to the pool.
- Verification: `tests/resources/test_workers.py::test_round_robin_prevents_one_document_from_starving_another_at_same_priority` — a 5-task burst from one document no longer strictly precedes a second document's single task at the same priority; confirmed to fail against pre-fix code (a `TypeError`, since the pre-fix pool had no `document_key` parameter at all) before being accepted. ## BF-046 — Find/Replace window cannot be moved or dragged to dock/undock

- Reported: 2026-09-14, on B2.
- Status: implemented, integrated on `main`. **Superseded by [BF-048](#bf-048--findreplace-panel-attaches-into-the-editor-pane-tree-instead-of-qmainwindow-docking):** the drag-to-dock/drag-to-undock gestures and the `QDockWidget.addDockWidget` mechanism described below no longer exist — "attached" now means the panel is a real leaf in the editor's pane tree, not a Qt-native dock. The title label has `WA_TransparentForMouseEvents` set so a drag started anywhere on the bar (not just the empty background) is captured, without stealing clicks from the attach/detach button beside it.

## BF-051 — LF→CRLF live conversion lags; CRLF→LF does not

- Reported: 2026-09-15, on B2.
- Status: implemented, integrated on `main`.
- Observation: using the [BF-023](#bf-023--eol-conversion-does-not-take-effect-until-save) live EOL conversion, converting CRLF to LF shows no noticeable lag; converting LF to CRLF does.
- Root cause, confirmed 2026-09-15: the lookaround cost was the actual cause, not the growing-edit size. `_needs_full_prefix` in `src/uniti/regex/search.py` treats any pattern containing a lookbehind (`(?<!...)`) as needing the *entire* scanned prefix retained in memory rather than a bounded window; the old CRLF pattern (`\r(?!\n)|(?<!\r)\n`) and CR pattern (`\r\n|(?<!\r)\n`) both used a negative lookbehind, so the streaming search buffer grew via repeated `buffer += text` without ever being trimmed — an O(n²) cost as the document scanned. The LF pattern (`\r\n|\r`) has no lookaround, stayed within a bounded window, and was unaffected. Reproduced directly: the old CRLF pattern took 0.35s on an 880 KB file vs. 0.15s for the fix, and raised `RegexContextLimitError` outright on a 4.4 MB file (over the 1 MiB retained-context cap) where the fix completed in 0.76s.
- Implementation: `_EOL_CONVERSIONS` in `src/uniti/regex/replace.py` now matches CRLF/CR without lookaround, using ordered alternation (`\r\n|\r|\n` for CRLF, `\r\n|\n` for CR) — since `\r\n` is tried first, a CRLF pair is always consumed as one token, so a lone `\r`/`\n` is distinguished without lookahead or lookbehind. `convert_document_eol` filters out matches already equal to the target text in code, preserving the existing "already-conforming pairs stay untouched" behavior and single-undo-step semantics.
- Verification: full local suite (1,829 tests, 6 expected skips) passed, including the existing CRLF/CR/LF conversion and untouched-pairs regression tests.

## BF-059 — Docked Find/Replace panel sizing: no default 50%, no resize-with-window

- Reported: 2026-09-15, on B3.
- Status: implemented, integrated on `main`.
- Request: the attached (docked) Find/Replace panel should not assume 50% of the main window's height; it should open at whatever size it was last used at; and it must not change height when the main window is resized.
- Root cause, confirmed directly: `FindReplaceWindow._insert_content_into_pane_tree` (`src/uniti/ui/find_replace.py`) attaches the panel by calling `EditorPaneTree.split_view(anchor, Qt.Orientation.Vertical)` (`src/uniti/ui/panes.py`), which always creates its `QSplitter` through `_make_split(..., proportions=(0.5, 0.5))` — the default parameter, never overridden for this call site. Every attach (including every re-attach after detaching) therefore starts at exactly 50/50, with no memory of a previously used size. Separately, `_make_split` never calls `QSplitter.setStretchFactor`, so both panes keep Qt's default stretch factor (1); on any resize of the containing window, `QSplitter` redistributes the size delta between panes in proportion to their current share — so the Find/Replace panel's absolute height changes on every main-window resize even though the user never touched the splitter handle.
- Disposition: (a) tracked in pixels — a fixed height, matching "do not resize"; (b) persisted globally in settings (`find_replace_attached_height`, mirroring `find_replace_geometry`); the `_sync_sizes`/`proportions` drift risk is avoided by not using that path for this split at all (see below).
- Implementation: `EditorPaneTree._make_split`/`split_view` (`src/uniti/ui/panes.py`) gained two new independent, opt-in parameters — `stretch` (a `(int, int)` `QSplitter.setStretchFactor` pair; when given, the ordinary `splitterMoved → _sync_sizes` proportion-tracking connection is skipped for that split, so ordinary user-created Split Right/Split Down splits are completely unaffected) and `fixed_sizes` (literal starting pixel sizes passed straight to `QSplitter.setSizes`, instead of proportions scaled against the pane tree's current — and, before its first real layout pass, unreliable — height). `FindReplaceWindow._insert_content_into_pane_tree` now calls `split_view(..., stretch=(1, 0), fixed_sizes=(1, self._attached_height))`: `fixed_sizes=(1, height)` gives the Find/Replace pane exactly `height` (any surplus/deficit lands on the editor pane, per Qt's own size-negotiation, confirmed directly — an initial proportion computed from the pane tree's current height was tried first and produced wildly wrong results, since that height is unreliable before layout, which is why the fix uses literal starting sizes instead), and `stretch=(1, 0)` (editor absorbs all of every later window-resize delta, panel absorbs none) keeps it pinned afterward. A new `FindReplaceWindow.attachedHeightChanged` signal (emitted from a dedicated `splitterMoved` connection on that one split, independent of `_sync_sizes`) fires when the user manually drags the attached splitter; `UNITIMainWindow` persists it to the new `Settings.find_replace_attached_height` field (also seeded on `FindReplaceWindow` construction in both standalone and service-owned/multi-window paths) via the existing `dataclass_replace` + `_save_settings()` pattern.
- Verification: `tests/ui/test_find_replace_contract.py` (3 tests: attach height is the remembered value rather than ~50% of the window, the attached panel's height is unchanged by a main-window resize, and manually dragging the splitter updates the remembered height for the next attach) and `tests/ui/test_panes.py`/`tests/app/test_settings.py` for the new `split_view` parameters and settings field.

## BF-061 — Format Document / Minify Document for JSON, XML, and Markdown

- Reported: 2026-09-15, on B3.
- Status: implemented, integrated on `main`. Planned in [2026-09-15-format-document-plan.md](03_implemented/milestones/2026-09-15-format-document-plan.md).
- Request: a "structure refactoring" feature for JSON/XML/Markdown documents, beyond the existing color-only syntax highlighting (BF-027/BF-041).
- Scope, confirmed with the user 2026-09-15: pretty-print ("Format Document") plus a reverse compact form ("Minify Document") for JSON and XML; Markdown gets Format Document only (no minify concept). This is text reformatting only — re-indentation, spacing, and whitespace normalization — not AST-aware structural refactors (no key sorting, tag rename, heading promotion, etc.); that would be a materially larger, separately-scoped effort if wanted later.
- Scope, confirmed with the user: validate first. JSON must parse as valid JSON and XML must be well-formed before formatting; an invalid document is refused with the parser's reported line/column, and the document is left untouched. Markdown has no strict grammar to fail against, so it always proceeds.
- Implementation: `src/uniti/core/reformatters.py` — `JSON`/`XML`/`MARKDOWN` `Reformatter`s keyed by the existing `syntax_profile.key` (BF-027/041). JSON uses the standard-library `json` module (indent 2 for format, `separators=(",", ":")` for minify; `JSONDecodeError.lineno`/`.colno` surface as the error position). XML deliberately uses `xml.dom.minidom`, not `ElementTree`, because ElementTree silently drops comments/processing instructions — a custom recursive pretty-printer indents element-only structure but leaves any element containing significant text (mixed content) completely untouched internally, since naive reformatting would inject whitespace into meaningful text (confirmed this was a real bug during implementation: `dom.toprettyxml()` alone splits mixed-content text around child elements onto separate indented lines, corrupting it); minify collapses only purely-whitespace inter-tag text. Both preserve the original XML declaration verbatim (including `encoding=`/`standalone=`) rather than minidom's regenerated bare one, and add no declaration when the source had none. Markdown gets a modest, explicitly-bounded line-based normalizer (ATX heading spacing, unordered-list bullet character, blank-line collapsing to one, trailing-whitespace/final-newline cleanup) that leaves fenced code-block content completely untouched and does not treat a leading `#!` (shebang-style) line as a heading; it is not a CommonMark parser and does not reflow paragraphs, align tables, or touch front matter.
- Wiring: `Format → Format Document` / `Format → Minify Document` (`UNITIMainWindow.format_current_document`/`minify_current_document`, `src/uniti/ui/main_window.py`), plain `QAction`s matching the existing Format-menu convention (Encoding/Line Endings are not in the command-registry/Hotkeys system either). Enabled state follows the active view's `syntax_profile.key`, refreshed on every tab/view change. Applied as one `document.replace(0, total_chars, formatted)` — one Undo step, and a no-op (no history entry) when the formatted text is already identical, consistent with `convert_document_eol`. Documents over `MAX_REFORMAT_CHARS` (16 Mi characters — formatting needs the whole document in memory, unlike UNITI's other streaming bulk edits) are declined with an explanatory dialog rather than attempted.
- Verification: `tests/core/test_reformatters.py` (20 tests: format/minify round-trips, invalid-input line/column errors, mixed-content/comment/CDATA/declaration fidelity and idempotency for XML, fenced-code and shebang preservation for Markdown) and `tests/ui/test_main_window_contract.py` (menu enablement per syntax type across tab switches, one-step Undo/Redo, the invalid-JSON error dialog leaving the document unchanged, and the size-cap rejection path). Full suite: 1858 passed, 6 platform-only skips.

## BF-068 — Detached Find/Replace panel geometry can restore off-screen after a monitor is removed

- Reported: 2026-09-17, on B3 ("investigate geometry / position of f/r pane when additional screens are removed").
- Status: implemented, integrated on `main`.
- Root cause, confirmed by reading every geometry-restore call site: the detached Find/Replace panel's saved `(x, y, width, height)` is restored verbatim via `QWidget.setGeometry` in four places — `FindReplaceWindow.detach()` (its own remembered pre-attach placement), `FindReplaceWindow.restore_state()` (session restore from a `FindReplaceRecord`), and `UNITIMainWindow.__init__`/`UNITIService.find_replace` (both restoring `Settings.find_replace_geometry` at startup). None of them checked whether that position still corresponds to any currently connected screen. If the panel was last placed on an external monitor that has since been unplugged (the most common real cause), every one of those four restores would set the window's geometry to coordinates outside every current screen — Qt does not reliably reposition a window whose explicit `setGeometry` call lands off-screen, so the panel becomes practically unreachable (no visible titlebar/handle to drag it back), with no existing code anywhere in the app checking screen geometry at all (confirmed by search — the only other `QScreen` reference in the codebase is unrelated, in `capabilities.py`).
- Fix: new `uniti.ui.screen_geometry` module — `clamp_geometry_to_screens(geometry, available_screens)` (pure, Qt-free of behavior, takes plain `(x, y, width, height)` tuples so it's testable without a real multi-monitor `QApplication`) returns the saved geometry unchanged if it overlaps *any* currently connected screen's available area (so a deliberate, still-valid placement is never "corrected" away), and otherwise recenters it (keeping its saved width/height, capped to fit) on the first available screen; `current_screen_geometries()` is the thin `QGuiApplication.screens()` adapter. `FindReplaceWindow` gained `set_detached_geometry(geometry)` (clamps, then applies, then updates the in-memory `_detached_geometry`), used at all four restore sites in place of the previous raw `setGeometry` calls.
- Scope, deliberately not touched: `UNITIMainWindow`'s own session-restored window geometry (`restore_window_record`, `self.setGeometry(*record.geometry)`) has the identical latent gap, but the report scoped this to the Find/Replace panel specifically; recorded here as a related, not-yet-fixed finding for a future pass, not silently left unmentioned.
- Verification: `tests/ui/test_screen_geometry.py` (6 tests: unchanged when overlapping one/either of several screens, recentered when the saved screen no longer exists, capped when larger than the available screen, partial-overlap still counts as reachable, and no-screen-information is a no-op) and two `tests/ui/test_find_replace_contract.py` integration tests (`detach()` and `restore_state()` each clamp a geometry saved on a now-removed screen, verified by monkeypatching `current_screen_geometries`). Full suite green.

## BF-069 — Per-view text-direction override, and an RTL end-of-text marker overlap fix

- Reported: 2026-09-17, a self-identified BF-064 follow-up rather than a new user report — flagged directly by the code comments introduced while building it: Auto's first-strong-character rule "misjudges a predominantly-RTL paragraph that happens to *start* with a Western character (a verse number's LTR text, an abbreviation), classifying the whole line LTR."
- Status: implemented, integrated on `main` (`82b011e`).
- Gap: Auto (BF-064's `is_rtl_paragraph`, UAX #9 first-strong-character detection) only ever looks at what comes first in a line. A predominantly-RTL paragraph that happens to open with Western text — a verse number, an abbreviation — gets classified LTR for its entire line, mis-shaping and mis-ordering everything that follows. Confirmed directly: `is_rtl_paragraph("John 3:16 قال يسوع من آمن به")` returns `False`.
- Fix: a per-view "primary direction" override — Auto (default, unchanged per-line detection) / Left-to-Right / Right-to-Left — that bypasses per-line detection entirely when set. Threaded through the full rendering/editing stack: `EditorState._cursor_line_is_rtl` and its four `move_visual_*` callers take an optional `direction_override`; `HorizontalLayouts` and `ShapedRowProvider` (the non-wrapped and wrapped layout providers) take a `direction_override` constructor argument that bypasses `direction_for_text`; `UNITITextView` owns the switch (`_direction_override`, exposed as `text_direction_override`/`set_text_direction_override`), threads it into both layout providers' cache-invalidation signatures, and consults it in `_direction_for_window` before the per-line cache.
- Also found and fixed while building this: the EOL/overflow whitespace marker's fixed `+3px` rightward nudge only lands in empty margin for LTR, where "further along reading direction" is also "further right on screen." For RTL, reading continues to the *left* of the line's end, so the same rightward nudge drew the marker glyph back on top of the line's own text instead of past its edge — confirmed directly with a 36-character Arabic line whose EOL marker's bounding box fully overlapped its own text's bounding box before the fix. Fixed with a new `UNITITextView._end_of_text_marker_x(left, glyph, *, rtl)` that places the glyph's own rendered width entirely to the left of `left` for RTL, used at both the EOL and overflow marker call sites.
- Persistence: the override is per-view state, not a global setting (unlike Whitespace/Tab Width) — saved in `ViewRecord.extra["text_direction_override"]` only when non-default, restored on session load.
- UI: a **View → Text Direction** submenu (Auto/Left-to-Right/Right-to-Left, exclusive radio actions), mirroring the existing Whitespace/Tab Width submenus. Switching tabs resyncs the radio group to the newly active view's own saved choice, since — unlike those two — this state is per-view, not global.
- Verification: new tests in `tests/ui/test_text_view_contract.py` (end-of-text marker clearance in both directions; a real-widget RTL EOL-marker positioning test; the override fixing the exact `John 3:16`-style misjudged line, confirmed against real hit-testing rather than just the reported direction; override-value validation; session round-trip persistence, including confirming the default Auto is never written) and a new `tests/ui/test_main_window_contract.py` test confirming per-view isolation and tab-switch resync of the menu's radio state. Full suite green: 1,991 passed, 6 platform-only skips.

## BF-071 — Multiline-aware syntax highlighting

- Reported: 2026-09-17, un-parking the remaining scope of the ["File-type profiles and syntax highlighting"](04_parked/CATALOG.md#file-type-profiles-and-syntax-highlighting) parked capability's "Not incremental or multiline-aware" bullet, directed at the user's request.
- Status: implemented, integrated on `main`.
- Gap: every profile's tokenizer (`uniti.core.syntax_profiles`) ran independently per visible row/window with no memory of anything before it, so a construct spanning more than one logical line — an XML `<!-- -->` comment, an `<![CDATA[ ]]>` section, a Markdown fenced ` ``` `/`~~~` code block, a YAML `|`/`>` block scalar — highlighted correctly only on whichever single line happened to contain both its opening and closing markers, and not at all on the lines in between.
- Fix: `SyntaxProfile.tokenize`'s contract grew from `Callable[[str], tuple[SyntaxToken, ...]]` to `Callable[[str, state], tuple[tuple[SyntaxToken, ...], state]]` — each call now takes the tokenizer's state as of the start of the line and returns the state to carry into the next line. `SyntaxProfile` gained an `initial_state` field (`None` for every profile). JSON/SFM/CSV/TSV/Plain Text stay fully stateless (wrapped trivially, their actual tokenizing logic unchanged) since none of them has a construct that can span a line under their current rule sets. XML, Markdown, and YAML gained real hand-written stateful tokenizers (`_xml_tokenize`, `_markdown_tokenize`, `_yaml_tokenize`) that track "inside an unterminated comment/CDATA section," "inside an unterminated fence (which character, how many)," and "inside a block scalar (at what indent)" respectively.
- UI wiring (`UNITITextView`): a new `self._syntax_start_states: dict[int, object]` caches the tokenizer's state at the *start* of each logical line, built incrementally — whenever the first visible row of a logical line is painted (`column_start == 0`), its resulting end-state is cached for `line + 1`. This mirrors BF-064's `_line_directions` cache pattern (a dict keyed by logical line, wholesale-cleared on every document edit in `refresh_document_revision`) rather than inventing a new caching shape; also cleared on `set_syntax_profile` since a state value from one profile is meaningless to another. A logical line whose start state isn't cached yet (a cold cache, or a scroll/search jump straight into an unvisited region of a huge file) falls back to the profile's `initial_state` rather than walking the whole document backward to compute it exactly — a deliberate, bounded approximation, not a full incremental-parsing subsystem: it self-corrects as soon as the user scrolls through the actual opening in order, and never risks the huge-file-safety property the original bounded per-row design was built to guarantee.
- Deliberate scope cuts, recorded rather than silently left as gaps: state threads across whole *logical* lines only, not within one very long logical line's own wrapped/horizontal-scroll rows (a construct opening and closing within different visible rows of the *same* giant line is not handled — the overwhelmingly common real case is separate logical lines, which is what BF-071 was un-parked to fix). CSV's quoted-field embedded newlines are unhandled: a quoted CSV field containing a literal newline changes what a "row" even is, entangling this with the document's own line segmentation rather than staying presentation-only, a materially larger and differently-shaped change. Markdown HTML block comments (`<!-- -->`) are unhandled: unlike fenced code blocks, no single-line recognition existed for them at all before this pass, so adding them would be new tokenizing scope rather than an extension of an already-flagged gap.
- Verification: 6 new tests in `tests/core/test_syntax_profiles.py` (all 14 existing tokenizer tests migrated to the new `(text, state)` → `(tokens, state)` signature via a small test helper, unchanged in what they assert, plus dedicated multi-line tests: an XML comment and a CDATA section each split across three `tokenize` calls confirming state and token spans at open/continue/close; a Markdown fence tracked across three lines including a fence-length-mismatch case that must not close early; a YAML block scalar tracked by its own established indent, including a blank line inside it and a dedent that correctly ends it and resumes normal tokenizing) and 3 new UI tests in `tests/ui/test_text_view_contract.py`: a real rendered-pixel test confirming a line with *no comment markers of its own* ("middle of comment") still paints in the comment color purely because state carried over from the previous line — the exact real-world bug this closes; a cache test confirming `_syntax_start_states` populates on paint and clears on `refresh_document_revision`/profile change; and a cold-cache scroll-jump test confirming no crash. Full suite green: 2,027 passed (9 new), 6 platform-only skips, no regressions.

## BF-072 — Match Report replacement-preview mis-renders a literal tab in the replacement pattern

- Reported: 2026-09-18 ("bug still remains in replace display for match panel: `[\1]\t"\2"` ... display -> `[aaa]"<tab>yyyy"`").
- Status: implemented, integrated on `main`.
- Observation: with a replacement pattern containing a literal tab escape adjacent to a capture-group backreference and other literal text, e.g. `[\1]\t"\2"` against a match of `aaa` and `yyyy`, the Match Report's per-group-colored replacement-preview row (BF-052 item 5) renders visibly out of order — expected `[aaa]` + TAB + `"yyyy"`, observed `[aaa]"` then the tab, then `yyyy` with the closing quote effectively lost/misplaced.
- Root cause, confirmed by reproducing at the data layer directly (not assumed): `_replacement_preview` (`src/uniti/regex/captures.py`) builds the correct string — a direct REPL reproduction against `[\1]\t"\2"` returned `'[aaa]\t"yyyy"'`, byte-for-byte correct — so the bug is purely in the paint layer, not the expansion logic. `CaptureReportDelegate._paint_content_group_spans` (`src/uniti/ui/capture_report_delegate.py`) slices the preview string into per-group-colored segments and advances its own x-cursor between successive `painter.drawText(...)` calls using `QFontMetrics.horizontalAdvance(text)`. `horizontalAdvance` doesn't account for tab-stop expansion, but `QPainter.drawText` does apply it when actually rendering a segment containing `\t` — so the advance computed for a segment like `"]\t\""` undershoots the tab's real rendered width, and the *next* colored segment (`"yyyy"`) is drawn at a stale x position that overlaps/precedes where the tab-expanded segment actually rendered. Only the colored multi-span preview path is affected (a replacement with both a backreference and a literal tab in its literal text); the plain single-color fallback path (a single whole-string `drawText` call in `content_rect`) is unaffected, since it never splits the string into separately positioned segments.
- Fix implemented 2026-09-18, following the root cause's own named direction: `_paint_content_group_spans` now lays the whole `content` string out once with a single `QTextLayout` (`setTextOption(NoWrap)`, one `QTextLayout.FormatRange` per group span setting only that range's `QTextCharFormat` foreground color) instead of measuring and drawing each colored segment separately. Positioning is no longer computed by the delegate at all — `QTextLayout.draw()` paints the whole line, tabs and all, in one internally-consistent pass; per-group color changes which `QTextCharFormat` a range uses, never where anything is positioned, so `horizontalAdvance`/`drawText` can no longer disagree about a tab's width. The width-fits check (deciding whether to fall back to the plain elided single-color path) now uses the same layout's `naturalTextWidth()` for the same reason — the old check (`QFontMetrics.horizontalAdvance(content)`) had the identical tab-blind-spot bug, just for the fit decision rather than positioning. `_draw_content_segment` (the old per-segment helper) is removed; the `vertical` alignment flag is no longer threaded through (manual vertical centering from the layout's own `line.height()` replaces `Qt.AlignmentFlag.AlignVCenter`, since `QTextLayout` doesn't take Qt's alignment-flag API directly).
- Verified: `tests/ui/test_capture_report.py::test_colored_group_spans_do_not_overlap_across_a_literal_tab` — renders the exact `[\1]\t"\2"`-shaped content to an offscreen `QImage`, confirms each group's own color paints as a single contiguous, correctly-ordered column range (group 1 entirely before group 2), and cross-checks each group's start column against `QTextLayout.cursorToX()` on an independent plain layout of the same string (within 5px). Confirmed directly, not assumed: re-ran this exact check against the pre-fix algorithm (reproduced standalone, not by reverting and re-testing in place) — it measured "yyyy" starting 45.6px off from the correct position, correctly failing the new test's tolerance; the fix measures within 2px. (The literal pixel *overlap* originally reported could not be reproduced in the offscreen `QPA` backend used for testing — same caveat as [BF-019](#bf-019--match-report-capture-group-row-indentation-and-truncated-label) — so this test verifies the corrected position against ground truth rather than the visual overlap symptom directly; the underlying measurement-inconsistency bug and its fix are unambiguous regardless.) Full existing `test_capture_report.py` suite (35 tests) passes unchanged.

## BF-083 — Find/Replace: a negated character class (`[^...]`) falsely forces full-document context retention, discarding all matches on a large document

- Reported: 2026-09-21, live during this feedback-triage session ("regex requires more bounded context" — the exact status-line text shown; "ther are 80+ open files. regex: `\\(\w+)\s([^\\]+)\\\1\*` et to regex\ whole doc"; "tyhe very same regext f/r worked before the latest updates").
- Status: implemented, integrated on `main`.
- Root cause, confirmed by reproduction before any fix was attempted: `_needs_full_prefix` (`search.py:64`, unchanged since the original `51c21c9` "add bounded regex document search" commit — not a recent regression, despite the report) did a naive `"^" in source` substring check to decide whether `_iter_engine_matches`'s incremental windowed scan must retain the *entire* scanned buffer from the start (`retain_prefix=True`) rather than trimming safely-resolved content after each chunk. That check has no awareness of character-class syntax, so a negated class like `[^\\]` — "any character except a backslash," an extremely common SFM/USFM marker-pairing idiom, and exactly the user's reported pattern — was mistaken for a `^` line-start anchor. With `retain_prefix` wrongly `True`, `context_start` (`search.py:260`) stays `0` on every iteration, so the buffer only ever grows as each new `window_chars` chunk is appended, regardless of how well-bounded the pattern actually is, until it exceeds `max_context_chars` (1 MiB default) and `RegexContextLimitError` is raised — discarding every match already found, not just failing to find new ones.
- Confirmed directly with a real reproduction before writing any fix: a synthetic 3,000,011-character well-formed SFM-like document (dense `\marker` lines, a handful of `\qt ... \qt*`-style paired spans) searched with the user's exact pattern raised `RegexContextLimitError` after correctly finding 382 matches — discarding all of them from the caller's point of view, since `find_all`'s `MatchStore` never receives them. A parallel unwindowed `compiled.finditer()` scan of the same text found exactly 1,023 matches, confirming both that the pattern and content were unremarkable (no pathological backtracking) and that the windowed engine was correctly finding matches right up until the false context-limit trip discarded the run.
- Why the existing SFM-marker regression test (`tests/test_regex_search.py::test_backreference_marker_pair_matches_across_tiny_windows_for_each_marker_name`) didn't already catch this: it uses `(?:(?!\\\1\*)[\s\S])+` for the "any character" span, not `[^\\]+` — `[\s\S]` contains no `^` at all, so it never exercised the buggy branch, and its tiny fixture text (~70 chars) couldn't have reached the default 1 MiB budget regardless.
- Fix: a new `_strip_character_classes(source)` helper walks the pattern source once, tracking character-class (`[...]`) boundaries (including the one class-syntax wrinkle that a literal `]` immediately after `[` or `[^` doesn't close the class) and escape pairs (`\\` plus the next character, which can never itself be a class delimiter or, inside a class, meaningful content). Everything *inside* a class is replaced with placeholder characters — including a leading `^` negation marker — before `_needs_full_prefix` runs its substring checks, so `[^\\]`'s `^` no longer reads as an anchor. Everything *outside* a class passes through unchanged (including escape pairs), since that's exactly where real `\A`/`\G`/lookbehind syntax and a genuine `^` anchor live, and those must still be detected correctly — confirmed by keeping `test_prefix_retaining_regex_is_bounded_by_context_limit`'s existing `^a.*Z` case passing unchanged (a real anchor must still force `retain_prefix=True` and correctly bound-check).
- Verified: `tests/test_regex_search.py::test_negated_character_class_is_not_mistaken_for_a_line_anchor` (direct unit coverage of `_needs_full_prefix` — the user's exact pattern, a plain `[^abc]+`, a literal `]` as a class's first content character, plus real top-level `^`/lookbehind/`\A`/`\G` cases confirming they're still detected) and `::test_backreference_pattern_using_a_negated_class_is_not_bounded_by_a_false_prefix_requirement` (end-to-end: the same marker-pair fixture as the existing backreference test, rewritten with `[^\\]+`, against a deliberately small `max_context_chars` that reproduced the failure pre-fix, now completing correctly with the same three matches). Full suite green: 2,069 passed (2 new), 6 platform-only skips, no regressions.
