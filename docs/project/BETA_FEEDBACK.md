## BF-012 — Full Unicode case folding misses a match with one-character search windows

- Found: 2026-09-08 during documentation-example verification, on B2; this is an internal finding, not a user report.
- Status: implemented, integrated on `main` (`596c88f`, "1b2 feedback implementation"). Doc note below describes the pre-fix state.
- Reproduction: compile `(?fi)straße` or `(?V1)(?i)straße` and search `STRASSE` through `search_document(..., options=SearchOptions(window_chars=1))`. Direct engine matching returns `(0, 7)`; UNITI returns no matches.
- Evidence boundary: windows of 8 and the default 65,536 characters return the expected match. A default-window probe with 65,531 preceding ASCII characters also passes. A failure with the production default window has not been reproduced; the one-character-window result still requires investigation before claiming complete streaming equivalence for full case folding.
- Root cause and fix: `_iter_engine_matches` (`src/uniti/regex/search.py`) defers any unsafe/partial-match scan until at least `_MIN_UNSAFE_SCAN_CHARS` (8) characters are buffered, specifically because the `regex` engine's `finditer(..., partial=True)` reports an unreliable partial-match start position once the scanned buffer is shorter than a variable-width full-casefold literal's full character range (e.g. `ß` folding to/from `ss`/`SS` under `(?f)`) — see the module docstring comment above `_MIN_UNSAFE_SCAN_CHARS`. - Reported: 2026-09-10, on B2.
- Status: defensive hardening applied, integrated on `main` (2026-09-13, part of the P1 F/R rework, Phase 2); both previously-suspected causes are now addressed or ruled out and end-to-end regressions pass in single- and two-window scenarios (2026-09-15). **Native affected-host confirmation still required** before this can be treated as fully resolved — see the investigation note below.

- Investigated 2026-09-13, status: root cause not confirmed, defensive change applied. - Methodology note: an initial attempt to reproduce a failure by sending the key via `QTest.keyClick` (rather than `QTest.keySequence`) appeared to show the shortcut never firing, with either one or two windows open — but this was a test-harness artifact, not an app bug. `QTest.keyClick` delivers a plain `QKeyEvent` directly to the target widget and does not exercise Qt's `ShortcutOverride`/shortcut-matching dispatch at all, so it cannot demonstrate this bug either way; `QTest.keySequence` is the correct simulation for shortcut delivery, and an existing single-window regression (`tests/ui/test_main_window_contract.py::test_zoom_shortcut_reaches_the_panel_while_find_input_has_focus`) already used it and passes. Anyone re-investigating this should use `QTest.keySequence`, not `QTest.keyClick`, or they will chase a false reproduction.
- Current assessment: both the single-window and two-window paths now have passing, methodologically-sound regressions using the correct Qt shortcut-simulation API, and both theories previously raised (`QTextEdit` claiming the override; ambiguous shortcut across windows) are addressed or ruled out. No further code change is identified. Native affected-host confirmation remains the only way to fully close this, since headless/offscreen Qt testing cannot certify real macOS window-manager/keyboard event delivery — if it still reproduces natively with these regressions green, the cause lies outside anything modeled here (e.g. an OS-level key-combo interception) and needs a fresh native investigation, not a rework of this panel's shortcut wiring.

## BF-030 — No benchmark coverage for many concurrently open documents

- Reported: 2026-09-11, on B2.
- Status: recorded; implementation pending.
- Observation: the existing large-file benchmarks (`benchmarks/scenarios.py`'s `giant_line` and `resource_recovery` scenarios) each exercise a single corpus; no scenario opens several documents concurrently and measures behavior.

At ~2 MB each, 100 files is roughly 200 MB of raw content — small next to this project's existing single-large-file targets (a 100 MiB "routine" tier and a 1 GiB sparse "design_target" tier already exist for one file), so the new stress dimension here is document *count*, not per-file size. This scale is a realistic profile for a working set of many small-to-medium structured files (the SFM/USJ formats referenced in [BF-027](#bf-027--file-type-syntax-highlighting-profiles-xml-yml-json-sfm-md) suggest this maps to a real multi-file translation/publishing workflow, not a synthetic edge case).

The originally requested 100 files @ ~2 MB is a deliberately larger, rounder benchmark target than this real profile (80 files, largest ~500 KB) — both are worth covering: the real profile as the primary target, the rounder figure as headroom.
- Acceptance to define during implementation: a new benchmark scenario and/or acceptance test opening documents at both the real profile (~80 files, largest ~500 KB) and the requested headroom profile (~100 files, ~2 MB each), measuring cache eviction behavior/re-index cost when switching among them, worker-pool contention, aggregate session-save size against the 256 MiB cap, and whether any of the above degrades below the existing single-document performance gates.

## BF-034 — "Whole word" malfunctions for non-Latin (CJK/Thai) text

- Reported: 2026-09-11, on B2.
- Status: implemented, integrated on `main`.
- User position: `\b ... \b` malfunctions for non-Latin text — the "Whole word" option fails to do what it claims for these scripts.
- Root cause, verified directly: word-boundary matching (`\b`) is fully supported by the `regex` module and is how this app already implements "Whole word" (`src/uniti/regex/analysis.py:148`, `\b(?:...)\b`, literal/plain-text search mode only — disabled whenever Regex mode is on). The engine call itself does not error or misbehave; the failure is that `\b`'s boundary is defined on a generic Unicode word-character class that only produces useful term isolation when a script is space-delimited. Tested directly: a literal "whole word" search for `中文` matches inside `中文 测试` (space-separated) but not inside `中文测试` (no space) — it can only match at the edges of a punctuation/whitespace-delimited run, never around an individual CJK term embedded in continuous text. The same applies to Thai. Net effect for the user: the feature silently fails to isolate a whole word for CJK/Thai, which is a malfunction from the product's perspective regardless of the underlying mechanism being "as designed" for space-delimited scripts.
- Acceptance to define during implementation: what a corrected, script-aware "whole word" boundary should do for CJK/Thai (e.g. a different boundary rule per detected script) — there is no universal literal-substring definition of "whole word" for scripts without word-delimiting whitespace, so this needs a real design decision, not a one-line fix.
- Design decision: rather than inventing a segmentation-based notion of "word" for these scripts (impossible without a dictionary this engine doesn't have), a literal "Whole word" search skips the `\b` requirement specifically on whichever edge of the search term falls in a script conventionally written without spaces — Han, Hiragana, Katakana, Hangul, Thai, Lao, Khmer, Myanmar (`_NO_SPACE_SCRIPTS`, `src/uniti/regex/analysis.py`) — leaving the requirement unchanged (plain `\b`) for every other script. This directly fixes the reported malfunction: a CJK/Thai term embedded in more of the same script now matches, instead of silently returning zero matches.
- Implementation: `_engine_expression` determines each edge's boundary independently from `expression[0]`/`expression[-1]` (using the `regex` module's own `\p{Script=...}` Unicode property matching, confirmed to support all eight scripts directly) rather than a single generic assertion — so a mixed-script term like `abc中文` still enforces a real boundary on its Latin left edge while relaxing only its Han right edge. Applies only to literal/plain-text "Whole word" search, matching the existing scope (disabled whenever Regex mode is on).
- Verification: `tests/test_regex_analysis.py` — CJK term embedded in continuous CJK text (both with and without a space neighbor), Thai embedded in continuous Thai text, existing Latin word-boundary enforcement unchanged (`cat` still excluded from `category`/`concatenate`), and a mixed-script term relaxing only its CJK edge (all three CJK/Thai cases confirmed to fail against the pre-fix code). Full suite: 1800 passed, 6 platform-only skips.

## BF-046 — Find/Replace window cannot be moved or dragged to dock/undock

- Reported: 2026-09-14, on B2.
- Status: implemented, integrated on `main`. **Superseded by [BF-048](#bf-048--findreplace-panel-attaches-into-the-editor-pane-tree-instead-of-qmainwindow-docking):** the drag-to-dock/drag-to-undock gestures and the `QDockWidget.addDockWidget` mechanism described below no longer exist — "attached" now means the panel is a real leaf in the editor's pane tree, not a Qt-native dock. - Report: the Find/Replace window can no longer be moved by dragging (only resized), and dragging it to dock/attach no longer works either — it looks like the window lost its title bar. While floating and dragging, a translucent `_DockDropIndicator` overlay previews a drop band across the bottom third of the panel's known host (`self._dock_host`, always set once the panel has been attached to a main window) whenever the cursor is over it; releasing there calls `attach_to(host)` to dock it, mirroring the existing "Attach Find/Replace" button's behavior but triggered by the drop location instead of a fixed always-bottom toggle. The title label has `WA_TransparentForMouseEvents` set so a drag started anywhere on the bar (not just the empty background) is captured, without stealing clicks from the attach/detach button beside it.
- Verification: three new regression tests in `tests/ui/test_find_replace_contract.py` (`test_find_replace_title_bar_drag_moves_a_floating_window`, `test_find_replace_title_bar_drag_undocks_an_attached_panel`, `test_find_replace_title_bar_drag_docks_a_floating_panel_dropped_on_its_host`), each confirmed to fail against the pre-fix code before being accepted. Full suite: 1750 passed, 6 platform-only skips, no failures.

## BF-048 — Find/Replace panel attaches into the editor pane tree instead of QMainWindow docking

- Reported: 2026-09-14, on B2.
- Status: implemented, integrated on `main`.
- Report: "the f/r window needs to ATTACH TO or be INSERTED INTO the text window. the F\R windows use a different 'class' of panel than the text windows." Confirmed by review: the editor tabs/splits are a custom `QSplitter`-based tree (`EditorPaneTree`/`PaneLeaf`, `src/uniti/ui/panes.py`), unrelated to Qt's native docking system, while the attached Find/Replace panel was a `QDockWidget` docked to the whole `QMainWindow` via `addDockWidget(BottomDockWidgetArea, ...)` — a strip living outside the central widget entirely, in a different widget-class hierarchy than the editor content it sits alongside. Not previously scoped anywhere (checked this log and the B2 rework plan — genuinely new feedback). Presented with three remediation shapes; the user chose full pane-tree integration.
- Design: `FindReplaceWindow` keeps its full public surface (`attach_to`/`detach`/`release_from`/`placement`/`export_state`/`restore_state`/etc.) so `main_window.py`/`service.py`'s existing attach/detach orchestration (`_sync_find_replace_host`, window register/unregister, active-view tracking) is unchanged — only what `attach_to`/`detach` *do* to the widget changed. The panel's actual UI content (`self.content`, a new `_FindReplaceContentHost(QWidget)`) gained a fixed `view_id` (`FIND_REPLACE_VIEW_ID`) and a `viewFocused` signal — the minimal contract `EditorPaneTree.add_view`/`split_view` (`panes.py`) already require, confirmed to need zero panes.py changes for basic insertion. `EditorPaneTree.add_view` gained one small new parameter, `title: str | None`, threaded to `PaneLeaf.add_view`, so a non-document tab can supply its own label instead of the existing fallback (`view.document.path.name`, which a non-document widget doesn't have).

Detaching/closing the pane-tree tab does the reverse (`take_view` + `close_leaf`-if-empty, the same collapse pattern already used by `EditorPaneTree.remove_shell_view` for session placeholders).

Rebuilding detached mode atop the pane tree would mean popping a full new document window (menu bar, status bar, tab strip) around a single Find/Replace tab, a real regression from today's compact floating panel — out of scope.
  - `main_window.py`: `_tab_label`/`_close_tab`/`_close_view_id` special-case the Find/Replace view id (closing the tab parks it back in the floating shell without forcibly showing it, mirroring a native dock-close-button's "hide, don't destroy"); `_on_current_changed` no longer resets the window title/status bar to the empty-window state when Find/Replace's pane has focus but other documents remain open; `_on_pane_view_selected` no longer treats the Find/Replace view id as an unresolved session-restore placeholder; `view_ids` now excludes it (it isn't a document, so it shouldn't appear in "close all documents"/"is any tab an unresolved placeholder" checks — a real bug caught by an infinite-loop hang in a reentrancy test, see Verification).
  - `session_runtime.py`: a captured session's pane tree prunes the Find/Replace leaf back out (and collapses the split) before persisting, since it isn't a `ViewRecord` — it has its own separate `find_replace` manifest field — so `SessionManifest`'s "every pane view belongs to a known view" validation stays satisfied; re-attaching after restore recreates the split fresh via `restore_shell`'s existing `attach_find_replace()` call, unchanged.
- Verification: two real reentrancy bugs were found and fixed during testing, not just test-assertion updates — (1) removing a view from a pane tree fires synchronous Qt signals (`take_view` → active-view-changed) that cascade back into `set_active_view`/`_sync_find_replace_host`/`attach_to` before the original call finished, causing unbounded recursion; fixed with a `_changing_placement` reentrancy guard at the top of `attach_to`/`detach`/`release_from`/the tab-close handler. (2) `main_window.view_ids` returning the raw pane tree's ids (including Find/Replace's) made `close_all_documents`'s "is every tab resolved" check spuriously true, hanging on a modal dialog in headless tests; fixed by excluding the Find/Replace view id from `view_ids`. Both were caught via `faulthandler`-instrumented stack dumps of hanging tests, not guessed at. Existing tests across `tests/ui/test_find_replace_contract.py`, `tests/app/test_service.py`, `tests/app/test_session_orchestration.py`, `tests/test_a21_cross_platform_acceptance.py`, `tests/performance/test_sustained_lifecycle.py`, `tests/test_alpha_smoke.py`, `tests/test_a20_recovery_session_acceptance.py`, and `tests/ui/test_capture_report.py` that asserted the old `QDockWidget`-parenting behavior (`panel.parentWidget() is window`, bare `QMainWindow()` hosts) were updated to the new pane-tree-membership checks; the two BF-046 drag-to-dock/undock tests were removed (that mechanism no longer exists) and replaced with a test confirming the floating shell's title bar only ever appears while detached. ## BF-050 — Match Report should default to showing 3 full matches, not 3 rows

- Reported: 2026-09-14, on B2. Explicitly queued by the user ("que for next implementation").
- Status: implemented, integrated on `main`.
- Request: show 3 full matches in the Match Report panel.
- Note distinguishing this from prior work: [BF-019](#bf-019--match-report-capture-group-row-indentation-and-truncated-label) already set `_CAPTURE_VIEW_MIN_VISIBLE_ROWS = 3` (`src/uniti/ui/find_replace.py`), which guarantees a minimum viewport height of 3 *row-heights*. ## BF-051 — LF→CRLF live conversion lags; CRLF→LF does not

- Reported: 2026-09-15, on B2.
- Status: implemented, integrated on `main`.
- Observation: using the [BF-023](#bf-023--eol-conversion-does-not-take-effect-until-save) live EOL conversion, converting CRLF to LF shows no noticeable lag; converting LF to CRLF does.
- Root cause, confirmed 2026-09-15: the lookaround cost was the actual cause, not the growing-edit size. `_needs_full_prefix` in `src/uniti/regex/search.py` treats any pattern containing a lookbehind (`(?<!...)`) as needing the *entire* scanned prefix retained in memory rather than a bounded window; the old CRLF pattern (`\r(?!\n)|(?<!\r)\n`) and CR pattern (`\r\n|(?<!\r)\n`) both used a negative lookbehind, so the streaming search buffer grew via repeated `buffer += text` without ever being trimmed — an O(n²) cost as the document scanned. The LF pattern (`\r\n|\r`) has no lookaround, stayed within a bounded window, and was unaffected. Reproduced directly: the old CRLF pattern took 0.35s on an 880 KB file vs. 0.15s for the fix, and raised `RegexContextLimitError` outright on a 4.4 MB file (over the 1 MiB retained-context cap) where the fix completed in 0.76s.
- Implementation: `_EOL_CONVERSIONS` in `src/uniti/regex/replace.py` now matches CRLF/CR without lookaround, using ordered alternation (`\r\n|\r|\n` for CRLF, `\r\n|\n` for CR) — since `\r\n` is tried first, a CRLF pair is always consumed as one token, so a lone `\r`/`\n` is distinguished without lookahead or lookbehind. `convert_document_eol` filters out matches already equal to the target text in code, preserving the existing "already-conforming pairs stay untouched" behavior and single-undo-step semantics.
- Verification: full local suite (1,829 tests, 6 expected skips) passed, including the existing CRLF/CR/LF conversion and untouched-pairs regression tests.

## BF-059 — Docked Find/Replace panel sizing: no default 50%, no resize-with-window

- Status: implemented, integrated on `main`.

Separately, `_make_split` never calls `QSplitter.setStretchFactor`, so both panes keep Qt's default stretch factor (1); on any resize of the containing window, `QSplitter` redistributes the size delta between panes in proportion to their current share — so the Find/Replace panel's absolute height changes on every main-window resize even though the user never touched the splitter handle.

- Implementation: `EditorPaneTree._make_split`/`split_view` (`src/uniti/ui/panes.py`) gained two new independent, opt-in parameters — `stretch` (a `(int, int)` `QSplitter.setStretchFactor` pair; when given, the ordinary `splitterMoved → _sync_sizes` proportion-tracking connection is skipped for that split, so ordinary user-created Split Right/Split Down splits are completely unaffected) and `fixed_sizes` (literal starting pixel sizes passed straight to `QSplitter.setSizes`, instead of proportions scaled against the pane tree's current — and, before its first real layout pass, unreliable — height). `FindReplaceWindow._insert_content_into_pane_tree` now calls `split_view(..., stretch=(1, 0), fixed_sizes=(1, self._attached_height))`: `fixed_sizes=(1, height)` gives the Find/Replace pane exactly `height` (any surplus/deficit lands on the editor pane, per Qt's own size-negotiation, confirmed directly — an initial proportion computed from the pane tree's current height was tried first and produced wildly wrong results, since that height is unreliable before layout, which is why the fix uses literal starting sizes instead), and `stretch=(1, 0)` (editor absorbs all of every later window-resize delta, panel absorbs none) keeps it pinned afterward. A new `FindReplaceWindow.attachedHeightChanged` signal (emitted from a dedicated `splitterMoved` connection on that one split, independent of `_sync_sizes`) fires when the user manually drags the attached splitter; `UNITIMainWindow` persists it to the new `Settings.find_replace_attached_height` field (also seeded on `FindReplaceWindow` construction in both standalone and service-owned/multi-window paths) via the existing `dataclass_replace` + `_save_settings()` pattern.
- Verification: `tests/ui/test_find_replace_contract.py` (3 tests: attach height is the remembered value rather than ~50% of the window, the attached panel's height is unchanged by a main-window resize, and manually dragging the splitter updates the remembered height for the next attach) and `tests/ui/test_panes.py`/`tests/app/test_settings.py` for the new `split_view` parameters and settings field.

## BF-061 — Format Document / Minify Document for JSON, XML, and Markdown

- Reported: 2026-09-15, on B3.
- Status: implemented, integrated on `main`. Planned in [2026-09-15-format-document-plan.md](03_implemented/milestones/2026-09-15-format-document-plan.md).
- Request: a "structure refactoring" feature for JSON/XML/Markdown documents, beyond the existing color-only syntax highlighting (BF-027/BF-041).
- Scope, confirmed with the user 2026-09-15: pretty-print ("Format Document") plus a reverse compact form ("Minify Document") for JSON and XML; Markdown gets Format Document only (no minify concept). This is text reformatting only — re-indentation, spacing, and whitespace normalization — not AST-aware structural refactors (no key sorting, tag rename, heading promotion, etc.); that would be a materially larger, separately-scoped effort if wanted later.
- Scope, confirmed with the user: validate first. JSON must parse as valid JSON and XML must be well-formed before formatting; an invalid document is refused with the parser's reported line/column, and the document is left untouched. Markdown has no strict grammar to fail against, so it always proceeds.
- Implementation: `src/uniti/core/reformatters.py` — `JSON`/`XML`/`MARKDOWN` `Reformatter`s keyed by the existing `syntax_profile.key` (BF-027/041). JSON uses the standard-library `json` module (indent 2 for format, `separators=(",", ":")` for minify; `JSONDecodeError.lineno`/`.colno` surface as the error position). XML deliberately uses `xml.dom.minidom`, not `ElementTree`, because ElementTree silently drops comments/processing instructions — a custom recursive pretty-printer indents element-only structure but leaves any element containing significant text (mixed content) completely untouched internally, since naive reformatting would inject whitespace into meaningful text (confirmed this was a real bug during implementation: `dom.toprettyxml()` alone splits mixed-content text around child elements onto separate indented lines, corrupting it); minify collapses only purely-whitespace inter-tag text. Both preserve the original XML declaration verbatim (including `encoding=`/`standalone=`) rather than minidom's regenerated bare one, and add no declaration when the source had none. Markdown gets a modest, explicitly-bounded line-based normalizer (ATX heading spacing, unordered-list bullet character, blank-line collapsing to one, trailing-whitespace/final-newline cleanup) that leaves fenced code-block content completely untouched and does not treat a leading `#!` (shebang-style) line as a heading; it is not a CommonMark parser and does not reflow paragraphs, align tables, or touch front matter.
- Wiring: `Format → Format Document` / `Format → Minify Document` (`UNITIMainWindow.format_current_document`/`minify_current_document`, `src/uniti/ui/main_window.py`), plain `QAction`s matching the existing Format-menu convention (Encoding/Line Endings are not in the command-registry/Hotkeys system either). Enabled state follows the active view's `syntax_profile.key`, refreshed on every tab/view change. Applied as one `document.replace(0, total_chars, formatted)` — one Undo step, and a no-op (no history entry) when the formatted text is already identical, consistent with `convert_document_eol`. Documents over `MAX_REFORMAT_CHARS` (16 Mi characters — formatting needs the whole document in memory, unlike UNITI's other streaming bulk edits) are declined with an explanatory dialog rather than attempted.
- Verification: `tests/core/test_reformatters.py` (20 tests: format/minify round-trips, invalid-input line/column errors, mixed-content/comment/CDATA/declaration fidelity and idempotency for XML, fenced-code and shebang preservation for Markdown) and `tests/ui/test_main_window_contract.py` (menu enablement per syntax type across tab switches, one-step Undo/Redo, the invalid-JSON error dialog leaving the document unchanged, and the size-cap rejection path). Full suite: 1858 passed, 6 platform-only skips.

- [ADR-0010](05_decisions/ADR-0010-bundled-font-selection-policy.md) records the durable policy — BF-006's font-sourcing process (pin an exact `notofonts` GitHub release, verify archive/file hashes, capture the OFL-1.1 notice, register in the schema-versioned manifest) had never been written down; it existed only as tribal knowledge encoded in `manifest.json`'s fields and `register_bundled_fonts()`'s validation logic. The ADR also flags a real, concrete code smell found while documenting it: the exact font count (`13`) is hardcoded in three separate places (`BundledFontCapability.complete`, `register_bundled_fonts`'s entry-count check, `tests/ui/test_font_policy.py`) instead of being derived from the manifest — the policy requires deriving it going forward so future additions don't need to remember all three.
- [2026-09-16-arabic-hebrew-font-bundling-plan.md](03_implemented/milestones/2026-09-16-arabic-hebrew-font-bundling-plan.md) applies that policy to the immediate need, fully sourced and verified (network access confirmed available in this pass): **Noto Naskh Arabic** from `notofonts/arabic` (tag `NotoNaskhArabic-v2.021`) and **Noto Sans Hebrew** from `notofonts/hebrew` (tag `NotoSansHebrew-v3.001`), both OFL-1.1, with exact archive/file SHA-256 hashes recorded after actually downloading and verifying both archives (not just trusting their GitHub metadata) and confirming both extracted files are valid OpenType font data.
- Naming finding worth flagging: Arabic's canonical source repository (following the exact same lowercase-generic-repo pattern used to source all 13 existing fonts) publishes "Noto Naskh Arabic," not "Noto Sans Arabic" — a separate `notofonts/NotoSansArabic` repository exists but has zero published releases, so it has no hash-pinnable archive and cannot be sourced under this project's process as written. The bundled family name will read "Naskh," a deliberate documented deviation from the "Sans `<Script>`" naming pattern the other 13 follow, not an oversight.
- Implemented 2026-09-16: both fonts and their OFL.txt notices added to `src/uniti/ui/assets/fonts/`, `manifest.json` extended to 15 entries, and `bundled_fonts.py`'s two hardcoded `13` checks replaced with a manifest-derived `BundledFontCapability.expected` field per ADR-0010. `resolve_editor_font()` confirmed to surface both "Noto Naskh Arabic" and "Noto Sans Hebrew" in its resolved family list. Fixing this also surfaced a real Arabic contextual-shaping finding (see [BF-064](#bf-064--rtlbidi-content-support-arabic--hebrew)'s font-bundling note and the plan's own "Implementation notes" section): a caret-advance test's strict per-keystroke monotonicity assumption didn't hold once real Arabic shaping was in play, and was corrected to test the actual invariant instead of weakened arbitrarily. Full suite green: 1,888 passed, 6 platform skips.
- Follow-up finding (2026-09-16, [BF-067](#bf-067--global-editor-font-weight-with-hotkeys)): both bundled fonts are static single-weight (Regular/400) instances, not the variable fonts Noto publishes upstream (confirmed: no `fvar` table in either `.otf`) — consistent with this ADR's "Regular weight only" policy, no action needed unless a future bold/italic feature is added.

## BF-067 — Global editor font weight, with hotkeys

- Reported: 2026-09-16, on B3 ("add global font weight to UNITI, incl hotkeys").
- Status: implemented and integrated on `main`.
- Request: a way to make the editor's rendered text bolder or lighter, adjustable by hotkey — the same kind of always-available, persisted preference zoom already is, but for weight instead of size.
- Architecture followed the existing zoom feature exactly, deliberately, rather than inventing a new live cross-window broadcast mechanism: font weight is per-`UNITITextView` state (`_font_weight`, one of Qt's nine named `QFont::Weight` steps — Thin 100 through Black 900), changing the *current* view and updating a `Settings.editor_font_weight` default that new/restored views pick up. This mirrors exactly how zoom and soft-wrap already behave — "global" in the sense of one persisted, always-reachable preference, not a live push to every already-open window (no existing UNITI preference does that outside the special-cased single shared Find/Replace panel instance, which isn't a generalizable pattern).
- `UNITITextView` (`text_view.py`): zoom's font-construction logic was refactored into a shared `_apply_font()` (rebuilds from the immutable `_base_font` using both `_zoom_percent` and `_font_weight` together) so setting one never silently discards the other — verified directly with a test that interleaves zoom and weight changes and confirms both survive. `set_font_weight`/`increase_font_weight`/`decrease_font_weight`/`reset_font_weight` snap to the nearest of the nine named steps (`_nearest_font_weight`, also guards against a non-standard host-reported initial weight). New `fontWeightChanged` signal mirrors `zoomChanged`.
- Persistence: `Settings.editor_font_weight` (new field, `settings.py`) as the cross-session/cross-window default, validated to one of the nine named steps. Per-view exact restoration: `ViewRecord.font_weight` (new field, `session.py`, default 400 for backward compatibility), which required bumping `SESSION_SCHEMA` to 5 (gated the same way `dock_return`/`group_id` were introduced in earlier schema bumps) — old session files without the field load with the 400 default, new saves always include it.
- Hotkeys (`shortcut_policy.py`): `editor.weight_increase` (`Ctrl+Shift+=`), `editor.weight_decrease` (`Ctrl+Shift+-`), `editor.weight_reset` (`Ctrl+Shift+0`) — same `EDITOR` scope and `Editor View` category as the zoom commands, confirmed to collide with nothing existing. Menu entries added to **View**, directly below Zoom In/Out/Reset.
- Verified directly, not assumed: a real `QTest.keySequence` hotkey-dispatch test confirms the shortcuts actually reach the focused editor through Qt's shortcut system (not just that the underlying methods work); a settings/session round-trip test; a `ViewRecord` validation test rejecting an out-of-range weight; and a rendering smoke test confirming mixed Arabic/Latin text still paints at maximum weight (900) without crashing even though the bundled Arabic/Hebrew fallback fonts are Regular-only (Qt synthesizes/fakes the heavier weight for those — accepted as-is, matching [ADR-0010](05_decisions/ADR-0010-bundled-font-selection-policy.md)'s scope; a demonstrated need for real bold Noto weights would be its own future decision under that ADR's trigger policy). Full suite green: 1,900 passed (12 new), 6 platform skips.
- Not done: no status-bar weight indicator was added (zoom has one; this was judged out of scope for the request as given — easy to add later if wanted). No attempt was made to give the bundled fallback fonts real bold faces.

## BF-068 — Detached Find/Replace panel geometry can restore off-screen after a monitor is removed

- Reported: 2026-09-17, on B3 ("investigate geometry / position of f/r pane when additional screens are removed").
- Status: implemented, integrated on `main`.
- Root cause, confirmed by reading every geometry-restore call site: the detached Find/Replace panel's saved `(x, y, width, height)` is restored verbatim via `QWidget.setGeometry` in four places — `FindReplaceWindow.detach()` (its own remembered pre-attach placement), `FindReplaceWindow.restore_state()` (session restore from a `FindReplaceRecord`), and `UNITIMainWindow.__init__`/`UNITIService.find_replace` (both restoring `Settings.find_replace_geometry` at startup). None of them checked whether that position still corresponds to any currently connected screen. If the panel was last placed on an external monitor that has since been unplugged (the most common real cause), every one of those four restores would set the window's geometry to coordinates outside every current screen — Qt does not reliably reposition a window whose explicit `setGeometry` call lands off-screen, so the panel becomes practically unreachable (no visible titlebar/handle to drag it back), with no existing code anywhere in the app checking screen geometry at all (confirmed by search — the only other `QScreen` reference in the codebase is unrelated, in `capabilities.py`).
- Fix: new `uniti.ui.screen_geometry` module — `clamp_geometry_to_screens(geometry, available_screens)` (pure, Qt-free of behavior, takes plain `(x, y, width, height)` tuples so it's testable without a real multi-monitor `QApplication`) returns the saved geometry unchanged if it overlaps *any* currently connected screen's available area (so a deliberate, still-valid placement is never "corrected" away), and otherwise recenters it (keeping its saved width/height, capped to fit) on the first available screen; `current_screen_geometries()` is the thin `QGuiApplication.screens()` adapter. `FindReplaceWindow` gained `set_detached_geometry(geometry)` (clamps, then applies, then updates the in-memory `_detached_geometry`), used at all four restore sites in place of the previous raw `setGeometry` calls.
- Scope, deliberately not touched: `UNITIMainWindow`'s own session-restored window geometry (`restore_window_record`, `self.setGeometry(*record.geometry)`) has the identical latent gap, but the report scoped this to the Find/Replace panel specifically; recorded here as a related, not-yet-fixed finding for a future pass, not silently left unmentioned.
- Verification: `tests/ui/test_screen_geometry.py` (6 tests: unchanged when overlapping one/either of several screens, recentered when the saved screen no longer exists, capped when larger than the available screen, partial-overlap still counts as reachable, and no-screen-information is a no-op) and two `tests/ui/test_find_replace_contract.py` integration tests (`detach()` and `restore_state()` each clamp a geometry saved on a now-removed screen, verified by monkeypatching `current_screen_geometries`). Full suite green.
