## Progress

**Implemented (this pass):**

- `uniti.core.bidi.is_rtl_paragraph` — Qt-free first-strong-character (UAX #9 P2/P3) direction detection, tested directly against `unicodedata.bidirectional` categories (`tests/core/test_bidi.py`).
- `ShapedWindow` (`text_layout.py`) accepts an explicit `direction` (default `LeftToRight`, preserving every existing call site's behavior); the hardcoded `LeftToRight` root cause is gone.
- `ShapedRowProvider` (wrapped mode, `shaped_wrap.py`) and `HorizontalLayouts` (non-wrapped mode, `horizontal_layout.py`) each detect a logical line's direction once, from its true start, and reuse it for every later window belonging to that line — including a window starting mid-line (a wrapped continuation row, or a horizontal-scroll checkpoint past the first 8192-char read), which would otherwise misjudge direction from a fragment that doesn't represent the whole paragraph. Both instances are already recreated on every document edit (`document.revision` is part of their construction signature in `text_view.py`), so no separate cache invalidation was needed there.
- `UNITITextView._shape` (the central per-row shaping call used for painting and hit-testing) gained the same per-line detect-once-reuse cache (`_line_directions`), with one added wrinkle: when a window doesn't start at its line's true beginning, one small bounded probe read (`document.read`, capped at 256 characters or the line's end) fetches enough of the line's actual start to detect correctly, rather than guessing from the window's own possibly-unrepresentative fragment. This cache is explicitly cleared in `refresh_document_revision` on every edit.
- Verified directly (not assumed): a pure-RTL line's logical position 0 now maps to the visual right edge and later positions map further left (the reverse of LTR) — both through `ShapedWindow` unit-level checks and through `UNITITextView._char_for_point` (real click-to-offset hit testing) in `tests/ui/test_text_view_contract.py`. A pure-LTR regression guard confirms the ordinary case is unaffected. Mid-line direction reuse (the continuation-window bug this whole design avoids) is directly tested for both `ShapedRowProvider` and `HorizontalLayouts` in `tests/ui/test_bidi_layout.py`, using an Arabic-then-Latin line long enough to force a genuinely separate second window. Painting, wrapped multi-row layout, and selection painting were smoke-tested against real Arabic/Hebrew/mixed content offscreen with no crash.
- **Caret movement (task 4, arrow keys and word movement):** `EditorState` gained `move_visual_left`/`move_visual_right`/`move_visual_word_left`/`move_visual_word_right`, each checking the cursor's logical line's direction (same paragraph-level `is_rtl_paragraph` rule, via a bounded ≤256-character probe read) and dispatching to the existing logical `move_left`/`move_right`/`move_word_left`/`move_word_right` in whichever order makes the physical key move toward the visual edge it's labeled for. `UNITITextView.keyPressEvent` (plain and Ctrl/Cmd Left/Right) and the Edit-menu Word Left/Right commands now call these instead of the unconditional logical ones. Home/End were deliberately left unchanged — they already mean "logical start/end of line," which is direction-independent (pressing Home reliably reaches wherever reading begins, matching standard bidi-editor convention), unlike Left/Right which are inherently visual-direction gestures.
- This is deliberately **paragraph-level, not bidi-embedding-level**: within an embedded run whose own direction differs from its paragraph's (e.g. an English phrase inside an Arabic sentence), arrow keys follow the paragraph's direction rather than that run's — reproduced directly and locked in as a named characterization test (`test_visual_movement_known_limitation_uses_paragraph_direction_not_local_run`) so this is a visible, deliberate scope boundary, not a silent gap. Full embedding-level-aware caret affinity (what BF-043 originally flagged as "genuinely hard") would need a real Unicode Bidi Algorithm pass computing per-character embedding levels — Python's stdlib only exposes raw `unicodedata.bidirectional` categories, not resolved levels, so that would mean either a hand-rolled UAX #9 implementation or a new third-party dependency, either a materially larger, separately-scoped effort.
- Verified directly (not assumed): both the `EditorState` unit level and a real `UNITITextView` with actual Qt key events (`QTest.keyClick`) confirm Right/Left arrows move toward their visually-labeled edge on an RTL line, and are unaffected on an ordinary LTR line.
- **Selection/match/invalid-byte highlight rects (the rest of task 4):** found and fixed a real bug, not merely a theoretical gap — `shaped.x_for_cp` is monotonically *increasing* with logical position on an LTR line but monotonically *decreasing* on an RTL one, and the three highlight-painting call sites (selection, search-match, invalid-byte-annotation rects in `text_view.py`) all assumed the LTR ordering, computing `width = x2 - x1` directly. On an RTL line this went negative and got clamped to a 1-pixel-wide rect sitting at the *wrong* edge of the actual span — reproduced directly (selecting an entire 7-character Arabic line painted a 0px-wide highlight before the fix). Fixed with a new `UNITITextView._span_rect(x1, x2, y, height)` helper that takes `min`/`max` of the two coordinates, used at all three call sites. Considered but did not switch to Qt's `QTextLayout.FormatRange` background-color painting (which I confirmed via direct pixel-level testing *does* correctly split into multiple rects at a bidi run boundary) — this is now a well-defined, deliberately deferred trade-off rather than "not investigated": it would trade the current unified multi-script row-height background for the text's own natural ascent/descent height, and doesn't obviously agree with painting the same full-row selection band the rest of the row (gutter, whitespace markers) already assumes.
- Full suite: 1888 passed, 6 platform-only skips — no regression to existing (LTR) behavior.

**Found and fixed 2026-09-16 — typing/composing into a right-to-left line froze the caret:**

Reproduced directly: typing five Arabic characters one at a time into an empty line left `_cursor_rectangle().x()` at the *exact same pixel* after every keystroke, in both wrapped and non-wrapped mode. Root cause: Qt's `QTextLine` anchors flush-*left* within its declared line width by default, regardless of paragraph direction — `setTextDirection` only reorders glyphs inside that box, it doesn't move the box's anchor. For a right-to-left line that keeps growing at its logical end (ordinary typing or IME composition), the box's left edge stays fixed and it just widens rightward — so the caret, which sits at the logical end, never visually moves; each new character just extends empty space between the caret and the newly-typed glyphs. This affected *all* RTL typing and IME composition, not merely a positioning nicety.

Fix: `ShapedWindow` gained a new `align_width_px` parameter — when the direction is right-to-left and either `width_px` (an active wrap width) or `align_width_px` (a supplied reference width with no wrapping) is available, `QTextOption.setAlignment(Qt.AlignmentFlag.AlignRight)` anchors the box to the *right* edge of that width instead, so it grows *leftward* as expected. `UNITITextView._shape` (the shared painting/hit-testing/caret entry point) now always supplies `align_width_px=self._wrap_width()` (the available text-area width) — harmless for LTR text, and included in `_shape`'s cache key since it depends on viewport width. Verified directly with `QTest`-free but real `EditorState.insert_text` typing loops, in both wrapped and non-wrapped mode, that the caret now strictly advances one direction per character (`test_typing_into_an_rtl_line_advances_the_caret_visually`), confirmed to fail against the pre-fix code before being accepted; an LTR regression guard confirms the ordinary case is unchanged. This also fixed the two IME preedit-position tests added for the RTL document scenario, which had failed with the same frozen-caret symptom before this fix and were not weakened to pass around it.

One existing hit-testing test's specific pixel expectations became stale after this fix (the row's geometry genuinely changed — RTL content now anchors to the right edge of the *available text area* rather than sitting in a narrow left-anchored box) and was updated to click at the row's new true right edge rather than an arbitrary point that used to be far past a narrow block.

**Found and fixed 2026-09-16 — full multi-rect selection splitting at an embedded run boundary:**

Previously deferred as "overcovers rather than splits." Fixed by adding `ShapedWindow.run_spans(a, b)` (`text_layout.py`), which calls Qt's own `QTextLine.glyphRuns(start_unit, length_unit)` — the same shaping/bidi-reordering engine already trusted for painting — to get one geometrically exact `(left, right)` extent per bidi/shaping run within the span, instead of hand-deriving run boundaries from `x_for_cp` monotonicity (which real testing showed does not hold in general — see the code comment history for why a naive sign-reversal-detection approach was rejected). `UNITITextView._span_rects` builds one rect per run (keeping the editor's uniform row height, not each run's own natural ascent/descent — the same trade-off that blocked adopting `FormatRange` background painting directly is avoided this way), used at all three existing highlight call sites (selection, search-match; the single-character invalid-byte-annotation call site is unaffected since one code point can never cross a run boundary). Verified directly: a span selecting "B" + the first two letters of an embedded Arabic word, inside an LTR paragraph, previously (confirmed by computing what the old single-bounding-box code would have produced) painted over the *unselected* remaining Arabic letters too; the fix's `run_spans`-based rects correctly exclude that unselected remainder. Confirmed to fail against the pre-fix single-box logic before being accepted. Full suite green afterward.

**Found and fixed 2026-09-16 — embedding-level caret affinity:**

Previously the single biggest open design risk (BF-043's original "genuinely hard" concern), deferred because Python's stdlib exposes only raw `unicodedata.bidirectional` categories, not resolved per-character embedding levels, and a hand-rolled UAX #9 pass or new dependency both looked like materially larger efforts. The actual fix needed neither: `UNITITextView._move_visual_char` shapes the cursor's whole logical line once (bounded to `ShapedWindow`'s existing 8192-code-point cap) and reads the *real* pixel x-coordinate of the cursor and its two grapheme-cluster neighbors via `ShapedWindow.x_for_cp` — the same authoritative Qt-computed geometry already used for painting — then moves to whichever neighbor actually sits in the requested visual direction. This is correct for arbitrary embedding depth within one line, since it never needs to reason about bidi levels directly; Qt's own shaping already encodes them in the pixel positions. `EditorState.move_visual_left/right` (paragraph-only, Qt-free by design) remains as the deliberate fallback in two bounded cases: at a line's own start/end (no in-line neighbor to compare against — crossing into a different paragraph is out of scope here, and the existing fallback already does this correctly) and for a line too long to shape within the 8192-code-point cap. Verified directly with a real `QTest.keyClick` Right-arrow press inside an embedded English "hello" within an Arabic paragraph, moving forward (matching the local run) instead of backward (matching only the paragraph) — confirmed to fail against the pre-fix paragraph-only dispatch before being accepted. The `EditorState`-level characterization test (`test_visual_movement_known_limitation_uses_paragraph_direction_not_local_run`) still passes and was reworded to clarify it now documents only the Qt-free fallback's own remaining behavior, not the real editing path.

**Not yet done — do not assume this works:**

- **The non-wrapped/horizontal-scroll path's deeper multi-checkpoint case.** The caret-freeze fix above (`align_width_px`) does fix typing/caret-advance for a non-wrapped RTL line that still fits within the viewport or within one 8192-char checkpoint — confirmed directly, both modes gave identical, correctly-advancing caret positions for a short line. What remains broken: a line long enough to need horizontal *scrolling* (multiple checkpoints) — reconfirmed directly on 2026-09-16 with a 12,000-character Arabic line: navigating to position 9000 (past the first 8192-char checkpoint) produces a caret rectangle at x≈39375, growing further *right* the deeper the cursor goes into the RTL line, when it should move further *left* off a right anchor. Investigated properly before deferring again, not just re-stated: `HorizontalLayouts`'s progressive checkpoint model accumulates `offset` as a pixel distance growing rightward from x=0 as more of the line is read — sound for LTR, where reading order and visual order agree, but wrong for RTL, where later logical content sits further left. A correct fix cannot simply flip the accumulation's sign, because the natural RTL layout is right-*anchored* (later content grows leftward from the line's total width), and the whole point of progressive checkpoints is to avoid ever computing an arbitrarily long line's total width up front. A real fix needs a different strategy — most plausibly a mirrored coordinate space specifically for RTL lines, with matching inversions everywhere `offset` currently feeds painting, hit-testing, the cursor rectangle, and the scrollbar range/value mapping (multiple call sites in `text_view.py`, all currently tuned and tested only for the LTR case). That is a real, separately-scoped architecture change, not a bounded patch, and was not attempted here — pushing an under-verified change through this shared, heavily-exercised pixel/scroll path (offscreen-only in this environment, with no way to visually confirm rendering) risked a worse regression than the documented, narrow gap it would replace.
- IME composition for Arabic/Hebrew keyboards (task 6): synthetic commit/cancel/preedit-position coverage was added (`tests/ui/test_multilingual_text.py`, mirroring BF-006's own synthetic IME methodology exactly), and benefits from the caret-freeze fix above. Physical native Arabic/Hebrew keyboard qualification remains untouched and cannot be done without native hardware.
- No native/physical qualification of any kind has been done — everything above is offscreen/synthetic verification only.

## Scope (confirmed with the user)

- **Content-level bidi only.** Arabic/Hebrew (and mixed RTL+LTR) text renders and edits correctly *inside* the editor: correct visual ordering, caret movement, and selection. The application's own chrome — menus, dialogs, the gutter, the scrollbar — stays left-to-right, unchanged. This matches how most code/text editors handle RTL content (VS Code, etc.) rather than offering a fully mirrored RTL UI, which would be a materially larger, differently-shaped effort (touching nearly every widget, not just the text engine) and is explicitly out of scope here.
- **Target scripts: Arabic and Hebrew**, verified to the same rigor BF-006 used for its LTR script expansion (representative glyph/shaping/editing/rendering tests per script, physical native confirmation tracked separately as its own open item, synthetic tests do not substitute for it).
- Everything below is *content* work. It does not reopen [ADR-0006](../05_decisions/ADR-0006-executable-health-recovery-boundary.md) or any other architectural boundary.

## Why this is tractable: the encouraging finding (BF-043)

The document core (`Document`, the piece table) already stores text as plain logical Unicode code points — never visual/display order. Nothing in the storage, search, replace, or history layers has any LTR assumption baked in. Bidi reordering is therefore a **presentation-layer concern**, confined to the shaping/layout/painting code in `src/uniti/ui/` — not a core-engine rewrite. This was already identified as an architecture finding (BF-043) before any RTL work was requested.

## Root cause of today's LTR-only rendering, confirmed directly

`ShapedWindow.__init__` (`src/uniti/ui/text_layout.py:66`) hardcodes:

```python
option.setTextDirection(Qt.LayoutDirection.LeftToRight)
```

Reproduced directly with a real `QTextLayout` (offscreen Qt): for a mixed Arabic+English string (`"مرحبا hello"`), forcing `LeftToRight` places the English run to the *right* of the Arabic word and anchors the paragraph's visual start at the left edge — backwards for an RTL reader's expectation. Switching to `Qt.LayoutDirection.LayoutDirectionAuto` (Unicode's first-strong-character paragraph-direction rule, built into Qt) instead anchors the paragraph correctly at the right edge, with the embedded English run correctly placed to the left of the Arabic text. Qt's text engine already performs full Unicode Bidi Algorithm reordering and correct glyph shaping (including Arabic contextual joining forms) regardless of this setting — `setTextDirection` controls the *paragraph base direction* used to resolve neutral characters and overall run placement, and today it is wrong for any RTL-based line.

This means the *shaping* half of the problem is close to a one-line fix at its core — detect each logical line's base direction and pass it through instead of a hardcoded constant. The genuinely hard parts are everywhere direction is *assumed* elsewhere in the surrounding layout/navigation/painting code, enumerated below.

## Task breakdown

### 1. Per-line direction detection

Add a `paragraph_direction(text) -> Qt.LayoutDirection` helper (Unicode P2/P3 first-strong-character rule — or simply delegate to `Qt.LayoutDirection.LayoutDirectionAuto` directly per line, letting Qt do the detection, if empirically it matches expectations across mixed content; needs a decision once implementation starts). Applied per **logical line**, not per arbitrary shaped window, since direction is a paragraph-level property — a window that starts mid-line must reuse its line's already-detected direction rather than re-detecting from a truncated fragment.

### 2. Wrapped mode (`shaped_wrap.py`) — the primary target

`ShapedRowProvider.__call__` already reads and shapes one logical line's window at a time (`line, column` keyed), which is naturally compatible with per-line direction: detect the line's direction once, thread it into `ShapedWindow`, and each wrapped visual row inherits it. This is the tractable, primary-target path — most editing happens with soft wrap on.

Still needs verification, not assumed: does a *wrapped* RTL row render right-aligned within the viewport (the expected behavior) once `ShapedWindow` gets the correct direction, or does something in the row-painting code (`text_view.py`) assume rows start flush-left? This needs a real check against the paint path, not just the layout math.

### 3. Non-wrapped / horizontal-scroll mode (`horizontal_layout.py`) — the harder path

`HorizontalLayouts.window` accumulates pixel checkpoints monotonically left-to-right as it reads further into a line (`offset + shaped.width`), fundamentally assuming forward-reading-order means rightward-visual-advance. For an RTL line, advancing further in logical/reading order means visually *leftward*. This checkpoint/caching model does not generalize to RTL without real rework — a naive fix is not available here the way it is for the wrapped path.

Two options, to decide before implementation:
- **(a) Full fix:** a parallel RTL-aware checkpoint accumulation (reversed offset direction, right-anchored). More work, but no behavioral gap.
- **(b) Scoped interim:** RTL logical lines are always soft-wrapped regardless of the document's wrap setting (a documented, narrower limitation) until (a) is done. Meaningfully smaller scope for a first cut, at the cost of an inconsistency to disclose clearly rather than hide.

### 4. Caret movement and selection (the genuinely hard part BF-043 already flagged)

Arrow-key navigation currently maps "left" to "previous logical position" and "right" to "next logical position" — correct for LTR, backwards for RTL (in an RTL line, the Right arrow should move toward the start of reading order, i.e. logically *backward*). This needs direction-aware mapping in the navigation code (`UNITITextView`'s move-left/move-right/word-movement handlers), and gets materially harder exactly at LTR/RTL boundaries within one line (a caret sitting between an RTL run and an embedded LTR run has two visually-plausible logical positions — this is the "caret affinity" problem BF-043 called out as "still genuinely hard," and is the single biggest open design risk in this plan). `QTextLine` exposes `cursorToX`/`xToCursor` (already used by `ShapedWindow`) which can anchor this, but the *policy* (which logical position a given visual click or arrow-key press resolves to at a direction boundary) needs real design and cannot be waved through as "Qt handles it."

Selection painting needs the same scrutiny: a single logical selection range that crosses a direction boundary may need to render as more than one visual rectangle per row (standard bidi-editor behavior) rather than one contiguous rect — needs a check against how `text_view.py` currently paints selection/match highlight rectangles.

### 5. Whitespace/EOL markers and gutter interaction

Whitespace markers (BF-003) and EOL markers are positioned via the same `x_for_cp` mapping `ShapedWindow` already provides, so they should follow correctly once direction is threaded through — but this needs a real check, not an assumption, particularly for markers at the visual start/end of an RTL line (which is the *right* edge, not the left). The gutter itself (line numbers) stays on the left per the confirmed content-only scope — it does not move for RTL lines.

### 6. IME/composition

BF-006 built a bounded virtual preedit projection (temporary row panning, synthetic commit/cancel events) for CJK IME. Arabic/Hebrew IME composition would reuse that same infrastructure, but the preedit caret positioning inside it needs to be direction-aware too — same underlying risk as item 4, scoped to the preedit-specific code path.

### 7. Fonts

No Arabic or Hebrew font is bundled today (confirmed: the 13 bundled Noto faces cover Han/Korean/Latin-Cyrillic/nine Indic scripts only, no Arabic/Hebrew). This needs adding pinned Noto faces for both scripts (Noto Naskh Arabic or Noto Sans Arabic, and Noto Sans Hebrew — pick to match the existing "official Noto" sourcing convention), through the same bundling pipeline as BF-006: pinned upstream commit, exact font/notice hashes recorded in the manifest, license and sample, counted honestly by `register_bundled_fonts()` rather than assumed present.

## Testing plan

Mirror BF-006's rigor:

- Representative glyph/shaping/editing/rendering tests for both scripts: pure-RTL lines, mixed RTL+LTR lines (embedded English/numbers inside Arabic/Hebrew text — numerals in particular need checking, since Arabic-Indic vs. European digit shaping is a real, separate concern from bidi direction), caret movement across a direction boundary, selection spanning a direction boundary, wrapped-row rendering, and (once scoped) the horizontal-scroll path.
- The existing multilingual interaction-latency benchmark (`benchmarks/multilingual.py`) gets Arabic/Hebrew scenarios added, checked against its existing thresholds rather than new ones.

## Open items before implementation starts

- Item 3's decision: full RTL-aware horizontal-scroll rework vs. the scoped interim (force-wrap RTL lines) for the first cut.
- Item 4's caret-affinity policy at direction boundaries — the single biggest design risk in this plan; needs a concrete proposal reviewed before coding, not resolved inline during implementation.
- Exact Arabic/Hebrew font faces to bundle and their licensing notices.
