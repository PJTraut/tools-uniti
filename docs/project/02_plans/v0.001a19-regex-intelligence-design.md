# UNITI v0.001a19 Regex Intelligence Alpha Design

Date: 2026-09-02
Status: proposed design awaiting written review
Milestone: [`v0.001a19` — Regex Intelligence Alpha](v0.001a19-regex-intelligence-alpha.md)

## Goal

Make regex authoring, diagnosis, navigation, capture inspection, and replacement a defining UNITI capability without weakening the bounded large-file, text-integrity, or document-authority guarantees established through a18.

a19 turns the existing regex lexer, highlighter, search, capture report, and replacement paths into one coherent intelligence system. The pinned third-party `regex==2026.5.9` package remains the sole authority for compilation, matching, capture numbering, duplicate-name behavior, branch-reset behavior, repeated captures, and replacement expansion.

## Existing baseline and design gap

UNITI already has substantial regex foundations:

- raw Regex mode and separately escaped Literal mode;
- a lightweight pattern/replacement lexer and Qt syntax highlighters;
- third-party-engine compilation, bounded-window search, timeouts, and cancellation;
- compact revision-bound `MatchStore` results with spill-to-disk behavior;
- visible-only editor match overlays, including narrow zero-width markers;
- named and repeated capture offsets;
- a capture-only report for the current and adjacent match;
- snapshot-based asynchronous Find All and replacement planning;
- stale-result invalidation after edits or pattern changes; and
- one-transaction Replace All through the authoritative `Document`.

The current pieces do not yet form a dependable intelligence contract. Group delimiters and references do not share per-group color identity. The handwritten lexer approximates some engine numbering rules without a general reconciliation result. Compile failures are flattened into one status string. Capture detail resolution can execute synchronously on the GUI thread and can read more text than a report should own. Zero-width matching works in core tests, but navigation, wrapping, rendering, single replacement, and bulk replacement do not yet share an explicit end-to-end contract.

## Design principles

1. The third-party engine decides semantics; UNITI only analyzes, bounds, schedules, and presents them.
2. Lexical presentation may be partial, but it must never claim semantic certainty that disagrees with a successful engine compilation.
3. A group number is the stable identity shared by its opening delimiter, closing delimiter, name, pattern backreference, replacement reference, and Match Report row.
4. Color supplements explicit numbers and names; color is never the only carrier of meaning.
5. Live authoring remains responsive. Potentially expensive compilation and capture resolution do not run on the GUI thread.
6. Search and replacement continue to consume immutable snapshots and publish only against the captured pattern generation, document identity, and revision.
7. Match Reports remain navigation-focused and bounded. They do not expand into an all-results table or one GUI object per search match.
8. Zero-width matches are first-class results with deterministic cursor, navigation, rendering, and replacement behavior.
9. Replace All remains one atomic document transaction and one Undo operation.
10. Existing a17 text-integrity and a18 resource/performance gates remain mandatory.

## Scope

a19 includes:

- a Qt-free semantic analysis result for pattern and replacement expressions;
- engine-validated capture numbering and stable group/color identity;
- recognition and presentation of global and scoped inline switches;
- named, numbered, duplicate-named, branch-reset, repeated-capture, and backreference behavior covered by pinned-engine fixtures;
- live structured compile diagnostics with an exact source location when the engine supplies one;
- pattern and replacement highlighting that shares group identities and marks invalid references;
- bounded asynchronous capture resolution and a clearer capture-only Match Report;
- explicit zero-width Find All, Next, Previous, Replace, Replace All, wrapping, and rendering rules;
- resource admission, cancellation, progress, and generation/revision-based stale-result rejection for regex work; and
- focused correctness, UI, large-result, and performance acceptance evidence.

## Outside a19

a19 does not add an alternative regex engine, a general-purpose parser API, document-language syntax highlighting, file-type profiles, an all-matches report grid, replacement preview/diff, project/workspace behavior, or a new preferences surface. Replacement preview remains excluded because current evidence does not justify the additional state and UI. Editor whitespace visualization and expanded keyboard-driven Unicode inspection remain separate future editor-display work rather than entering the regex milestone implicitly.

## Approaches considered

### Selected: lightweight structural analysis reconciled with engine metadata

UNITI extends its existing linear lexer into a typed analysis layer, compiles with the pinned engine, and reconciles presentation metadata with `groups`, `groupindex`, flags, and compiler diagnostics. Supported structural forms receive precise identities. Unknown or unsupported forms remain neutral rather than being assigned speculative semantics.

This preserves responsive highlighting and source spans while keeping successful engine compilation authoritative. If structural metadata cannot be reconciled with the compiled result, matching may still proceed through the engine, but uncertain group-color metadata is withheld and a non-blocking presentation diagnostic explains the limitation.

### Rejected: derive the UI entirely from compiler output

The compiled pattern exposes authoritative aggregate metadata but not a complete source-span map for every delimiter, inline switch, and reference. Compiler output alone cannot drive precise source highlighting or paired delimiters.

### Rejected: implement a complete independent regex parser

A second full parser would duplicate the pinned package's evolving grammar and could disagree about capture identity or accepted syntax. That conflicts with ADR-0003 and would create a maintenance surface disproportionate to the milestone.

## Architecture

The regex intelligence path is split into five responsibilities:

```text
Find/Replace expression generation
              |
              v
     Qt-free lexical analysis
              |
              v
    pinned-engine compilation ------> structured diagnostic
              |
              v
 engine-reconciled RegexAnalysis
       |                    |
       v                    v
input highlighting     search/replace request
                            |
                            v
                 snapshot + TaskCoordinator
                            |
             +--------------+--------------+
             |                             |
             v                             v
       bounded MatchStore          ReplacementPlan
             |
             v
 current/adjacent capture-resolution task
             |
             v
  bounded CaptureReport -> Qt list model
```

Qt-free code owns syntax spans, diagnostics, capture identity, report records, search semantics, and replacement semantics. Qt code owns debounce timing, colors, focus, widgets, and delivery of immutable results on the GUI thread. The `Document` remains the only text and history authority.

### File responsibility map

- `src/uniti/regex/analysis.py`: immutable analysis, diagnostic, flag-scope, and group-identity records; reconciliation with pinned-engine compilation.
- `src/uniti/regex/lexer.py`: linear structural tokenization and compatibility entry points; no Qt and no alternative matching semantics.
- `src/uniti/regex/captures.py`: bounded capture-report records and resolution for one requested match against a snapshot.
- `src/uniti/regex/engine.py`: pinned-engine compilation entry point and normalized compiler-error extraction.
- `src/uniti/regex/search.py`: bounded match iteration and explicit zero-width progress contract.
- `src/uniti/regex/results.py` and `src/uniti/regex/match_store.py`: compact match navigation and zero-width lookup behavior.
- `src/uniti/ui/regex_input.py`: palette-aware rendering of immutable analysis tokens and diagnostic spans.
- `src/uniti/ui/capture_report.py`: model-backed capture-only presentation with no per-search-match widgets.
- `src/uniti/ui/find_replace.py`: expression generations, debounce, task orchestration, navigation, and result publication; semantic logic delegates to Qt-free modules.
- `src/uniti/ui/text_view.py`: visible-only normal and zero-width match rendering.

The implementation may retain a responsibility in its present file where a split would add indirection without clarifying ownership. It must not add unrelated refactoring.

## Analysis contract

`RegexAnalysis` is an immutable result for one exact expression and monotonically increasing UI generation. It contains ordered tokens, paired delimiter information, group identities, inline-switch records, one of `PENDING | VALID | INVALID | OVER_LIMIT`, and zero or more structured diagnostics. A pending result may drive lexical colors but never enables search or replacement.

Each pattern token records a kind, half-open source span, validity, optional group number/name, optional paired-token identity, and optional color identity. Each replacement token records the same source information plus its referenced group identity when valid. Capture group number is the canonical color key. Duplicate named groups and branch-reset alternatives that resolve to the same engine group number therefore receive the same color. Palette colors cycle when groups exceed the available accessible palette, while displayed number/name labels preserve unambiguous identity.

The structural analyzer recognizes at least:

- escaped literals and Unicode properties;
- character classes and their escapes;
- anchors, alternation, quantifiers, and lazy/possessive suffixes;
- capturing, noncapturing, atomic, lookaround, conditional, and branch-reset groups;
- Python-style and angle-bracket named captures supported by the pinned engine;
- global and scoped inline switches, including removals;
- numbered and named pattern backreferences; and
- numbered and named replacement references.

Successful compilation supplies the authoritative total group count, name-to-number mapping, and effective flags. UNITI compares those facts with the structural result before publishing semantic group identities. If capture count or name mapping disagrees, the complete analysis remains valid for engine execution but all uncertain group identities and reference colors are suppressed together; UNITI never publishes a partly contradictory numbering map. Scoped-switch tokens are presentation spans accepted by successful engine compilation, not an independent statement about match execution. Constructs not needed for the approved authoring surface may receive neutral structural highlighting while still compiling and matching correctly.

Interactive analysis is limited to 65,536 Unicode code points per expression. Longer expressions remain editable but compilation/search is refused with a precise limit diagnostic until shortened. This bounds retained analysis copies, token counts, and compiler work submitted by the UI.

## Compilation and diagnostics

Pattern edits advance a pattern generation immediately, cancel or invalidate result/report work, and apply cheap structural highlighting. After a 150 ms quiet interval, the UI submits engine compilation through the shared task coordinator at interactive priority. Only a result whose generation and exact pattern text still match the fields may publish.

An engine error becomes a `RegexDiagnostic` containing severity, safe message, and a half-open source span derived from the engine's `pos`, `lineno`, and `colno` attributes when available. End-of-input errors use a visible caret marker at the final position. The status surface shows a concise message such as `missing ) at column 5`; the highlighter marks the corresponding span; accessible text contains the same message without relying on color.

Structural warnings never override successful compilation. Invalid compilation disables Find, Replace, and Replace All for that generation. A pending compilation displays `checking pattern…`; an empty pattern displays `enter a pattern`. Literal mode retains its current escaping and Case Sensitive/Whole Word semantics and does not present escaped implementation syntax as user-authored regex.

Replacement analysis consumes the current successful pattern analysis. References to absent numeric or named groups are marked invalid before replacement starts. Actual expansion still uses `regex.Match.expand`; the lexer does not invent replacement semantics.

## Highlighting and group identity

Pattern and replacement inputs render from the latest immutable analysis rather than independently tokenizing with different context. Capturing group open/close delimiters, the name inside a named capture, and every valid reference share the group's palette slot. Noncapturing structures use a neutral structural style. Inline switches have a distinct style, with scoped-switch delimiters paired like other groups.

The palette provides at least eight distinguishable group colors with acceptable contrast against the active field background. A palette or theme change rebuilds formats and rehighlights. Invalid syntax uses a wave underline plus diagnostic text; it is not identified by red color alone. Selection, input-method composition, cursor visibility, and the independent 50-step field histories remain intact.

## Search, navigation, and zero-width semantics

Search continues to use non-overlapping `regex.finditer` semantics through bounded virtual-document windows. a19 makes these rules explicit:

1. Every engine-emitted match is stored once, including matches whose `start == end`.
2. Match ordering is `(start, end)` in engine emission order for identical spans.
3. Find All may include zero-width matches at document start, between characters, at line boundaries, and at document end.
4. Next and Previous operate by result index after Find All. They always advance to a different stored result when more than one exists, even when consecutive results share a character position.
5. A single-result search may wrap to itself and reports `match 1/1`; it does not launch a second search merely because its selection length is zero.
6. Navigating to a zero-width match places the caret at its position without fabricating a document selection.
7. The viewport paints a visible caret-like match marker with a minimum device-independent width. Start-of-line, end-of-line, wrapped-row, and document-end markers remain visible without changing layout.
8. Single Replace applies the engine-expanded insertion/deletion once to the selected result, clears the stale result set, and positions the caret after inserted text.
9. Replace All plans every engine-emitted zero-width replacement once against the captured revision. Application remains monotonic, atomic, and one Undo operation.

Partial-window retention and duplicate suppression receive focused tests at chunk boundaries so a zero-width result cannot be lost or emitted twice when a search buffer advances.

## Match Report

The Match Report remains capture-only: group `0` is never displayed. It presents the current match followed by the immediate next match, wrapping at the end, with a delimiter and an explicit `Match n of N` heading. A one-match result appears once rather than being duplicated as its own neighbor.

Each group row shows authoritative number, optional name, participation state, bounded value preview, and occurrence information. The report distinguishes:

- unmatched group: `not matched`;
- participating empty capture: `empty at <position>`;
- one non-empty capture: escaped/truncated value;
- repeated capture: first five escaped/truncated values plus the total occurrence count; and
- unavailable detail: a safe reason such as an over-limit match or stale revision.

Capture resolution never runs synchronously from navigation painting or a button handler. Navigation immediately updates the editor and publishes a lightweight `loading captures…` report. A capture-resolution task reads an immutable snapshot around the requested match, checks cancellation between groups, and returns an immutable report sealed to pattern generation, document identity, revision, result-store identity, and match index.

A report resolves only when the complete match plus required context fits within 65,536 characters. It retains at most five value previews of at most 80 characters per group and no more than 1 MiB of report payload. If the complete capture report cannot fit, UNITI publishes one explicit unavailable-detail record for that match rather than a partial group list that could be mistaken for complete output. The match span and navigation behavior remain valid. Transient engine capture lists are processed one group at a time and not retained wholesale.

The Qt report uses a model-backed list rather than constructing widgets for search matches. Cancelling report work, navigating again, editing, changing mode/pattern, closing the target document, or replacing text invalidates the old generation. Stale completion closes owned snapshots and publishes nothing.

## Asynchronous task and resource behavior

The task system gains a regex-analysis kind at interactive priority and a capture-report kind at visible priority, or equivalent explicit priorities if extending `TaskKind` would not clarify diagnostics. Find All remains a foreground search task; replacement planning remains a foreground replacement task.

Each Find/Replace window owns one logical compile-analysis slot and one capture-report slot. A running third-party engine call may finish after cancellation because the call itself is not interruptible; no second call for that slot starts until it returns. The slot retains only the newest pending generation and starts that generation next, so rapid typing cannot create an unbounded queue. Generation seals prevent every superseded completion from publishing. The debounce interval avoids submitting work for ordinary intermediate keystrokes.

Task notifications crossing from worker threads into Qt are edge-triggered wake-ups, not authoritative state payloads. On each wake-up, the GUI thread reads the coordinator's latest snapshot and ignores any delivery generation older than the last applied generation. This prevents a queued snapshot emitted on the GUI thread before dispatch from arriving after newer worker-thread progress and clearing it. The rule applies to existing Save/EOL/navigation status as well as new a19 regex tasks.

Search and replacement use the a18 snapshot, progress, resource-admission, memory, and temporary-disk rules. Capture report failure does not destroy valid match navigation. Search failure does not alter the document. Replacement expansion failure does not apply a partial plan. All temporary stores, plans, and snapshots close on success, failure, cancellation, staleness, or window shutdown.

## Error and status behavior

The Find/Replace surface distinguishes these states without modal dialogs:

- empty expression;
- checking pattern;
- valid pattern with group count;
- compiler diagnostic with location;
- invalid replacement reference;
- searching/replacing with progress;
- cancelled operation;
- timeout or bounded-context refusal;
- stale result after text change;
- valid match count and navigation index; and
- capture details unavailable within the report bound.

User-authored patterns and replacement strings are never copied into lifecycle logs. Diagnostics may record error class, safe message, position, lengths, counts, duration, cancellation, and resource state.

## Verification strategy

Qt-free tests cover:

- every supported token class and malformed boundary;
- global/scoped inline switches and removals;
- ordinary, named, duplicate-named, branch-reset, conditional, and repeated groups;
- engine-reconciled group numbering and stable color identity;
- valid/invalid pattern and replacement references;
- structured compiler positions, including end-of-input errors;
- expression-length refusal;
- zero-width matches at document, line, and chunk boundaries without duplicates;
- next/previous behavior for equal-position and single zero-width results;
- bounded capture summaries for unmatched, empty, repeated, huge, and stale matches;
- cancellation and closure of snapshots, stores, and plans;
- deliberately reordered cross-thread task notifications, proving the GUI applies only the latest coordinator state; and
- atomic zero-width Replace All with one Undo step.

Offscreen Qt tests cover debounce/generation behavior, palette-aware group pairing, diagnostic underlines and accessible text, action enablement, capture loading/publication, rapid-navigation cancellation, zero-width rendering, Literal/Regex separation, and shutdown cleanup. Native macOS smoke confirms focus, typing, colors, navigation, report readability, cancellation, and zero-width markers on the real platform plugin.

The existing a18 performance suite remains authoritative. a19 acceptance reruns the quick suite and the controlled routine search/replace scenarios. Dense results must stay inside `MatchStore` and replacement-plan bounds; interactive highlighting/navigation must remain inside the packaged interaction gates; no selected compatible baseline may regress to `FAIL`.

## Milestone acceptance

a19 freezes only when:

1. `regex==2026.5.9` remains the only semantic engine and its advanced-fixture matrix passes;
2. pattern and replacement fields expose paired, engine-validated group identity and precise safe diagnostics;
3. named, duplicate-named, branch-reset, repeated, unmatched, and empty capture behavior is correct;
4. Match Report resolution is asynchronous, bounded, cancellable, and stale-safe;
5. zero-width Find All, Next, Previous, Replace, Replace All, wrapping, and rendering pass end to end;
6. Replace All remains one atomic Undo operation and every a17 text-integrity rule passes;
7. task status delivery cannot regress from newer progress to an older queued/empty snapshot under concurrent GUI and worker notifications;
8. dense-result search, cancellation, memory, and responsiveness remain within the a18 policy gates;
9. the complete ordinary suite, deep self-check, offscreen combined smoke, native macOS smoke, quick performance suite, and controlled routine regex scenarios pass with fresh evidence; and
10. no known regex correctness, infinite-navigation, GUI-freeze, stale-publication, partial-replacement, data-loss, or text-integrity defect remains.
