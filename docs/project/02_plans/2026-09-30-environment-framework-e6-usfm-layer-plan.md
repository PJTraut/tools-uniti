# Isolated File-Type Environments — Phase E6 (USFM Layer) Plan

Date: 2026-09-30
Status: **Implemented.** Its "later phases" list (project `.sty` loading, the marker/style inspector, E7+ rich views) was implemented 2026-10-02; see [ADR-0015](../05_decisions/ADR-0015-stylesheet-layers-and-rich-views.md). OccursUnder-driven validation is still left to `usfmtc`.
Origin: [E1–E4 plan](2026-09-29-environment-framework-e1-e4-plan.md) / [ADR-0013](../05_decisions/ADR-0013-environment-framework-ownership-boundary.md) deferred SFM/STY design past E4; [E5 plan](2026-09-29-environment-framework-e5-sfm-foundation-plan.md) shipped generic SFM and deferred everything USFM-specific to this phase — Phase E6 of the external handover spec's own phase numbering (`@externalresources/UNITI_Claude_Code_Environment_Handover_Spec.md` §74).

## Scope

**In scope:** the spec's Phase E6 bullets — the official baseline `usfm.sty`, USFM detection/profile (as a distinct `Environment` from generic SFM), chapter/verse navigation, USFM-specific validation, and a `usfmtc` reference-conformance adapter.

**Explicitly out of scope (later phases):** loading a project's *own* `.sty` at runtime (discovery/precedence — `StyleRegistry.from_layers` already supports layering mechanically, nothing wires it into activation yet), a marker/style inspector UI (no UI consumer exists for `EnvironmentFinding`/structural queries yet — same deferral E3–E5 already established), OccursUnder-driven structural/nesting validation (left to `usfmtc`'s grammar, see decision 5), and the rich-view/source-map framework (E7+).

## Design decisions made while implementing

1. **`usfm.sty` is vendored, pinned, and hash-verified — not fetched at runtime.** The spec is explicit that reference resources must not be fetched from the Internet during normal editing (§85). Vendored from `github.com/ubsicap/usfm@69838c870133bb0c9f7b42f741053c08cd7b29e0` (`sty/usfm.sty`, declared `Version=3.0.11`) into `core/environments/sfm/assets/usfm.sty`, with provenance and a sha256 in `assets/manifest.json`, loaded and verified the same way `ui/bundled_fonts.py` verifies font assets (ADR-0010's established pattern for vendored third-party binary/reference resources) — reject and degrade rather than trust an unverified file.
2. **Licensing is explicitly unresolved, not silently assumed.** `github.com/ubsicap/usfm` declares no LICENSE file (`license: null` via the GitHub API, checked at vendoring time). Vendored anyway, per an explicit user decision made when this was raised — recorded in `manifest.json`'s `licenseNote` field rather than left implicit, since "the file is obviously fine to redistribute" was not something this session could verify.
3. **`.usfm` gets its own `Environment` (`UsfmEnvironment`, key `"usfm"`), not a mode flag on `SfmEnvironment`.** `ADR-0013` decision 3 already resolves environment identity per-extension via `profile_for_extension(...).key`; giving `.usfm` its own `SyntaxProfile` key (`syntax_profiles.USFM`, reusing `SFM`'s tokenizer rules — the lexical marker syntax is identical) lets it resolve to its own environment through the exact same mechanism E2 built, with no new resolution machinery. `.sfm` keeps resolving to generic `SfmEnvironment` unchanged. USFM-vs-generic-SFM *content sniffing* (a `.sfm` file that's actually valid USFM) is not implemented — extension is the only detection signal in this phase, matching the "smallest next step" principle; adding content-based resolver scoring (spec §10) is deferred until a real need for it surfaces.
4. **Baseline loading is lazy and cached**, exactly like activation always has been in this framework: nothing at package-import time reads or parses `usfm.sty` — only `UsfmEnvironment.__init__`, itself only constructed when a `.usfm` document opens, triggers the first (cached) load. Satisfies the spec's "do not initialize SFM/STY/parser infrastructure during startup unless a file is actually opened" (§9) without any special-casing.
5. **No hand-rolled OccursUnder/structural walker.** `usfmtc`'s grammar-based parser already reports misplaced/unknown markers (verified empirically: it flagged an unrecognized `\zzzcustom` tag against its built-in grammar). Building a second, StyleRegistry-driven OccursUnder checker before observing a gap `usfmtc` doesn't already cover would be speculative — this phase's own baseline-only `StyleRegistry` would mostly restate what `usfmtc` already knows. The registry is kept for structural *queries* (a future marker/style inspector), not duplicated into a second validator.
6. **`usfmtc` position data is not translated into `EnvironmentFinding` source ranges.** Empirically, `usfmtc`'s reported `Pos(line, col)` does not correspond to a naive line count of the raw source — the same offending line reports different line numbers depending on which header markers precede it (verified with `\id`/`\usfm` present vs. absent). Guessing a translation risks silently mislocating an error onto the wrong text, which is worse than an unlocalized finding. Every `usfmtc` finding therefore spans the whole document; the message includes `usfmtc`'s own verse reference (e.g. `"GEN 1:1"`) so it stays actionable. Revisiting this needs either deeper study of `usfmtc`'s internal counting or a lower-level API with real source offsets — not attempted here.
7. **`usfmtc` added as a hard dependency** (`pyproject.toml`, `usfmtc>=0.4`), not optional — per explicit user decision. Imported lazily inside `usfmtc_adapter.validate_with_usfmtc()` (not at module top), so its own import/grammar-construction cost is paid only when a `.usfm` document is actually validated, matching decision 4's laziness for the same reason.
8. **Chapter/verse navigation is a Core-only index with no UI wiring**, following the same "build the mechanism, defer the consumer" pattern `EnvironmentFinding`/`validate()` already established in E3. `build_chapter_verse_index()` walks the lossless tokenizer (not `usfmtc`) for `\c`/`\v` markers — no stylesheet knowledge needed, since chapter/verse markers are fixed USFM lexical convention, not `.sty` data.
9. **The unmatched-end-marker check is shared**, factored out of `sfm_environment.py` into `sfm/validation.py`, so `UsfmEnvironment` reuses the identical generic-SFM lexical rule rather than a second copy that could drift — USFM is generic SFM plus more, not a different marker syntax.

## What shipped

- `core/environments/sfm/assets/usfm.sty`, `assets/manifest.json`: vendored baseline (provenance, sha256, licensing note).
- `core/environments/sfm/usfm_baseline.py`: `load_usfm_baseline()` — cached, hash-verified, never-raises loader.
- `core/environments/sfm/validation.py`: `unmatched_end_marker_findings()`, factored out of `sfm_environment.py`.
- `core/environments/sfm/navigation.py`: `VerseLocation`, `build_chapter_verse_index()`.
- `core/environments/sfm/usfmtc_adapter.py`: `validate_with_usfmtc()` — lazy import, whole-document-span findings (decision 6).
- `core/environments/usfm_environment.py`: `UsfmEnvironment` (`key = "usfm"`) — decoration via the new `USFM` `SyntaxProfile`, `style_registry` property (baseline-only `StyleRegistry`), `chapter_verse_index()`, `validate()` (shared end-marker check + `usfmtc`).
- `core/syntax_profiles.py`: `USFM` profile (reuses `SFM`'s tokenizer rules); `DEFAULT_EXTENSION_PROFILES["usfm"]` changed from `"sfm"` (E5) to `"usfm"`.
- `core/environments/__init__.py`, `app/service.py`: `UsfmEnvironment` registered alongside its siblings.
- `pyproject.toml`: `usfmtc>=0.4` dependency; `uniti.core.environments.sfm` package-data for the vendored asset + manifest.
- Tests: `tests/test_sfm_usfm_baseline.py` (3), `tests/test_sfm_navigation.py` (6), `tests/test_sfm_usfmtc_adapter.py` (4), `tests/test_usfm_environment.py` (9), plus 2 updated/new cases in `tests/core/test_syntax_profiles.py` for the new `USFM` profile — 22 new tests.
