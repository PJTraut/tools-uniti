# UNITI v0.001b1 Real-World Feedback Beta Design

Date: 2026-09-05
Status: approved
Activation condition: the complete `v0.001a24` Beta Candidate gate passes with fresh evidence

## Goal

Promote the fully verified A24 application to `v0.001b1` and run a private, opt-in, cross-platform real-world feedback period without reopening broad feature development, adding automatic telemetry, or weakening UNITI's document-safety and bounded-resource guarantees.

B1 is a stabilization milestone. A24 proves that the executable product is fit to enter beta; B1 learns from independent human use of the exact promoted builds and turns accepted defects into reproducible, verified corrections.

## Approved decisions

1. A24 remains the final alpha gate. UNITI does not identify itself as B1 until every A24 acceptance item passes on one exact candidate with fresh local, hosted, clean-host, bundle, health, startup, recovery, and performance evidence.
2. A24 closes before B1 opens. The A24 candidate and evidence remain immutable historical facts; B1 is created by a separate promotion commit.
3. Promotion updates source/display/package and bundle metadata, project documentation, tests, and the active roadmap milestone, then pushes the verified commit to `main`.
4. Promotion creates no Git tag, GitHub release, public package, installer publication, or automatic update channel. A later verified beta-build decision may create an immutable tag.
5. B1 feedback opens only after B1-labelled macOS, Windows, and Linux bundles from the same commit pass the complete clean-host executable and bundle gates.
6. B1 remains feature-frozen. Work is limited to defect correction, diagnostic clarity needed to reproduce a report, bounded evidence plumbing, tester documentation, and release-blocking compatibility or safety remediation.
7. Feedback is opt-in and manually submitted. UNITI never uploads telemetry, diagnostics, documents, or feedback automatically.
8. A23's sanitized diagnostic export is reused. B1 does not create a second diagnostic, health, repair, or recovery authority.
9. Every distribution contains one visible top-level `BETA_TESTER_INFO.txt` whose version and build identity agree with the executable manifest.
10. The minimum feedback gate is fourteen calendar days and three independent testers: at least one tester on macOS, one on Windows, and one on Linux.
11. Each tester covers ordinary editing; the cohort collectively covers large files, encoding/EOL and malformed input, regex replacement, recovery/Safe Session, repair, and multi-window/split/docking behavior.
12. Raw feedback and support bundles stay outside Git. The repository retains only bounded, content-free classification and verification evidence.

## Existing boundary

A23 owns the executable application, embedded runtime, native launcher, Health & Recovery Center, sanitized diagnostic export, repair transactions, Safe Session, one-instance forwarding, and bundle manifests. A24 owns feature freeze and the complete beta-candidate acceptance gate.

B1 consumes those verified capabilities. It does not implement executable packaging for the first time, reinterpret an incomplete A24 item as a beta limitation, or use user feedback as a substitute for automated acceptance evidence.

Accounts, cloud telemetry, background upload, remote control, automatic updating, public crash reporting, an in-application issue tracker, signing/notarization expansion, and a general analytics subsystem remain outside B1.

## Approaches considered

### Selected: strict milestone handoff

Close A24 on an exact verified candidate, preserve its evidence, and create B1 with a separate metadata/documentation promotion commit. Qualify B1-labelled bundles before private distribution and collect bounded content-free evidence from explicit human feedback.

This keeps alpha proof, beta identity, distributed binaries, and feedback evidence unambiguous. A report always names the exact build that produced it.

### Rejected: overlap A24 and B1

Labelling late A24 builds as beta while A24 gates remain open would blur whether feedback applies to a proven beta candidate or unfinished alpha work. It would also allow real-world reports to be mistaken for missing clean-host or deterministic acceptance evidence.

### Rejected: tag-first public beta

Creating a tag or public release at promotion would make an immutable distribution claim before the first B1-labelled bundle matrix and private feedback round pass. B1 deliberately starts on `main` without a tag or public release.

## Promotion state machine

```text
A24_ACTIVE
  |-- any required gate not PASS --------------------> remain A24_ACTIVE
  `-- exact candidate + all required evidence PASS
                         |
                         v
                 A24_IMPLEMENTED
                         |
              separate promotion commit
                         |
                         v
                 B1_ACTIVE_NOT_OPEN
  |-- any B1-labelled bundle gate not PASS ----------> remain closed
  `-- same-commit macOS + Windows + Linux PASS
                         |
                         v
                 B1_FEEDBACK_OPEN
  |-- critical safety report ------------------------> pause distribution
  |-- behavior-changing correction -----------------> qualify a new build
  `-- complete cohort + duration + coverage + triage
                         |
                         v
                 B1_FEEDBACK_GATE_PASS
```

Passing the feedback gate does not infer a tag, release, next version, or public distribution. Those require a separate explicit decision.

## A24 closure contract

Promotion admission requires all of the following on one exact A24 candidate:

- every A24 milestone checklist item is checked with fresh evidence;
- no known data-loss, byte/encoding/EOL corruption, unsafe overwrite, unsafe repair, or startup-dead-end defect remains;
- Undo/Redo, saved history, recovery, Safe Session, repair rollback, regex replacement, and one-service ownership pass;
- 10–100 MB ordinary use and sparse 1 GiB design-target behavior remain characterized and bounded;
- reproducible native bundles and complete inventories pass on macOS, Windows, and Linux;
- healthy, warning, blocking, fatal, self-heal, consent-repair, rollback, and Safe Session startup outcomes pass;
- no supported public CLI dependency remains; and
- selected performance and bundle-inventory baselines are recorded without raw user or document content.

`WARN`, `INVALID`, `NOT RUN`, a skipped required platform, or unreviewed evidence cannot authorize promotion.

## Promotion transaction

The A24 closure and B1 promotion are separate commits so Git history retains the exact alpha evidence boundary.

The A24 closure commit:

1. records the exact candidate and all acceptance evidence;
2. moves the A24 milestone and governing design/implementation records to `03_implemented`;
3. updates the implemented index and current product documentation; and
4. captures a historical handover snapshot.

The B1 promotion commit:

1. changes `VERSION` and display identity to `v0.001b1`;
2. changes PEP 440 package identity to `0.1b1` in `pyproject.toml`, `uniti.__version__`, and exact version tests;
3. updates launcher, bundle manifest, diagnostics, support-bundle, and tester-information identity inputs from the same canonical version source;
4. creates the active B1 milestone and moves the roadmap from A24 to B1;
5. updates current status, scope, development guidance, and handover without rewriting A24 evidence; and
6. passes the complete local source/documentation gate before push to `main`.

Hosted and clean-host executable gates then qualify the exact pushed B1 commit. A failed gate keeps B1 active but closed to testers. It does not rewrite or reopen the implemented A24 record.

## Private beta distribution

Qualified same-commit native bundles may be supplied manually to named testers by the project owner. This design does not create a public release page, permanent download channel, installer feed, updater, account, or network service.

Each platform bundle remains governed by A23/A24 manifest, inventory, reproducibility, size, startup, and clean-host rules. Testers replace a beta bundle explicitly; UNITI does not update itself. A distributed bundle is qualifying evidence only when its manifest/build identity matches the active B1 feedback candidate.

If a behavior-changing correction is accepted, a new B1 build identity is produced and all three platform bundle gates rerun. The fourteen-day gate restarts for changes to document bytes, persistence, recovery, repair, startup, one-instance ownership, executable contents, or platform behavior. Documentation-only corrections that do not change the distributed bundle do not restart it.

## `BETA_TESTER_INFO.txt`

Every B1 distribution contains exactly one UTF-8 `BETA_TESTER_INFO.txt` at the visible top level next to the public application entry point. It is generated from one version-controlled template during packaging and is listed in the bundle manifest.

The file contains:

- exact display/package version, source commit, build identifier, platform, and deterministic build date;
- a beta-risk notice and recommendation to retain backups of important documents;
- supported operating-system and bundle expectations;
- the required feedback workflows and concise start instructions;
- known limitations approved for the active build;
- steps to open Health & Recovery and export a sanitized support bundle;
- a list of information excluded from that bundle;
- a reminder to review the export before sending it;
- severity guidance for data loss, corruption, unsafe overwrite/repair, and startup failure;
- instructions to return feedback to the person who supplied the private beta build; and
- an explicit statement that UNITI never submits feedback or diagnostics automatically.

The build date derives from the canonical source/build timestamp rather than wall-clock packaging time so reproducible builds remain possible. The file is at most 64 KiB. Packaging fails on a missing/duplicate file, invalid UTF-8, unresolved template token, mismatched version/build/platform identity, disallowed control character, or manifest omission.

The tester file contains no secret, credential, private repository location, expiring URL, personal address, or machine-specific absolute path.

## Feedback workflow

1. The project owner assigns the tester an opaque local tester ID and supplies one qualified platform bundle.
2. The tester reads `BETA_TESTER_INFO.txt`, uses UNITI normally, and exercises the stated scenarios.
3. The tester reports observations manually to the person who supplied the build. A sanitized A23 support bundle is optional and always user-initiated.
4. The maintainer assigns an opaque issue ID and records only the content-free classification facts in repository evidence.
5. Narrative, screenshots, support archives, paths, and reproduction documents remain outside Git and follow the tester's explicit sharing decision.
6. Accepted defects receive a minimal deterministic reproduction, a failing regression test, a correction, relevant local and platform verification, and a fixed/verified disposition.
7. A new qualifying build is distributed when a correction changes executable behavior. Superseded builds are marked closed to new feedback.

UNITI itself does not know tester identity, contact details, issue-system credentials, or submission destination. The private distributor relationship supplies that context.

## Content-free feedback evidence

The repository stores one schema-versioned bounded summary for the active B1 candidate. It contains separate tester-coverage records and issue records so a completed workflow with no defect remains provable without inventing an issue.

Each tester-coverage record contains only:

- opaque tester ID;
- fixed tester class (`independent_human`, `developer`, or `synthetic`);
- exact manifest build identifier and platform family;
- one approved workflow category;
- day-precision completion date; and
- fixed `completed` outcome.

Each issue record contains only:

- opaque tester and issue IDs;
- exact source commit, manifest build identifier, and platform family;
- one approved workflow category;
- fixed severity and triage state;
- first/last observation dates at day precision;
- reproducibility outcome;
- correction commit where applicable; and
- verification platform/result facts.

Allowed workflow categories are `ordinary_editing`, `large_file`, `format_integrity`, `regex_replacement`, `recovery_safe_session`, `repair`, and `multi_window_layout`.

Allowed triage states are `new`, `reproduced`, `accepted`, `duplicate`, `cannot_reproduce`, `fixed`, `verified`, and `declined_with_reason`. Decline reasons and reproduction outcomes use fixed codes; narrative does not enter the summary.

The summary is capped at 256 KiB and 1,000 aggregate coverage-plus-issue records, rejects unknown fields and duplicate identities, and contains no document content, filename/path, regex text, replacement text, clipboard data, recovery/session payload, raw diagnostic value, free-form comment, tester name, email address, credential, IP address, or machine identifier. Raw submissions and support bundles are never committed as fixtures or CI artifacts.

## Severity and distribution policy

`critical` covers suspected data loss, silent byte/encoding/EOL corruption, unsafe overwrite, unsafe repair or rollback, recovery evidence destruction, or a supported-platform startup dead end. A new critical report pauses broader distribution immediately until it is reproduced or safely ruled out. A correction must pass the complete affected safety matrix and all-platform executable smoke before distribution resumes.

`high` covers a dependable core workflow that cannot complete safely but retains all data and recovery evidence. `normal` covers incorrect or materially confusing supported behavior with a safe workaround. `low` covers bounded cosmetic or documentation defects.

Every report is triaged. `cannot_reproduce` records the attempted build/platform/workflow matrix. `declined_with_reason` requires one fixed policy reason. Neither state silently removes a report from gate evidence.

## Feedback gate

The feedback clock starts only when the first tester receives a B1-labelled build that passed the same-commit macOS, Windows, and Linux qualification matrix.

The gate requires:

- at least fourteen elapsed calendar days on the current qualifying behavior candidate;
- at least three independent human testers, including at least one on each supported platform family;
- ordinary open/edit/save/explicit-Quit use by every tester;
- collective coverage of every approved workflow category;
- every received report assigned an issue ID and terminal or actively blocking triage state;
- every accepted correction regression-tested and verified on its applicable platforms;
- complete local, hosted, clean-host executable, health, recovery, bundle-inventory, and performance gates on the final candidate; and
- zero unresolved `critical` findings.

Synthetic smoke, CI, developer self-use, benchmark runs, duplicate tester identities, elapsed time before qualification, and reports from mismatched or unverifiable builds do not satisfy the human cohort requirement.

The project may retain unresolved non-critical reports only through an explicit reviewed disposition that demonstrates a safe workaround and no contradiction with supported B1 behavior. The feedback gate is not a mechanism for relabelling failed safety or required acceptance work as a known limitation.

## Failure handling

- Diagnostic/support export failure changes no document, session, recovery, repair, or application state. The existing bounded local failure guidance remains available and the tester can report manually.
- Oversized or malformed support input is not unpacked into the repository. Intake records only a fixed rejection outcome outside the application.
- A build/manifest mismatch makes a report diagnostically useful but ineligible for the candidate gate until its identity is established.
- A missing or invalid tester-information file fails bundle qualification and blocks distribution.
- A feedback-summary capacity breach blocks new evidence publication; it never deletes unresolved records silently. The maintainer closes/summarizes resolved entries under review before admitting more.
- Unknown severity, state, workflow, platform, or correction identity fails closed and cannot count toward the gate.
- Failure to recruit the required cohort leaves B1 active and incomplete; automated tests cannot substitute for users.

## Verification strategy

### Promotion verification

- exact A24 completion checklist and evidence audit;
- version identity tests across `VERSION`, Python metadata, package metadata, launcher, diagnostics, manifest, and UI display;
- documentation lifecycle/link/status validation;
- complete source suite, compile gate, self-check, offscreen/native smoke, and clean worktree;
- push/remote SHA equality on `main`; and
- no tag or release at promotion.

### Distribution verification

- same-commit macOS, Windows, and Linux standalone builds;
- reproducibility and normalized bundle-inventory comparison;
- clean-host launch, one-instance/open forwarding, health, repair, recovery, Safe Session, and explicit-Quit acceptance;
- tester-file presence, uniqueness, UTF-8, 64 KiB bound, identity, deterministic timestamp, manifest membership, and unresolved-token rejection; and
- no host Python, public CLI, updater, automatic upload, or network dependency.

### Feedback verification

- summary schema, enum, size/count, duplicate, identity, chronology, and privacy-field tests;
- support-export redaction and inherited A23 size/failure tests;
- candidate clock/cohort/platform/workflow calculations with deterministic dates;
- behavior-change reset and documentation-only non-reset tests;
- critical-report distribution-pause tests;
- accepted-defect regression and platform-evidence linkage; and
- a final manual audit that raw reports, archives, screenshots, paths, content, and personal identifiers are absent from Git and CI artifacts.

## Completion boundary

B1 begins only after A24 is implemented and the promotion commit reaches `main`. Real-world feedback begins only after the exact B1 bundles qualify. B1 completes only when its feedback gate passes with fresh final-candidate evidence.

B1 completion does not automatically create a tag, release, package publication, next beta version, release candidate, or general-public distribution. Those are separate product and distribution decisions.
