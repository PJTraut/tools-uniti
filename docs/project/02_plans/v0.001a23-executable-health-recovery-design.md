# UNITI v0.001a23 Executable Health & Recovery Alpha Design

Date: 2026-09-05
Status: approved
Milestone: [`v0.001a23` — Executable Health & Recovery Alpha](v0.001a23-executable-health-recovery-alpha.md)

## Goal

Replace UNITI's public source-launcher and fail-to-terminal startup experience with a native executable application that performs a fast read-only health classification and either opens the editor or gives the user precise repair, recovery, Safe Session, diagnostic-export, or reinstall guidance.

A23 is a distribution and startup-resilience milestone. It preserves the one-service, document-authority, durability, recovery, bounded-resource, local-only, and cross-platform guarantees implemented before it.

## Approved decisions

1. A23 is queued immediately after A22. The former A23 Beta Candidate becomes A24.
2. The shipped product has a GUI-only public interface. Private developer and CI scripts remain command-driven but are not shipped or compatibility-supported product interfaces.
3. The deliverable is a native standalone application bundle: macOS `.app`, a Windows application directory containing `UNITI.exe`, and a Linux application directory/AppDir with a desktop launcher.
4. Python, PySide6, Qt, the regex engine, and required application dependencies are embedded. Normal users do not install, select, repair, or maintain host Python.
5. Packaging uses a pinned `pysidedeploy.spec` in standalone mode, backed by the Qt-supported Nuitka deployment path and built independently on each target operating system.
6. A tiny compiled native launcher remains independent of Python and Qt. It validates a bounded critical bundle surface, starts the inner UNITI executable through a private protocol, and presents minimal fatal-runtime/reinstall guidance if the inner health system cannot start.
7. The application health check is read-only. Healthy startup continues automatically; warnings allow editing with a Health notice; recoverable blockers open Health & Recovery before loading documents; fatal bundle/runtime failures remain launcher-owned.
8. Repair is offline, local-only, previewed, explicitly confirmed, narrow, verified, and reversible where practical. It never alters user documents or valid recovery evidence.
9. Repair quarantine is bounded by the first of seven days or 128 MiB. Same-filesystem moves avoid copying large application-state artifacts.
10. One service-owned Health & Recovery Center combines diagnosis, repair guidance, and the existing document-recovery choices without merging their underlying authorities.
11. Native Open With, double-click, drag/drop, and activation requests forward to the one running service. Launcher arguments and IPC are private implementation details, not a public CLI grammar.
12. Public CLI compatibility is retired only after executable parity passes. The installed console entry point and supported `.command`/`.bat` launchers then leave the product surface.
13. Signing, notarization, installers, updating, network repair, privilege elevation, and malicious-tamper guarantees remain outside A23.

## Existing baseline and gaps

The implemented A21 baseline already provides:

- ordered startup phases with stable exit/failure classes, setup state, and bounded startup logging;
- fast and deep self-checks plus deterministic/native smoke paths;
- explicit bootstrap into a UNITI-owned Python environment and dependency validation;
- absolute cross-platform application paths and capability-aware durability;
- exact macOS, Windows, and Linux source-launcher coverage;
- one process-lifetime `UNITIService`, one-instance arbitration, native local IPC, and forwarded file requests;
- complete settings/session/recovery schemas, saved-byte hashes, durable session generations, bounded recovery journals, and explicit recovery choices;
- export-safe diagnostics and bounded failure evidence; and
- a four-lane hosted source matrix.

That architecture remains a developer/source distribution. Ordinary startup can fail before a GUI exists and prints a repair command to a terminal. Users must have or bootstrap Python, launch through shell scripts or the console entry point, and understand `--self-check`, `--smoke`, or repair flags. Recoverable phase failures terminate instead of becoming typed health findings. There is no unified health/repair UI, repair transaction/quarantine authority, embedded runtime, bundle manifest, or clean-host executable proof.

## Scope

A23 includes three implementation workstreams under one milestone:

1. **Health and repair core:** typed findings, quick/deep probes, severity/action policy, repair plans, verified transactions, bounded quarantine, Safe Session, and sanitized export.
2. **Health & Recovery UI:** pre-editor blocker presentation, in-editor warnings, repair/recovery actions, verification, rollback results, and later re-entry from Tools.
3. **Executable distribution:** native outer launcher, private readiness/open-event protocol, pinned standalone packaging, bundle manifest/inventory, product CLI retirement, and three-OS clean-host evidence.

The milestone also includes targeted structural corrections found while exercising these paths. It does not document away a startup dead end or unsafe repair as a known limitation.

## Outside A23

A23 does not add an installer, package manager, updater, signing, notarization, store submission, elevation helper, network download, account, cloud diagnostic upload, remote support channel, shell-command repair, or permanent OS service.

It does not promise bit-for-bit security against a maliciously replaced unsigned bundle. SHA-256 manifests detect accidental corruption and support diagnosis; they are not code signatures or a trust root.

It does not broaden document editing, regex semantics, workspace/project scope, plugin capability, syntax highlighting, or application preferences beyond the health/repair actions required here.

## Approaches considered

### Selected: Qt-supported standalone bundle with two-level health

Use Qt's `pyside6-deploy` configuration in standalone mode to produce the embedded UNITI application per target OS. Put a small native launcher outside the Python/Qt failure boundary and keep the full typed health, repair, recovery, and UI system inside UNITI.

This is the only approach considered that satisfies executable-only product use, user-visible guidance when the embedded runtime cannot start, detailed cross-platform repair when it can, and a bounded bundle whose components remain inspectable.

### Rejected: PyInstaller one-folder with custom ownership

PyInstaller can produce one-folder bundles and is easier to inspect than one-file extraction. It would require UNITI to own more PySide6 collection/hooks and platform deployment behavior than the current Qt-supported deployment path. It remains a fallback only if an A23 feasibility proof finds a blocking `pyside6-deploy` defect.

### Rejected: Qt-only health in the current source runtime

Keeping all health behavior inside the present Python entry point would be smaller, but cannot present guidance when Python, Qt, or dependency bootstrap itself fails. It also retains the public CLI/bootstrap lifecycle that A23 is intended to remove from the product.

## Roadmap and workstream boundary

A22 remains active and owns sustained dogfood/performance hardening. A23 remains queued until A22 completes. A23 can reuse A22 startup timing, resource, crash/recovery, and evidence infrastructure, but cannot expand A22's implementation scope.

Within A23, the Qt-free health/repair core is built first against source-mode fixtures. The Health & Recovery UI consumes that stable model. The launcher and bundle workstream then makes the same public application path executable-only. Public CLI removal is last, after parity and private automation replacements pass.

A24 Beta Candidate freezes features and validates the completed executable/health architecture. It does not own first implementation of executable packaging.

## Shipped artifact topology

```text
native OS launch / open-document event
                |
                v
small native outer launcher
  |-- quick manifest identity / critical presence + size
  |-- private child readiness channel
  |-- native fatal-runtime guidance
  `-- private activation/open request handoff
                |
                v
standalone inner UNITI executable
  |-- embedded CPython + required modules
  |-- PySide6 / selected Qt libraries and plugins
  |-- regex engine + UNITI resources
  |-- read-only quick HealthEngine
  |-- one UNITIService
  `-- editor or Health & Recovery Center
```

The outer launcher is process-lifetime infrastructure, not a daemon. It starts or contacts one inner UNITI service for the current user, monitors the readiness outcome, and exits according to the per-platform application-lifecycle adapter. It has no editor, repair, document, session, or recovery semantics.

The inner executable contains the current UNITI application. Source and bundled modes use the same health, service, document, recovery, and UI APIs; only runtime identity, bundle facts, and native-event adapters differ.

## Native launcher responsibilities

The launcher accepts only native OS activation/open-document events and a build-owned private handoff from its platform registration. It has no `--help`, `--version`, repair flags, positional-file contract, or general option parser.

Its critical path:

1. locate its own bundle root without consulting the working directory or `PATH`;
2. read a strictly bounded launcher manifest header;
3. verify schema, platform, build identity, required inner executable, and critical file presence/size;
4. connect to an existing primary instance or spawn the exact bundled inner executable with shell execution disabled;
5. pass a private inherited readiness endpoint and bounded native-open request;
6. wait until ready, health-blocked, forwarded, or fatal under an explicit deadline; and
7. present minimal native guidance when the inner system cannot report for itself.

The launcher never runs Python from the host, invokes a package manager, changes application state, repairs the bundle, or parses document content. Full file digests are intentionally outside the every-launch critical path.

Native fatal presentation uses a small platform adapter: the Windows system message API, a macOS native alert API, and the standard Linux desktop portal/notification path with a bounded local error record fallback when no graphical notification service is available. Messages expose a stable code, application version, reinstall guidance, and the location-neutral option to open the containing help record; they do not expose command lines or raw loader errors.

## Private readiness and activation protocol

The launcher/inner protocol is schema-versioned, length-prefixed, local-only, and size bounded. It carries only:

- protocol/build identity;
- launcher outcome and inner readiness state;
- activation intent;
- a bounded list of native-open file paths supplied by the OS; and
- one stable safe failure code.

The protocol is not accepted over a network socket and has no arbitrary command field. The existing one-instance authority remains in UNITI. A secondary launcher either forwards its native-open request to the primary or reports that the primary Health & Recovery Center has queued it. It never creates a second document service.

If the primary is health-blocked, requested files remain visible as a bounded pending count; UNITI opens them only after repair, recovery, or Safe Session permits document loading. Existing canonical path identity and one-document authority still apply.

## Health model

`HealthEngine` is Qt-free and owns a fixed probe registry. A probe receives explicit immutable inputs and returns one or more immutable findings. It does not mutate, repair, display UI, read global Qt state, or convert failure into success.

Each `HealthFinding` contains:

- stable issue code and probe version;
- `healthy`, `warning`, `blocker`, or `fatal` severity;
- affected subsystem and safe summary;
- bounded typed evidence facts;
- applicable action identifiers;
- whether normal editor startup is permitted;
- whether Safe Session is permitted; and
- whether deep verification is required.

Reports order blockers, recovery findings, and warnings deterministically. Unknown fields, duplicate issue IDs, contradictory actions, unbounded evidence, and invalid severity transitions fail closed into one bounded internal-health finding.

Health reports never contain document text/bytes, search or replacement expressions, clipboard contents, credentials, IPC payloads, arbitrary exception strings, or raw stack traces. In-app presentation may identify an affected user-visible document when recovery already owns that disclosure; export-safe reports redact paths and source identities.

## Quick and deep probes

Quick probes run read-only before session restoration and target a controlled-host warning budget of 250 ms and failure budget of 500 ms. Hosted timings are diagnostic. Independent probe deadlines prevent one blocked filesystem or service from hanging the complete health decision.

The quick set covers:

- launcher-supplied bundle/build identity;
- absolute application roots, basic read/write capability, and free-space reserve;
- settings and setup-state schema headers;
- current session pointer plus bounded complete-generation discovery;
- recovery-journal discoverability without replaying every transaction;
- live versus stale instance ownership;
- previous clean/unclean shutdown evidence;
- required Qt platform plugin and concrete editor-font capability; and
- disposable cache/temp directory health.

Deep verification runs only on explicit request or when a finding requires it. It can hash the complete allowlisted bundle, validate all selected session packs, inspect recovery journals under existing bounds, exercise write/sync/replace probes in owned temporary paths, and run the existing functional self-checks through direct APIs.

Probe failure is a finding, not an unhandled startup exception. A probe that cannot distinguish healthy from damaged state does not report healthy.

## Startup state machine

```text
LAUNCHER_PREFLIGHT
  |-- fatal ----------------------------> NATIVE_REINSTALL_GUIDANCE
  `-- inner started
         |
         v
INNER_QUICK_HEALTH
  |-- healthy --------------------------> SESSION_RESTORE -> EDITOR_READY
  |-- warning --------------------------> EDITOR_READY + HEALTH_NOTICE
  `-- blocker --------------------------> HEALTH_AND_RECOVERY
                                             |-- repair -> VERIFY --+
                                             |-- recover -> VERIFY -+--> continue
                                             |-- Safe Session ------+--> BLANK_EDITOR
                                             `-- Quit ----------------> CLEAN_EXIT
```

Recoverable startup callbacks return findings rather than terminating the process. Unexpected inner startup errors are converted to a stable `internal-startup` blocker when Qt remains usable. Only a failure below the Python/Qt boundary remains launcher-fatal.

Healthy startup does not display or wait on the Health & Recovery Center. Warnings do not seize focus; they appear in a persistent non-color-only Health status surface. Blockers prevent session/document loading until a valid action completes or the user selects Safe Session.

## Repair model

`RepairEngine` is separate from `HealthEngine`. It accepts a sealed report plus selected action IDs and produces an immutable `RepairPlan`. Plans identify the affected owned artifact categories, preconditions, consequences, quarantine/rollback behavior, mutation boundary, and postcondition probes.

A repair transaction:

1. confirms the report seal is still current;
2. validates exact target ownership and capacity;
3. presents the complete plan and receives explicit consent;
4. atomically moves affected application state to same-filesystem quarantine where applicable;
5. performs the narrow mutation;
6. reruns every relevant probe;
7. commits on verified success or restores quarantine on failure; and
8. emits one bounded result and durability level.

No repair accepts an arbitrary path, command, module, package, URL, or script. No repair modifies user documents, valid recovery candidates, a running process's live lease, or the installed bundle.

Cancellation is permitted until the first mutation boundary. A brief atomic rename/replace boundary completes before cancellation can take effect, avoiding partial repair state.

## Supported finding/action matrix

| Finding | Severity | Offered action |
|---|---|---|
| Invalid settings | blocker or warning | quarantine invalid file; restore defaults; verify |
| Invalid setup state | blocker | quarantine owned record; rebuild from bundle facts; verify |
| Missing application directory | blocker | create exact owned directory; verify permissions/durability |
| Unwritable application root | blocker | guidance/export; no privilege escalation |
| Low free space | blocker or warning | explain requirement; optionally clear exact disposable data; recheck |
| Stale instance record | blocker | retire only after failed liveness proof; retry arbitration |
| Live primary | healthy | forward activation/open request |
| Stale/missing session pointer with valid generation | warning or blocker | repair pointer to verified generation |
| Invalid session state | blocker | preserve evidence; inspect recovery or start Safe Session |
| Recovery candidates | blocker | existing Save/Open Disk/Locate/Skip choices |
| Damaged disposable cache/temp | warning | clear exact owned artifacts; recreate directory |
| Missing preferred font with valid fallback | warning | select/report verified fallback |
| Missing required Qt platform capability | fatal | launcher-visible reinstall guidance |
| Bundle digest/inventory mismatch | fatal | full verify; reinstall guidance |
| Internal health failure | blocker | retry, Safe Session if permitted, sanitized export, or Quit |

The matrix is allowlisted and schema-versioned. UI code does not invent or broaden repairs.

## Quarantine and rollback

Repair quarantine lives under one application-state-owned root on the same filesystem as the state it protects. Renames are preferred over copies so large invalid session artifacts do not duplicate disk use. Each entry records schema, issue/action ID, original owned category, created/expiry time, byte accounting, and integrity digest without exporting the original path.

Retention is bounded by the first of seven days or 128 MiB. Oldest expired/closed repair entries prune first. Current repair rollback state, valid recovery evidence, active session generations, and user documents are never pruned to satisfy this budget. If the repair cannot establish a reversible move, it refuses before mutation unless the target is already-classified disposable cache/temp data and the preview states that deletion is irreversible.

Rollback revalidates both the quarantine entry and current destination state. It never overwrites newer application state. Conflicts remain visible for manual choice.

## Safe Session and recovery authority

Safe Session creates one normal `UNITIService` and a blank editor shell while deliberately bypassing persisted session restoration. It does not reset settings unless a separately confirmed settings repair already succeeded. It preserves session manifests, history packs, recovery journals, pending native-open requests, and quarantine entries.

The user can reopen Health & Recovery from Safe Session, inspect recovery, export diagnostics, or retry verification. Pending native-open files are not opened automatically until the health policy says document loading is safe.

The existing `RecoveryManager` remains authoritative for journal discovery, exact saved-byte hashes, candidate replay, Locate/Open Disk/Save/Skip semantics, and evidence retirement. The new center hosts those choices but does not reimplement them in repair code.

## Health & Recovery Center

The center is one service-owned window that can appear before the editor or reopen later from `Tools -> Health & Recovery`.

Its issue-first structure contains:

- an overall state, plain-language summary, and last-check time;
- a deterministic list with blockers first, recovery items second, and warnings last;
- selected-issue details: detection, impact, recommended action, affected application-state category, quarantine/rollback behavior, and verification steps; and
- applicable `Repair`, `Recover...`, `Verify Again`, `Start Safe Session`, `Export Diagnostics...`, and `Quit` actions.

Bundle corruption never displays a misleading Repair action. `Repair Recommended` may group compatible allowlisted actions, but it shows one consolidated preview and confirmation before execution. Conflicting actions remain separate.

Repair/deep-check work is asynchronous through the resource/task authority. Progress exposes the current stable phase and safe cancellation. Each result becomes `Repaired`, `Still Present`, or `Rolled Back` after immediate recheck. Failure keeps the center available.

Keyboard navigation, screen-reader labels, accessible issue summaries, non-color severity indicators, logical focus order, and copyable safe details are required. Raw traces remain internal and appear only in an explicitly exported sanitized diagnostic when allowed.

## Packaging policy

The checked-in `pysidedeploy.spec` is the sole deployment configuration. It pins the application entry point, project file, standalone mode, exact required Qt modules/plugins, exclusions, product metadata, and per-platform additions. Build dependencies and their hashes/versions are locked separately from runtime dependencies.

Builds occur natively on macOS, Windows, and Linux. They do not cross-compile or download dependencies during the verification phase. The build environment may be command-driven because it is private developer/CI infrastructure.

The bundle contains only required application/runtime components. QML, QtWebEngine, QtCharts, multimedia, development tools, tests, corpora, source-only bootstrap/CI scripts, caches, and build intermediates are excluded unless an explicit runtime dependency proves otherwise.

Every build emits a schema-versioned manifest with:

- product, display, protocol, and manifest versions;
- OS/architecture/build identity;
- locked Python/PySide6/Qt/regex/Nuitka inventory;
- allowlisted relative file inventory, byte sizes, and SHA-256 digests;
- selected Qt modules/plugins;
- normalized aggregate/component sizes; and
- build evidence free of workspace/home/temp paths.

The first accepted bundles establish per-platform size anchors. Later normalized inventory growth of 10% warns; 20% blocks acceptance until explicitly reviewed. Unknown executables, libraries, plugins, or writable content fail inventory validation.

Two clean builds per OS must produce identical dependency inventories and normalized manifests. Platform toolchain metadata that cannot be made byte-identical is normalized and separately reported; A23 does not claim unsupported bit-for-bit determinism.

## CLI retirement

Executable parity is proven before public CLI removal. The final A23 product boundary is:

- no installed `uniti` console entry point;
- no supported `uniti.command` or `uniti.bat` product launcher;
- no public `--help`, `--version`, `--self-check`, `--smoke`, repair, or positional-file grammar;
- version, health, diagnostics, repair, and recovery available in the GUI; and
- native OS open/activation events as the only external document-open surface.

Self-check, smoke, bootstrap, build, and test automation move to private `scripts/` entry points or direct Python APIs. Source developers may run those scripts from the owned development environment. They carry no end-user compatibility promise and are excluded from bundles.

The product still has internal process arguments or inherited handles where the OS/bundler requires them, but they are generated and validated by the launcher protocol and are never documented as user commands.

## Error handling

- Outer launcher failure before inner readiness produces a stable native message and bounded local record.
- Quick-probe failure becomes warning/blocker/fatal according to allowlisted policy; it never becomes healthy by default.
- Health-model validation failure becomes one internal-health blocker.
- Repair precondition drift invalidates the plan before mutation.
- Repair mutation/verification failure rolls back when safe and remains visible.
- Rollback conflict never overwrites newer state.
- Quarantine-capacity failure refuses non-disposable repair before mutation.
- Native activation overflow refuses excess paths with a visible bounded count; it does not grow a queue without limit.
- Full bundle verification failure recommends reinstall and never rewrites the bundle.
- Diagnostic export failure leaves health/repair state unchanged.

## Security and privacy boundary

The launcher never invokes a shell and always resolves its inner executable beneath its own bundle. Private messages are length bounded and accept no arbitrary command. Application-state repairs resolve targets beneath exact `AppPaths` roots and use fixed artifact categories rather than user-supplied paths.

The system is offline. It does not upload diagnostics, fetch packages, contact an update server, elevate privileges, or ask for credentials. Export requires an explicit user-selected destination and applies the existing export-safe redaction/budget policy.

Because A23 bundles are unsigned, their manifests provide integrity diagnostics rather than publisher authentication. Signing/notarization and secure update trust require a separate approved design.

## Performance and storage budgets

- Quick inner health: warning at 250 ms and failure at 500 ms on the controlled reference host.
- Hosted health timing: diagnostic only; hangs and deadlines remain failures.
- Launcher manifest header and private messages: fixed decoded byte/count limits.
- Health findings and exported diagnostics: fixed finding, per-field, per-file, and aggregate limits.
- Repair quarantine: seven days or 128 MiB, oldest eligible entries first.
- Bundle inventory: one manifest per build; build intermediates and failed disposable bundles are not retained in the repository.
- Bundle growth: warn at 10%, block at 20% pending review.
- Startup/repair tests inject capacity/LOWDISK failures and never consume real disk to create them.

A23 inherits the A22 performance policy and cannot weaken session/history/recovery or failure-evidence budgets to make executable evidence pass.

## Verification strategy

Qt-free tests cover:

- finding/report schema, exact keys, fixed issue/action vocabulary, ordering, sealing, and safe serialization;
- quick/deep probe classification through injected filesystem, schema, liveness, capacity, bundle, Qt, font, session, and recovery facts;
- per-probe and aggregate deadlines;
- repair-plan compatibility, preview, consent token, target ownership, stale-plan rejection, mutation boundaries, verification, commit, and rollback;
- quarantine naming, same-filesystem moves, byte/day pruning, current-entry protection, and rollback conflicts;
- Safe Session preservation; and
- private launcher protocol framing, limits, schema, and command rejection.

Qt integration tests cover:

- healthy invisible pass-through;
- warning notice without focus seizure;
- blocker-first Health & Recovery presentation;
- applicable action visibility and bundle-repair exclusion;
- grouped repair preview/confirmation;
- recovery choices through the existing manager;
- progress, cancellation, verification, rollback, retry, export, Safe Session, and Quit;
- one center and one service across windows/secondary activations; and
- accessibility names, roles, focus order, and non-color severity meaning.

Native/bundle tests cover:

- target-native launcher compilation and no-console GUI launch;
- Unicode/spaced bundle and opened-file paths;
- missing/damaged manifest, missing inner executable, spawn failure, readiness timeout, health blocker, forwarding, and clean exit;
- Windows native message, macOS native alert, and Linux desktop notification/fallback behavior;
- builds from locked clean environments on each OS;
- hostile/empty `PATH`, `PYTHONPATH`, and `PYTHONHOME` without host-runtime use;
- complete allowlisted bundle inventory, excluded module/plugin checks, and full hash verification;
- two clean normalized-manifest/dependency-inventory matches per OS;
- cold/warm startup and 250/500 ms controlled health budgets; and
- corruption tests performed only on disposable bundle copies.

Private CI scripts continue to run source-mode tests, compilation, deep self-check, smoke, and performance gates. Executable acceptance additionally launches the built bundle through the same user-facing outer executable and native event path. Successful verification does not automatically publish an artifact or release.

## Milestone acceptance

A23 freezes only when:

1. healthy application-bundle startup reaches the editor automatically;
2. every supported warning and blocker produces applicable visible guidance;
3. fatal inner-runtime failure produces stable native reinstall guidance;
4. approved repairs require consent, mutate only owned state, verify success, and roll back safely;
5. user documents and valid recovery evidence survive every repair, failure, Safe Session, and injected capacity condition;
6. one service and one Health & Recovery Center own all windows and native activation/open requests;
7. Safe Session bypasses persisted restoration without deleting or rewriting it;
8. macOS, Windows, and Linux standalone bundles run without host Python or source checkout state;
9. two clean builds per OS have matching normalized manifests and dependency inventories;
10. quick health and bundle size/inventory remain within approved budgets;
11. public console entry points and shell launchers are retired only after parity, with private automation replacements green;
12. complete source and executable tests, deep self-check, offscreen/native smoke, A22 performance inheritance, and documentation coherence pass; and
13. no known startup dead end, silent failure, unsafe repair, recovery-evidence loss, data-loss, or unbounded bundle/state growth remains.

Required invalid, unavailable, or unverified OS evidence blocks freeze. Hosted bundle evidence or any pushed build configuration requires separate push authorization. A23 completion does not authorize signing, notarization, installer publication, updating, release upload, or a tag.

## Documentation boundary

Until implemented, A23 remains in `02_plans`. Current architecture/scope describe the A21 implemented source-distribution baseline and identify A23 only as approved future scope. A22 stays the sole active milestone.

At A23 completion, its milestone, design, and execution plans move to `03_implemented`; current status, scope, architecture, development, roadmap, implemented index, and handover advance coherently to A24 Beta Candidate.
