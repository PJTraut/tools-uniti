# UNITI v0.001a17 Text Integrity Alpha Design

Date: 2026-09-01
Status: approved active-milestone design; implementation not yet verified

## Goal

Make text preservation and deliberate transformation explicit invariants. Opening, editing, saving, and exporting must not silently change a file's encoding, BOM, byte order, line endings, malformed source bytes, document identity, or save state.

This design extends the existing lazy document, byte-source, annotated-decoding, streaming-save, file-identity, and tab systems. It does not replace those systems or introduce a second document authority.

## Scope

This milestone adds or completes:

- exact encoding profiles for UTF-8, Windows-1252, UTF-16 LE/BE, and UTF-32 LE/BE;
- independent encoding-confidence and line-ending reports;
- a serious low-confidence encoding-choice flow with live preview;
- explicit BOM, byte-order, and line-ending preservation or conversion;
- a UNITI-owned Save As dialog with filename and format controls together;
- safe copy/export and tab-lifecycle semantics;
- mandatory encoding-change warnings when an existing file will be overwritten;
- verified streaming saves before atomic replacement;
- malformed-byte conversion protection; and
- dirty/save-point semantics for format changes.

Large-file performance proof remains `v0.001a18`. a17 keeps all new inspection, preview, output, and verification work bounded-memory and streaming where full-file work is required.

## Canonical format grammar

### Encoding profiles

The UI and core use exact, indivisible encoding profiles:

- `UTF-8`
- `UTF-8 BOM`
- `Windows-1252`
- `UTF-16 LE`
- `UTF-16 LE BOM`
- `UTF-16 BE`
- `UTF-16 BE BOM`
- `UTF-32 LE`
- `UTF-32 LE BOM`
- `UTF-32 BE`
- `UTF-32 BE BOM`

Omission of `BOM` means no BOM. LE/BE and BOM are never inferred from a separate UI switch. `UTF-8, CRLF`, for example, means UTF-8 without a BOM and CRLF line endings.

Changing codec, byte order, or BOM presence is an encoding change.

### Line endings

Input analysis reports:

- `LF`
- `CRLF`
- `CR`
- `Mixed`, with exact counts

Output policy is one of:

- `Preserve`
- `LF`
- `CRLF`
- `CR`

A mixed file defaults to `Mixed (preserve)` in Save As. UNITI never normalizes line endings merely because a file was opened or saved. A uniform output policy is an explicit conversion.

### Compact display

Status and summaries combine the independent dimensions, for example:

```text
UTF-8, CRLF
UTF-16 BE BOM, Mixed
```

## Architecture

### Core format values

An immutable encoding-profile value owns the exact codec, byte order, BOM bytes, display label, and strict content codec. Callers do not reconstruct these relationships from strings.

An independent line-ending report records LF, CRLF, and CR counts plus the dominant and mixed state. An output-format value combines an encoding profile with a line-ending output policy.

The existing `EncodingInfo` and EOL analysis evolve toward these values without moving decoding, encoding, or save authority into the UI.

### Text-file service

A central Qt-free text-file service coordinates:

1. bounded source inspection;
2. separate encoding and line-ending assessments;
3. preview decoding under a selected profile;
4. output staging through the existing piece-table and streaming-save path;
5. staged-file verification; and
6. atomic destination replacement.

The service returns structured reports and errors. Dialogs collect decisions and render those reports; they contain no independent codec, BOM, EOL, or overwrite rules.

### Document authority

`Document` remains authoritative for logical text, source bytes, annotations, edit history, path, disk identity, selected output policy, dirty state, and save point.

The document distinguishes:

- the exact source/saved format;
- a pending output format, if one was explicitly selected; and
- source-byte annotations that have not been edited away.

Changing a pending output encoding or line-ending policy marks the document dirty. Returning every pending format dimension to the saved value clears metadata dirtiness when the text is also at its save point.

Save As selections are provisional until the user submits the dialog. Exporting to another destination never mutates the source document's format, history, path, dirty state, or save point.

### Application coordination

The main window owns tab and destination coordination. It compares resolved paths and existing tab identities, requests overwrite confirmations, invokes the core service, and opens or reloads tabs only after verified output exists.

This keeps document identity and GUI lifecycle decisions outside the encoding and save primitives.

## Open and reinterpret flow

### Separate assessments

Opening begins with two independent assessments.

The encoding assessment contains:

- suggested exact profile;
- confidence;
- alternatives;
- BOM or structural evidence;
- contradictory evidence;
- malformed preview-byte evidence; and
- whether explicit confirmation is required.

Confidence below `0.75`, contradictory evidence, or malformed preview bytes requires serious confirmation. The threshold and evidence rules live in the Qt-free core and are covered by tests; UI code does not duplicate them.

The line-ending assessment contains exact LF, CRLF, and CR counts. A uniform result is informational. A mixed result is a repairable format condition, not an encoding emergency.

### Serious encoding dialog

When confirmation is required, UNITI stops before creating the editor tab and opens a modal format dialog containing:

- a serious warning and reason;
- the suggested profile and confidence;
- an exact encoding-profile selector;
- a bounded read-only preview that updates with the selected profile;
- malformed-byte evidence visible in the preview;
- the separately detected line-ending summary; and
- `Open` and `Cancel` actions.

Selecting `Open` records an explicit user override. Selecting `Cancel` creates no document or tab.

Manual `Reinterpret As` reuses the same preview and selection flow. Reinterpretation is blocked for a dirty document because it would discard or detach edits from their source-byte interpretation. A clean document may be re-opened in the same tab after explicit confirmation.

### Malformed bytes

Malformed byte spans remain visibly annotated by the existing decoder and preserve their exact source bytes while their source pieces remain untouched.

If malformed bytes are encountered outside the initial bounded preview, the document gains a persistent serious encoding indicator. Same-profile `Preserve` output remains safe. Encoding or line-ending conversion requires a complete streaming validation and is blocked while unresolved malformed source spans remain.

Editing over a malformed span deliberately replaces those raw bytes with valid logical text and removes that span's annotation.

### Line-ending report

Line-ending issues never share the serious encoding modal.

- Uniform line endings appear in status only.
- Mixed line endings produce a non-blocking report.
- The report offers `Keep`, `Convert to LF`, `Convert to CRLF`, and `Convert to CR`.
- `Keep` preserves the existing mixed structure.
- A conversion selection marks the document dirty, but disk content changes only on Save.

## Save As design

UNITI uses an application-owned cross-platform Save As dialog so the output identity and output format remain visible together:

```text
File name:    [aaa.txt]
Encoding:     [UTF-8]
Line endings: [CRLF]
```

The encoding selector contains the exact profiles from this design. The line-ending selector defaults to the source/saved state, including `Mixed (preserve)` where applicable.

The existing format actions use the same canonical profiles and output-policy values. There is no separate menu-only encoding grammar.

### Same destination

When the resolved destination is the current document's path:

- the selected output format applies to the current document;
- successful output updates its exact saved format and disk identity;
- the save point advances and dirty state clears only after verification;
- the existing tab remains current; and
- no additional tab is created.

### Different destination

When the resolved destination differs:

- UNITI exports the current logical text using the selected format;
- the original tab remains attached to its original path and format;
- the original history, dirty state, and save point remain unchanged; and
- after verification, the exported file opens in a new active tab.

Full resolved path, not basename alone, determines whether the destination is the same file. A same-named file in another directory is a different destination.

## Overwrite and conversion warnings

### Existing destination not open

Save As over an existing file that is not open in UNITI requires one normal overwrite confirmation.

Before presenting that confirmation, UNITI inspects the destination's encoding. If the selected output encoding differs, the confirmation prominently states the exact change, for example:

```text
Encoding will change: UTF-8 -> UTF-16 LE BOM
```

If target encoding confidence is low, the user must explicitly confirm the target's format before replacement. UNITI does not claim a definite before/after conversion from uncertain evidence.

### Destination already open

If the destination is already open and clean, UNITI requires two confirmations:

1. confirm replacement of the file on disk; and
2. confirm replacement and reload of the already-open tab.

Any encoding change is shown within this warning sequence and does not replace either overwrite protection. After verified replacement, UNITI reloads and activates the existing target tab instead of creating a duplicate.

If the existing target tab is dirty, replacement is blocked until that tab is saved or closed.

### Save over the current file

Ordinary Save does not show a generic overwrite warning. However, if the pending encoding profile differs from the current saved profile, Save requires a serious conversion confirmation showing the exact before and after profiles.

After a successful verified conversion, later saves do not repeat the conversion warning unless the encoding changes again.

New destinations do not require an encoding-change warning because no existing file is being transformed or replaced.

Line-ending conversion remains separately reported and explicitly selected. It is not classified as the same serious encoding warning.

## Verified save transaction

Every Save and Save As uses the same transaction:

1. Capture the document revision, destination identity, and requested output format.
2. Recheck external-change and open-tab overwrite guards.
3. Stream output to a temporary sibling of the destination.
4. Flush and sync the staged file.
5. Verify the staged file.
6. Atomically replace the destination only after verification succeeds.
7. Sync the parent directory where supported.
8. Update document or tab state only after replacement succeeds.

Verification is streaming and bounded-memory. It confirms:

- exact BOM presence or absence;
- exact codec and byte order;
- strict decoding under the selected profile;
- exact requested line-ending policy, or preservation when requested;
- exact streaming equality with the expected logical output after any requested EOL transformation; and
- staged byte length and digest equality against the stream UNITI wrote.

The document revision and destination identity are checked again before commit so an edit or external file replacement cannot cause stale output to be treated as current.

## Failure behavior

- An unrepresentable character aborts strict encoding and reports the output profile, character, Unicode code point, and document position.
- Unresolved malformed source bytes abort format conversion but do not prevent same-profile `Preserve` output.
- External replacement, permission failure, disk failure, verification mismatch, stale revision, or cancellation aborts the transaction.
- Temporary files are removed after failure where possible.
- A failed or cancelled transaction does not change the destination, path, selected/saved format, dirty state, history, or save point.
- A failed export does not open or reload a tab.

## Testing strategy

### Core profile and detection tests

- Map every exact profile to its codec, byte order, BOM bytes, and display name.
- Confirm that omission of `BOM` always writes no BOM.
- Cover BOM recognition, BOM/structure conflicts, bounded confidence, alternatives, explicit overrides, and the serious-confirmation decision.
- Verify that encoding and line-ending assessments remain independent.

### Save matrix

- Exercise every Unicode profile with LF, CRLF, CR, and mixed-preserve inputs.
- Round-trip Western and Cyrillic text through every Unicode profile.
- Round-trip representable Western text through Windows-1252.
- Reject unrepresentable Cyrillic output to Windows-1252 without touching the destination.
- Verify every explicit line-ending normalization.
- Verify malformed-byte preservation and blocked unsafe conversion.

### State and lifecycle tests

- Confirm metadata dirty-state and save-point transitions.
- Confirm same-destination Save As updates the current document only after success.
- Confirm different-destination export leaves the source unchanged and opens a new active tab.
- Confirm normal overwrite, double open-target overwrite, and dirty-target blocking.
- Confirm encoding-change warnings for Save and Save As, including BOM and byte-order changes.
- Confirm later ordinary saves do not repeat an already-completed conversion warning.

### Failure and verification tests

- Inject write, sync, permission, verification, external-change, and stale-revision failures.
- Confirm the original destination and all document state remain unchanged.
- Confirm staged output fails before atomic replacement when BOM, byte order, decoding, EOL, or logical-text verification disagrees.

### UI and acceptance tests

- Contract-test the low-confidence dialog, live preview, separate line-ending report, Save As field order, format labels, warning content, and tab behavior.
- Run the complete automated suite, deep self-check, architecture-boundary checks, and native macOS GUI smoke.
- Exercise real files from every supported format class through open, edit, Save, Save As, and reopen.

## Acceptance gate

`v0.001a17` freezes only when:

1. The complete automated suite is green.
2. Deep self-check and architecture-boundary checks are green.
3. Native macOS GUI smoke is green.
4. Real files from every supported format class survive open, edit, Save, Save As, and reopen checks.
5. No known silent encoding, BOM, byte-order, line-ending, malformed-byte, document-identity, or save-state defect remains.

The canonical acceptance rule remains:

> Opening and saving a file must not silently change its encoding or line endings.
