# UNITI v0.001a18 Large-File Alpha Design

Date: 2026-09-02
Status: proposed design awaiting written review
Milestone: [`v0.001a18` — Large-File Alpha](v0.001a18-large-file-alpha.md)

## Goal

Make 10–100 MiB files routine without introducing a deliberate 1 GiB ceiling, while preserving UNITI's text-integrity, document-authority, and desktop-usability invariants.

a18 is a user-experience performance milestone. It establishes a repeatable suite that can evaluate the current and future application, then corrects the resource, caching, indexing, task, and UI paths that the suite proves are not bounded or responsive.

## Baseline evidence

Exploratory measurements were taken on the current a17 implementation before this design was written. The host was a `Mac15,8` with Apple arm64, 16 logical cores, 48 GiB RAM, macOS 26.6.2, Python 3.12.4, and Qt 6.11.2. Corpora were generated in disposable local temporary directories.

| Scenario | Current observation |
|---|---:|
| 100 MiB core `Document.open` | 0.005 s |
| 100 MiB application Open through full inspection | 0.170 s |
| 100 MiB first offscreen paint | 0.185 s |
| 100 MiB Open/first-paint RSS increase | 103.77 MiB |
| Jump to line 1,000,001 | 2.754 s synchronously |
| Search 100 MiB / 2,438,548 matches without result storage | 3.484 s |
| Background no-match search GUI heartbeat | 7.0 ms p95 / 60.5 ms maximum |
| Normal search cancellation | 1.3 ms |
| 100 MiB verified Save As | 3.875 s synchronously |
| 100 MiB application search RSS increase | 4,160.7 MiB |
| Cache accounting after that search | 1,200.2 MiB used / about 6,920 MiB allowed |

The baseline shows that the lazy document foundation is viable and background search is responsive, but far navigation and Save block the GUI. More seriously, a sequential UI search retains decoded spans, undercounts their true Python memory, and permits a multi-gigabyte cache. Fast completion does not compensate for that user-experience failure.

These figures are evidence for the design, not immutable performance promises. Canonical thresholds live in one adjustable table and will tighten as real editing establishes better expectations.

## Design principles

1. Performance is measured as user experience: time to usable content, interaction latency, cancellation, progress, memory pressure, and safe completion.
2. A long total duration is acceptable only while the GUI remains responsive, reports progress, and offers safe cancellation.
3. Host-sensitive throughput is recorded and compared with compatible baselines; freezes and runaway memory use are absolute failures on every eligible host.
4. The complete source file is never materialized as one Python `bytes` or `str` object.
5. Sequential work does not populate random-access caches unless a consumer explicitly requests reusable windows.
6. User edits and Undo/Redo remain authoritative document state, never disposable cache.
7. Background work publishes immutable results only after checking document revision, disk identity, and cancellation.
8. Workers never access Qt widgets. Qt receives small progress and completion records on the GUI thread.
9. Resource policy is automatic. a18 adds Cancel and Pause Background Work, not manual worker-count or cache-size preferences.
10. A threshold may tighten after repeated dogfood evidence. It never loosens automatically.

Apple documents 100 ms as the approximate upper bound before discrete interaction delay becomes noticeable and recommends substantially shorter work during continuous interaction. Qt likewise requires long-running processing to stay off the GUI thread. UNITI adopts conservative Python/Qt gates around those principles rather than claiming frame-perfect native-widget timing.

## Scope

a18 includes:

- a host-aware, schema-versioned performance suite for current and future UNITI builds;
- deterministic 10 MiB, 100 MiB, and sparse 1 GiB corpus tiers;
- one version-controlled table for thresholds, host eligibility, and resource policy;
- accurate process/cache measurements and comparable baseline reports;
- live CPU, memory, cache, disk, worker, and queue awareness;
- resource-aware task admission, priority, concurrency, throttling, pausing, and cancellation;
- bounded streaming, decoded-window, line-index, and wrapped-row memory;
- progressive Open/EOL analysis, navigation/indexing, search/replace preparation, Save, and Save As;
- progress and resource-pressure indication in the existing status/diagnostics surfaces; and
- regression and acceptance coverage for responsiveness, memory, integrity, cancellation, staleness, and cleanup.

## Outside a18

a18 does not add regex language features, syntax highlighting, file-type templates, project/workspace behavior, plugins, telemetry, network benchmarking, a general task manager, or a preferences UI for performance tuning. a19 remains responsible for regex intelligence. a22 remains responsible for longer-term dogfood/performance hardening after the a18 foundation exists.

## Adjustable threshold authority

`src/uniti/resources/performance_policy.toml` is the single authority for benchmark tiers, host eligibility, user-experience gates, comparison limits, cache ceilings, resource-pressure transitions, and workload parameters. It lives inside the installed package because both the production resource engine and the repository benchmark runner must consume the same named policy values; neither duplicates unexplained constants.

The initial table is equivalent to:

[host_requirements.routine]

[gates.open_to_usable_ms]
warn = 500

[gates.gui_heartbeat_p95_ms]

When both an absolute memory limit and a physical-memory fraction exist, the smaller value governs. Unknown keys, missing required keys, invalid relationships such as `warn > fail`, and unsupported schema versions fail validation before a benchmark or production policy starts.

The table is repository configuration, not a user preference. Real-work evidence first tightens a warning. A warning becomes a failure threshold only after repeated comparable passing runs. Loosening a failure threshold requires an explicit documented reason and before/after evidence.

## Host preflight

Every performance run begins with a read-only local preflight before corpus generation or application launch. It records:

- CPU model/generation, architecture, physical and logical core counts;
- physical and currently available RAM plus memory-pressure state;
- current system load and UNITI process state;
- OS, kernel, Python, Qt, UNITI version, and Git commit;
- filesystem type, free space, temporary root, and sparse-file capability;
- display scale and refresh rate for native GUI scenarios; and
- power or thermal constraint state when the host exposes it reliably.

Preflight performs no network access and sends no telemetry.

Two modes are supported:

- `baseline` requires an eligible, sufficiently idle host. A contended or pressured run is `INVALID` and cannot replace a selected baseline.
- `real-world` records current conditions and continues when safe. It supports dogfood diagnosis but does not silently become the controlled baseline.

Absolute responsiveness and runaway-memory rules still apply to eligible real-world runs. Throughput comparisons require a compatible host fingerprint. Compatibility includes architecture, operating-system family, physical core class/count, RAM class, Python/Qt major-minor versions, and corpus schema; the exact CPU model and patch versions remain recorded for interpretation.

If RAM, disk, sparse-file support, or GUI capability is insufficient, the affected tier is `NOT RUN`, never `PASS`. Corpus generation cannot begin when the staged-save scenarios would consume unsafe free space.

## Benchmark corpus

Corpora are deterministic and generated by bounded streaming writes into an owned temporary directory. Corpus bytes are not committed.

The suite defines stable scenario IDs for:

- ordinary fixed-length UTF-8 lines;
- newline-dense UTF-8 text;
- one giant logical line;
- mixed Western, Cyrillic, and multibyte Unicode;
- sparse search matches;
- dense search matches;
- mixed LF/CRLF/CR content;
- malformed UTF-8 preserved under the exact-profile rule; and
- a sparse 1 GiB source with markers near the beginning and beyond 1 GiB.

Each corpus has a schema version, deterministic seed, expected byte size, expected logical markers, encoding profile, EOL evidence, and digest where a complete digest is practical. Corpus creation is outside the scenario timing window. Cleanup occurs after success, failure, cancellation, or interruption.

## Performance-suite architecture

The repository gains this non-production test structure:

```text
benchmarks/
├── corpus.py
├── host.py
├── scenarios.py
├── evaluate.py
├── report.py
└── baselines/
src/uniti/resources/
└── performance_policy.toml
tests/performance/
└── [policy, corpus, runner, evaluator, and scenario tests]
scripts/
└── performance_suite.py
```

Execution is:

```text
host preflight
    -> temporary corpus generation
    -> one fresh child process per measured scenario
    -> raw schema-1 result
    -> threshold and compatible-baseline evaluation
    -> aggregate JSON and readable terminal/Markdown summary
```

Fresh child processes isolate peak and retained RSS, Qt/application state, caches, temporary files, and failures. The parent owns timeouts, termination after a hung scenario, artifact collection, and final cleanup. A killed child can therefore be classified without corrupting a later measurement.

Representative commands are:

```bash
.venv/bin/python scripts/performance_suite.py --tier quick
.venv/bin/python scripts/performance_suite.py --tier routine --mode baseline
.venv/bin/python scripts/performance_suite.py --tier design-target
.venv/bin/python scripts/performance_suite.py --compare benchmarks/baselines/<baseline>.json
```

The default automated suite tests the benchmark machinery and deterministic architectural limits. The explicit quick/routine/design-target commands run measured workloads. Routine performance is a required a18 freeze gate but does not silently add 100 MiB artifacts to every ordinary `pytest` invocation.

## Measurements and result grammar

Each result records the preflight fingerprint, mode, tier, scenario ID/schema, version/commit, repetition count, raw samples, median, p95, maximum, throughput, GUI heartbeat intervals, cancellation latency, first-progress latency, progress gaps, peak RSS, retained RSS, configured/accounted cache, worker/queue observations, output digests, and cleanup state.

RSS is intentionally retained as a user-impact measurement even when part of it is file-backed. Python heap, UNITI-accounted cache, and platform RSS are reported separately where available. Cache accounting is measured against the objects it retains; producers may not use payload-only estimates that omit dominant Python container/object overhead.

Results use exactly these states:

- `PASS`: every applicable hard user-experience and integrity gate passed.
- `WARN`: the run remains usable but crossed a warning limit or regressed by at least 15% against a compatible baseline.
- `FAIL`: a freeze, cancellation, memory, integrity, cleanup, or at-least-25% compatible regression gate failed.
- `INVALID`: host contention, pressure, interruption, or measurement failure made the baseline unreliable.
- `NOT RUN`: a declared host capability or capacity requirement was unavailable.

An invalid, not-run, missing, or timed-out required scenario never counts as passing. The evaluator distinguishes product failure from harness failure and prints the exact threshold, observed value, unit, host state, and scenario.

## Resource authority

The existing Qt-free `ResourceManager` becomes the application-wide authority for static host capacity, live resource snapshots, cache budgets, and expensive tasks.

```text
HostResourceProfile + periodic ResourceSnapshot
                      |
                      v
                ResourcePolicy
          +-----------+-----------+
          |           |           |
          v           v           v
    task admission  active limit  cache target
          |           |           |
          +-----------+-----------+
                      |
                      v
          progress/state snapshot -> Qt status adapter
```

The static profile is captured once per application start. Lightweight live sampling updates available memory, pressure, system load, process RSS, cache use, active/queued work, and relevant free disk space. Probe failure cannot crash editing; it moves policy conservatively and reports unavailable evidence.

The worker pool retains a bounded maximum number of threads. Policy changes an active-admission limit instead of repeatedly creating and destroying threads. Queued work remains priority-ordered and cancellable.

Initial operating behavior is:

| Resource state | Worker admission | Cache target | Behavior |
|---|---:|---:|---|
| Normal | available physical capacity minus GUI reserve | configured cap | user work plus bounded prefetch |
| Busy | approximately half normal admission | 75% cap | defer inactive-document and speculative work |
| Constrained | one background worker | 25% cap | evict inactive/search caches and prioritize direct user work |
| Critical | essential work only | visible/nearby minimum | pause disposable work and issue a clear warning |

Memory at or above 25% available is Normal, 15–25% is Busy, 8–15% is Constrained, and below 8% is Critical. CPU load of 0.75 per logical core produces Busy and 1.0 produces Constrained, but CPU load alone never produces Critical. The more severe CPU or memory state governs. Exact transition ratios and recovery hysteresis live in `src/uniti/resources/performance_policy.toml`. Two consecutive healthier samples are required before relaxing pressure, preserving the existing anti-flap behavior.

## Task model and priority

Every expensive operation is represented by a Qt-free task record containing:

- stable task ID and kind;
- owning document identity and revision where applicable;
- priority and foreground/background classification;
- expected memory and temporary-disk demand;
- cancellation token;
- completed/total work units when total is known;
- current phase and last-progress time;
- safe-cancellation and non-cancellable commit boundaries; and
- immutable result, failure, or cancellation outcome.

Priority order is:

1. short visible-window preparation and critical recovery durability;
2. explicit current-user Save/Save As and navigation;
3. explicit search and replacement preparation;
4. active-document indexing and EOL analysis;
5. inactive-document indexing; and
6. speculative prefetch and maintenance.

Priority does not allow a worker to mutate a Qt object. Starvation protection eventually admits lower-priority work while Normal, but Busy or worse may keep disposable work paused.

Tasks process bounded chunks. Between chunks they check cancellation, current policy, document revision, disk identity where applicable, and progress cadence. A task that has crossed the brief atomic-replacement commit boundary finishes that boundary rather than exposing a partial destination.

## Document read snapshots and staleness

Search, replacement preparation, indexing, and staged output consume immutable read snapshots rather than a mutable live `PieceTable`. A snapshot records document revision, source/disk identity, exact format, frozen piece descriptors, and the edited text referenced by those descriptors. It opens independent byte access for worker use and copies edited content only, never the complete immutable source.

Search and indexing may coexist with editing. An edit cancels or invalidates revision-bound work; stale results are closed and discarded without changing the view. Search no longer disables the editor merely to protect mutable iteration.

Save and Save As keep the target document temporarily edit-locked in a visible, cancellable state for a18. Other tabs and the rest of the application remain usable. This avoids falsely marking a moving revision as saved or rebasing newer edits over an atomically replaced source. Allowing same-document edits during Save is explicitly deferred until a future design can preserve those semantics without ambiguity.

## Bounded cache behavior

The cache cap is the smaller of 512 MiB and 12.5% of physical RAM, subject to live available-memory pressure. The initial minimum reserved for regenerable visible/nearby windows is 16 MiB. These values remain adjustable in the policy table.

Cache producers declare a usage intent:

- `VISIBLE`: current viewport data with highest disposable retention;
- `NEARBY`: bounded adjacent windows;
- `RANDOM`: reusable navigation/search context;
- `STREAMING`: one-pass work that bypasses reusable decoded-window caching; and
- `INACTIVE`: data owned by a non-current document and evicted first.

Streaming search, EOL analysis, verification, Save, and Save As do not fill the random-access decoded-span cache. Full-file iteration retains only its bounded working window. Closing a document evicts all of its disposable entries.

Memory accounting includes strings, boundary tables, annotations, page indexes, record containers, and dominant Python object overhead. The cache rejects any single entry larger than its current target. Under pressure it evicts by state and recency, then lowers future admission; it never treats Undo/Redo history or unsaved edits as cache.

## Progressive indexes

The current dense line-start array and ever-growing wrapped-row object list are replaced by chunk summaries plus bounded local detail.

A logical-line summary records a chunk's character start/end, line count, CR-boundary state, and revision. Sparse prefix counts support binary lookup. Exact starts inside a chunk are decoded into compact integer arrays only when visible or directly queried, then held by the resource cache. Background indexing publishes complete immutable summaries only if its source revision remains current.

Wrapped rows use sparse checkpoints and cached row blocks keyed by document revision, wrap width, and font metrics. They never retain one Python object per visited visual row. Width or revision changes discard the derived wrap cache without touching document text.

Painting performs no full-file work. It requests only visible line windows, annotations, selection intersections, and match intersections. Continuous scroll/paint measurements enforce the heartbeat and interaction gates.

Far Go to Line and document-end navigation become progressive user tasks. UNITI acknowledges the command immediately, reports indexing progress, remains cancellable, and moves the cursor only when the revision-bound target is resolved. Ordinary nearby line/page movement remains synchronous because it stays within the short interaction budget.

## Progressive operation flows

### Open and line-ending analysis

Open performs bounded encoding detection, exact-profile evidence, and preview before constructing the tab. Full EOL analysis is no longer part of time to first paint. It runs with non-caching sequential byte access in the shared task system, reports `Analyzing…`, and publishes only if disk identity and document identity still match. Mixed-EOL policy remains explicit and modeless.

### Search and Find All

Search consumes a document snapshot through streaming cache intent, appends compact records to a bounded `MatchStore`, reports scanned progress, and checks cancellation between bounded engine windows. Patterns whose unresolved context exceeds the configured bound fail with an explanatory context-limit result rather than growing an unbounded buffer. Visible highlighting continues to query only intersecting results.

### Replace and Replace All

Replacement preparation creates a memory-bounded or spooled monotonic plan. A bulk piece-table application path applies an admitted plan in one bounded transaction rather than repeatedly rebuilding a growing piece list. Replace All remains one Undo operation.

Before application, the resource policy estimates plan, resulting piece, inserted-text, deleted-text, and Undo costs. A plan that cannot fit the safe user-state envelope is refused before mutation with a precise explanation. UNITI never evicts user history to make room automatically.

### Save and Save As

Staging, encoding/EOL transformation, flushing, verification, and reread execute as a high-priority progressive task while the source document is edit-locked. The status surface reports phase and bytes processed. Cancellation before commit removes the temporary and changes neither destination nor document state. Destination identity is checked through the existing verified transaction immediately before the brief non-cancellable atomic replacement.

Successful completion is applied on the GUI thread: in-place Save advances the save point and refreshes source services; Save As opens or reloads exactly one verified output tab according to the a17 rules. Failure, cancellation, stale identity, or resource refusal leaves the original state intact.

## UI resource and task indication

The status bar exposes one compact accessible resource label:

- `Resources: Normal`
- `Resources: Busy`
- `Resources: Constrained`
- `Resources: Critical`

Color may reinforce state but never carries the meaning alone. The tooltip shows sampled CPU/load, available memory, process RSS, cache used/budget, active/queued work, and any unavailable probe.

Busy is passive. Constrained produces a nonmodal notice when an operation is actually throttled or paused. Critical explains which disposable work stopped and what essential operation, if any, was refused. Repeated identical warnings are coalesced until the state recovers.

The active operation reports a short phase, determinate progress when total bytes/characters are known, indeterminate progress otherwise, and Cancel when cancellation is safe. Operations that finish inside the first-progress threshold are complete rather than late and do not need to flash a progress surface. `Pause Background Work` affects indexing, EOL analysis, prefetch, and maintenance; it does not pause an explicit Save already in progress or recovery durability.

## Error handling and integrity

- Host telemetry failure selects conservative policy and remains visible in diagnostics.
- Benchmark preflight failure produces `INVALID` or `NOT RUN`, never a false pass.
- Worker failure becomes a structured task failure; the GUI displays a concise message and diagnostics retain details.
- Cancellation closes match/result spools, snapshots, byte sources, and staged temporaries.
- Stale revision or disk identity discards results before application.
- Memory pressure pauses or refuses work before allocation exceeds policy; it never silently normalizes, truncates, substitutes, or drops text.
- Disk-space admission accounts for source, stage, verification, and spool requirements with a safety margin.
- Save verification and atomic-replacement guarantees from a17 remain mandatory under all task states.
- A killed benchmark child cannot alter repository files or selected baselines.

## Verification strategy

Ordinary automated tests cover:

- threshold-table schema and relationship validation;
- deterministic host-profile and live-policy transitions through injected snapshots;
- active worker admission, priority, starvation protection, pause, and cancellation;
- cache caps, accurate accounting, streaming bypass, eviction order, and document cleanup;
- snapshot independence and stale-result rejection;
- compact line/wrap index correctness before and after edits;
- bounded replacement-plan admission and atomic bulk Undo;
- progressive Open/EOL, navigation, search, Save, and Save As state machines;
- progress cadence and accessible resource/status text; and
- corpus, subprocess, result-schema, evaluator, timeout, and cleanup behavior.

Measured scenarios cover:

- Open to usable editor and first viewport;
- typing, selection, nearby navigation, far navigation, and scrolling;
- wrapped and unwrapped painting, including a giant line;
- sparse/dense Find All, cancellation, and visible result lookup;
- admitted Replace All and safe refusal;
- verified Save and Save As;
- Normal/Busy/Constrained/Critical resource transitions; and
- memory recovery after closing documents and completing/cancelling work.

All correctness checks compare expected logical text, exact output bytes/format, revision, save state, destination identity, and cleanup state. Performance results cannot override an integrity failure.

## Milestone acceptance

a18 freezes only when:

1. the complete ordinary automated suite is green;
2. the quick performance suite passes;
3. the routine 100 MiB suite passes in controlled baseline mode on the local reference host;
4. the sparse 1 GiB lazy-open/design probe passes without a whole-file allocation or deliberate ceiling;
5. native macOS use confirms heartbeat, typing, scrolling, navigation, cancellation, progress, and resource indication;
6. peak and retained memory stay inside the adjustable envelope;
7. search, replacement, Save, and Save As preserve a17 text-integrity guarantees; and
8. no known basic freeze, runaway-memory, stale-result, data-loss, or text-integrity defect remains.

Required `INVALID` or `NOT RUN` scenarios block the freeze until rerun on an eligible host. Generated corpora and raw artifacts remain disposable; a selected schema-versioned baseline and concise completion evidence are retained with the implemented milestone.
