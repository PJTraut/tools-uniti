# Isolated File-Type Environments — Phase E5 (SFM Foundation) Plan

Date: 2026-09-29
Status: **Implemented.**
Origin: [E1–E4 plan](2026-09-29-environment-framework-e1-e4-plan.md) explicitly deferred SFM/STY design ("Per this project's documentation rules, SFM/STY design deserves its own record once E4 has proven the framework"); [ADR-0013](../05_decisions/ADR-0013-environment-framework-ownership-boundary.md) names the same deferral. This is that record for the first slice — Phase E5 of the external handover spec's own phase numbering (`@externalresources/UNITI_Claude_Code_Environment_Handover_Spec.md` §74).

## Scope

**In scope:** the spec's Phase E5 bullets — generic SFM detection, a lossless tokenizer, a basic source model, a `.STY` raw parser, a normalized style registry, style layering, structural-dependency queries, syntax decoration, and marker diagnostics — still using the Core text editor only (no rich views, no USFM-specific behavior).

**Explicitly out of scope (later phases, per the spec's own sequencing):** USFM detection/validation and the official baseline `usfm.sty` (implemented in [E6](2026-09-30-environment-framework-e6-usfm-layer-plan.md)), a `.STY` *writer*/export (no bullet in E5's list calls for one; nothing here needs it yet), OccursUnder/Rank-driven paragraph-level nesting in the source tree (needs a loaded style registry wired into activation — still deferred past E6, see that plan's decision 5), typographic/presentation STY fields (font, margins, justification — Formatted View, E9), the rich-view/source-map framework (E7), and `usfmtc` integration (implemented in [E6](2026-09-30-environment-framework-e6-usfm-layer-plan.md)).

## Design decisions made while implementing

1. **Package shape.** Unlike JSON/XML/YAML's single flat file each, generic SFM needs several small collaborating pieces, so `core/environments/sfm/` is a subpackage (`tokens.py`, `tokenizer.py`, `nodes.py`, `parser.py`, `sty.py`). The `Environment` implementation itself stays a flat sibling file, `core/environments/sfm_environment.py`, so `core/environments/__init__.py` keeps exporting one `Environment` class per file type from the same flat surface the app layer already expects (`app/service.py`'s registration loop).
2. **Lossless tokenizer scope.** `SfmToken` has only two kinds, `MARKER` and `TEXT` — not the spec's fuller list (`WHITESPACE`, `LINE_BREAK`, `ATTRIBUTE_*`, ...). Nothing built in this phase (the source tree, the end-marker validator) needs a finer split, and the lossless invariant (`"".join(t.text) == source`) holds regardless. Finer kinds are added when a real consumer needs them.
3. **Generic parser nests only explicit `\marker ... \marker*` pairs.** A marker never closed by a matching end-marker — the normal case for paragraph markers (`\p`, `\v`, `\c`, ...), since USFM only assigns `EndMarker`s to character-style markers — becomes a flat `MARKER` leaf rather than swallowing the rest of the document as its children. Deciding that an unclosed `\v` should nest everything until the next `\v`/`\c` needs `OccursUnder`+`Rank` from a loaded style registry, which E5 does not wire into activation (see decision 6) — building a wrong generic guess now would be a worse foundation than staying flat about what the document itself actually states (explicit pairs). This is Phase E6's job.
4. **`.STY` raw layer preserves field order and unknown fields, not comment/blank-line byte-exact structure.** `RawStyleRecord`/`RawStyleEntry` keep every field in original order and original text (`raw_line`), including fields this reader doesn't recognize — so a future writer has what it needs. It does not track comments or blank lines between records, because nothing in E5 writes a `.STY` back out; that precision is deferred to whichever future phase adds a writer.
5. **Normalized `SfmStyle` covers structural/semantic fields only** (`OccursUnder`, `Rank`, `EndMarker`, `StyleType`, `TextType`, `TextProperties`, `NotRepeatable`→`repeatable`), not the spec's typographic fields (`FontSize`, `Justification`, margins, ...). Those belong to the Formatted View (E9). Every unrecognized field — typographic or otherwise — still round-trips through `SfmStyle.extensions` rather than being silently dropped, so no information is lost even though E5 doesn't interpret it.
6. **`StyleRegistry` layering exists as a pure function (`from_layers`) but nothing wires it into `SfmEnvironment.activate()` yet.** Loading a project's actual `.STY` files (discovery, precedence, official baseline) is USFM-specific setup — Phase E6. E5 proves the layering mechanics (`from_layers`, `_merge_styles`, field-by-field override) work correctly in isolation, tested directly against `RawStyleSheet`s, without deciding where stylesheets come from at runtime.
7. **`SfmEnvironment.validate()` flags unmatched end markers only, never unclosed opens.** In generic SFM (no loaded stylesheet) an unclosed `\p`/`\v`/`\c` is the overwhelmingly normal case, not a defect — flagging it would make every ordinary USFM file "invalid." An end marker with no matching open anywhere in the document (`\bd*` with no preceding `\bd`) is unambiguous evidence of an actual mistake regardless of stylesheet knowledge, so that's the one finding this phase reports. This mirrors decision 3's same reasoning applied to diagnostics instead of the source tree.
8. **Decoration is unchanged**, still `SyntaxProfileDecorationAdapter(SFM)` wrapping the existing single-category regex highlighter. STY-aware decoration (e.g. a distinct `sfm.marker.unknown` scope) needs a style registry at activation time — E6, once USFM detection and stylesheet loading exist.
9. **Extension mapping:** added `"usfm": "sfm"` to `syntax_profiles.DEFAULT_EXTENSION_PROFILES` (`.sfm` already mapped) so a `.usfm` file also gets the generic SFM environment/highlighting by default — matching the handover spec's own `SFM_MANIFEST.extensions = (".sfm", ".usfm")`. This does not distinguish USFM from generic SFM; that distinction is E6's.

## What shipped

- `core/environments/sfm/tokens.py`, `tokenizer.py`: `SfmToken`/`SfmTokenKind`, `tokenize_sfm()` (lossless, gap-free), `reconstruct()` (round-trip check helper).
- `core/environments/sfm/nodes.py`, `parser.py`: `SfmNode`/`SfmNodeKind`, `parse_sfm()` — the permissive overlay tree described in decision 3.
- `core/environments/sfm/sty.py`: `RawStyleEntry`/`RawStyleRecord`/`RawStyleSheet`/`parse_raw_stylesheet()` (raw layer); `SfmStyle`/`normalize_style()` (typed view); `StyleRegistry`/`from_layers()` (layered structural queries: `style_for`, `occurs_under`, `end_marker`, `rank`, `is_repeatable`, `style_type`).
- `core/environments/sfm_environment.py`: `SfmEnvironment` (`key = "sfm"`), matching `JsonEnvironment`/`XmlEnvironment`/`YamlEnvironment`'s exact shape — decoration adapter plus a `validate()` gated on `context.resource_profile.allow_full_parse` (same pattern as XML's `ElementTree` gate, since it also fully materializes the document).
- `core/syntax_profiles.py`: `DEFAULT_EXTENSION_PROFILES["usfm"] = "sfm"`.
- `core/environments/__init__.py`, `app/service.py`: `SfmEnvironment` registered alongside its siblings.
- Tests: `tests/test_sfm_tokenizer.py` (7 cases), `tests/test_sfm_parser.py` (7 cases), `tests/test_sfm_sty.py` (11 cases), `tests/test_sfm_environment.py` (7 cases), plus one new case in `tests/core/test_syntax_profiles.py` for the `.usfm` extension mapping — 53 new tests total, following the E3/E4 test-file conventions exactly.

## Verification

New test modules plus the full suite (`pytest tests/`) must stay green — no existing test's expectations should change (`.usfm` had no prior mapping, so no existing test asserted Plain Text for it).
