# UNITI v0.001a16 Startup, Bootstrap, and Initialization Design

Date: 2026-09-01
Status: approved technical design

## Goal

Add a safe, explicit, diagnosable lifecycle that bootstraps UNITI from an existing host Python 3.12+, creates or maintains a UNITI-owned isolated runtime, validates normal startup without mutating that runtime, persists phased setup/startup state, exposes fast and deep self-checks, and reaches the existing editor without weakening its architecture.

## Scope

This milestone implements:

- a standard-library bootstrap entry point that works before UNITI or PySide6 is installed;
- host Python 3.12+ discovery and validation;
- source-checkout and application-local environment modes;
- managed-environment ownership, creation, adoption, repair, validation, and relaunch;
- dependency installation from canonical `pyproject.toml` metadata during explicit bootstrap only;
- a phased startup coordinator with atomic setup-state persistence and bounded JSONL logging;
- settings/setup schema migration and malformed-file preservation;
- bounded runtime, path, filesystem, resource, recovery, Qt, font, clipboard, IME, and display checks;
- `uniti --self-check`, `uniti --self-check --deep`, and `--json` output;
- startup/setup diagnostics integration;
- acceptance tests and documentation for the lifecycle; and
- version completion as `v0.001a16` / `0.1a16`.

This milestone does not implement host-Python installation, embedded Python, signed installers, shortcuts, an updater, accounts, telemetry, or network-dependent normal startup.

## Accepted policies

1. A discoverable Python 3.12 or newer must already exist on the host.
2. Bootstrap may mutate only a verified UNITI-owned environment.
3. Normal `uniti` startup never invokes `pip`, repairs dependencies, or accesses the network.
4. Source mode uses exactly `<source-root>/.venv`.
5. Explicit local mode uses an OS-appropriate UNITI application-data runtime.
6. The exact source-checkout `.venv` may be safely adopted after virtual-environment validation.
7. An existing application-local target must have a matching UNITI ownership marker; an unmarked target is refused.
8. Dependency declarations in `pyproject.toml` remain canonical.
9. The current document, regex, large-file, save, recovery, resource, and Qt ownership invariants remain unchanged.

See [ADR-0001](../05_decisions/ADR-0001-host-python-runtime-policy.md), [ADR-0002](../05_decisions/ADR-0002-document-authority-boundary.md), and [ADR-0003](../05_decisions/ADR-0003-regex-engine-authority.md).

## High-level lifecycle

```text
host Python
    -> scripts/bootstrap.py
    -> standard-library uniti.bootstrap package
    -> source .venv or application-local venv
    -> install/repair/validate inside managed runtime
    -> managed Python -m uniti
    -> parse CLI before Qt import
    -> phased StartupCoordinator or SelfCheckRunner
    -> existing UNITIMainWindow/editor engine
```

Environment mutation and application startup are separate processes. Bootstrap launches UNITI as a child process and returns its exit code; normal UNITI never reaches back into bootstrap to mutate its environment.

## Module design

### `scripts/bootstrap.py`

This is the only source file that must remain parsable before Python 3.12 is selected. It uses only broadly available standard-library syntax.

Responsibilities:

- locate the repository root and `src` directory;
- if the current interpreter is older than 3.12, probe `UNITI_PYTHON`, the current executable, `python3`, supported versioned Python commands, and Windows `py -3` candidates without using a shell;
- validate each candidate by running a small subprocess that prints JSON version/executable identity;
- relaunch itself under the first supported candidate; and
- under Python 3.12+, prepend `src` and delegate to `uniti.bootstrap.cli.main()`.

If no candidate is supported, it prints the exact Python 3.12+ prerequisite and returns exit code `10`.

### `uniti.bootstrap.model`

Qt-free, third-party-free bootstrap types:

- `BootstrapMode`: `SOURCE` or `LOCAL`;
- `HostPython`: command tuple, executable, version, implementation, architecture;
- `BootstrapRequest`: mode, source root, dev/repair/no-launch/self-check/deep/json flags, forwarded arguments;
- `RuntimeMarker`: schema, owner, environment ID, mode, resolved paths, host/runtime identity, timestamps, dependency fingerprint, and health;
- `BootstrapResult`: environment/runtime paths, marker, fingerprint, fast-path flag, and launched exit code;
- `BootstrapError`: sanitized message plus a lifecycle exit code.

### `uniti.bootstrap.discovery`

Responsibilities:

- validate the selected host interpreter;
- confirm the source root by requiring `pyproject.toml`, `src/uniti`, and project name `uniti-editor`;
- resolve source mode to `<source-root>/.venv`;
- resolve local mode to `AppPaths.local_runtime_dir`;
- return the platform-specific runtime Python path (`bin/python` or `Scripts/python.exe`); and
- query interpreter identity through subprocess JSON rather than trusting filenames.

No subprocess uses `shell=True`.

### `uniti.bootstrap.environment`

`EnvironmentManager` owns safety and mutation.

For a missing environment it:

1. creates the exact target directory;
2. atomically writes `.uniti-runtime.json` with `healthy: false` before invoking `venv`;
3. creates the environment with `venv.EnvBuilder(with_pip=True, clear=False)`;
4. validates the runtime interpreter; and
5. leaves the marker and partial environment intact if a later step fails.

For an existing source `.venv` without a marker it validates:

- the target resolves exactly beneath the selected source root;
- `pyvenv.cfg` exists;
- the expected runtime executable reports `base_prefix != prefix`;
- runtime Python is 3.12+; and
- no conflicting marker exists.

It then writes the unhealthy ownership marker before dependency mutation.

For an application-local environment, an absent target may be created. An existing target without a marker, or with a mismatched owner, mode, environment ID, or environment path, is refused with exit code `11`. Its recorded source path is installation provenance rather than ownership: a later explicit bootstrap may install from a different validated UNITI source root and updates that provenance only after successful validation. No environment is deleted, cleared, or silently replaced.

A bootstrap lock uses atomic exclusive file creation in the managed runtime parent. It stores session ID, PID, timestamp, mode, and target. A live owner causes an actionable refusal. A dead/stale lock is preserved with a timestamped `.stale` name before a new lock is acquired. Lock cleanup never touches unrelated files.

### `uniti.bootstrap.dependencies`

`DependencyManifest` reads `pyproject.toml` with `tomllib` and verifies project name/version plus the base, `ui`, and optional `dev` dependency groups.

Installation uses the project itself as the canonical requirement:

```text
source: <runtime-python> -m pip install -e <source-root>[ui]
source --dev: <runtime-python> -m pip install -e <source-root>[ui,dev]
local: <runtime-python> -m pip install <source-root>[ui]
local --dev: <runtime-python> -m pip install <source-root>[ui,dev]
```

On a new environment, bootstrap ensures pip is present and prepares packaging tools inside the managed environment. `--repair` repeats installation even when the fingerprint matches. Bootstrap never invokes bare `pip` and never installs into the bootstrap interpreter.

Validation runs:

- runtime metadata queries for `uniti-editor`, `regex`, and PySide6;
- imports of UNITI, `regex`, and PySide6;
- `runtime-python -m pip check`; and
- version checks against the selected dependency declarations.

Installed-metadata requirement satisfaction is delegated to `pip check`; UNITI does not grow a partial PEP 440/508 implementation. Bootstrap separately requires/imports PySide6 when the `ui` extra is selected because optional-extra requirements are not enforced by `pip check` after installation.

The environment fingerprint hashes:

- selected dependency declarations;
- UNITI package/display version and source build identity;
- source root and mode;
- host/runtime interpreter identity; and
- installed dependency versions.

A healthy marker with a matching fingerprint still receives lightweight import and `pip check` validation, but skips installation unless `--repair` is present.

### `uniti.bootstrap.cli`

Supported bootstrap interface:

```text
python3.12 scripts/bootstrap.py [--local] [--dev] [--repair]
                                [--no-launch]
                                [--self-check [--deep] [--json]]
                                [--] [file ...]
```

`--local` selects application-local mode. `--deep` implies `--self-check`. `--json` is accepted only with self-check. Remaining arguments are forwarded to UNITI; `--` permits filenames beginning with a dash.

After successful bootstrap, the default launch command is:

```text
<managed-python> -m uniti [forwarded arguments]
```

Self-check launch adds `--self-check`, `--deep`, and `--json` as selected. `--no-launch` prints the managed UNITI executable command and exits `0`.

## Application paths

`AppPaths` gains `data_dir` while preserving existing config/state/cache semantics.

Derived paths:

- `local_runtime_dir = data_dir / "runtime" / "venv"`;
- `setup_state_file = state_dir / "setup-state.json"`;
- `log_dir = state_dir / "logs"`;
- `startup_log_file = log_dir / "startup.jsonl"`;
- `temp_dir = cache_dir / "temp"`;
- `session_dir = cache_dir / "sessions"`; and
- existing `recovery_dir` and `settings_file` remain authoritative.

Platform data roots:

- macOS: `~/Library/Application Support/UNITI`;
- Windows: `%LOCALAPPDATA%/UNITI`;
- Linux/Unix: `$XDG_DATA_HOME/uniti` or `~/.local/share/uniti`.

`ensure()` creates all required application-owned directories. Capability checks subsequently verify writability rather than assuming creation implies safety.

## Setup-state schema

`uniti.app.setup_state` defines schema `1` and uses only the standard library.

The persisted JSON contains:

```text
schema
uniti: display_version, package_version, build_identity
startup: ok, stage, failure_code, failure_message, fast_path
install: mode, source_root, environment_path, environment_id
python: host executable/version, runtime executable/version, owned
platform: sys_platform, system, release, machine
dependencies: ok, fingerprint, versions
schemas: settings=1, recovery=2, session=1
resources: physical, available, cache_budget, worker_count, pressure
capabilities: filesystem and Qt/platform result maps
session_id
last_bootstrap
last_startup_attempt
last_successful_startup
```

Timestamps use UTC ISO 8601 with a `Z` suffix. Paths are resolved strings. Failure messages are sanitized and contain no traceback, environment dump, credentials, or document content.

`SetupStateStore` writes through a sibling temporary file, flushes/fsyncs it, atomically replaces the target, and syncs the parent directory where supported. If existing JSON is malformed, it first copies the original to a timestamped `.invalid` sibling. If preservation fails, it does not overwrite the original. Unsupported future schemas fail with exit code `13` and are not replaced.

Bootstrap updates ownership, fingerprint, dependency, and `last_bootstrap` fields. Normal startup updates attempt, phase, capability, resource, and success fields while preserving bootstrap data.

## Settings schema and migration

Settings schema `1` is:

```json
{
  "schema": 1,
  "last_directory": null,
  "performance_mode": "Automatic"
}
```

An existing unversioned settings object is treated as schema `0`, validated using current field rules, and atomically migrated to schema `1`. Malformed content is copied to a timestamped `.invalid` sibling before schema-1 defaults replace it. A future unsupported schema raises a clear error and remains untouched.

`SettingsStore.load()` retains its `Settings` return contract. A new `prepare()` operation performs preservation/migration and returns migration diagnostics before the GUI loads settings.

## Startup coordinator

`uniti.app.startup` defines:

- `StartupPhase` ordered enum;
- `ExitCode` integer enum;
- `StartupFailure` with phase, exit code, safe message, and cause for local logging only;
- `StartupCoordinator` state machine;
- `StartupContext` containing paths, state, identity, resources, settings, recovery candidates, capability results, and session ID; and
- `StartupLog` for bounded JSONL phase records.

The coordinator owns phase ordering, timing, persistence, and failure translation. Application callbacks own phase-specific construction so the coordinator remains Qt-free.

```text
BOOT
  01 RUNTIME_IDENTITY
  02 ENVIRONMENT_VALIDATION
  03 DEPENDENCY_VALIDATION
  04 APPLICATION_PATHS
  05 SCHEMA_MIGRATIONS
  06 SETTINGS_LOAD
  07 RESOURCE_CALIBRATION
  08 STALE_STATE_CLEANUP
  09 RECOVERY_DISCOVERY
  10 GUI_CAPABILITIES
  11 SESSION_RESTORE
  12 READY
```

Before phase execution, startup creates the minimal state/log parent needed to record failure. Phase 04 then validates the complete path set.

Each successful phase atomically persists its state and appends a timed JSONL record. Failure persists the last phase and translated safe error. `READY` sets `startup.ok`, `last_successful_startup`, and the completed capability/resource snapshot.

The startup log rotates before exceeding 5 MiB, retains at most ten rotated files, and uses atomic rename within `log_dir`. Phase-08 age cleanup applies after size/count rotation.

`application.py` supplies lazy callbacks for GUI phases. Phase 10 imports PySide6, constructs/reuses `QApplication`, and runs platform checks. Phase 11 creates application services/window, presents recovery candidates, and opens command-line files. Persistent tab-session restoration is not introduced; “session restore” in `a16` means recovery plus requested-file restoration and per-process session initialization.

Resources and recovery services created before a failure shut down in reverse order. The existing final shutdown guarantees remain.

## Runtime and capability probes

`uniti.app.capabilities` contains bounded, Qt-free probes for:

- Python/runtime/platform/architecture identity;
- physical and available memory;
- CPU/logical worker calculation;
- free disk space for application paths;
- create/write/fsync/atomic-replace behavior in UNITI-owned temp locations;
- mmap availability;
- metadata/xattr support as capability, not universal requirement;
- practical file-handle limits where exposed by the platform; and
- runtime environment ownership marker validity.

Probes create only uniquely named files inside UNITI temp directories and remove those files in `finally` blocks. A capability may be `available`, `unavailable`, or `unknown` with a safe reason.

The lazy Qt probe records:

- PySide6 and Qt versions;
- Qt platform plugin/backend;
- application creation success;
- resolved monospace/native fallback font family;
- clipboard availability and selection support;
- input-method availability;
- screen count, logical DPI, and device-pixel ratios.

Unavailable optional platform capabilities remain diagnostic unless safe GUI operation is impossible.

## Resource calibration

`ResourceManager` remains the owner of runtime cache and worker policy. It exposes read-only `cache_budget_bytes` and `worker_count` properties for setup state and diagnostics. No second resource policy is created for startup.

Calibration records the same memory snapshot, automatic cache target, initial pressure, and worker count used to construct `ResourceManager`.

## Recovery discovery and cleanup

Phase 09 uses the existing `RecoveryManager.discover()` behavior to validate and enumerate journals. User prompts and replay remain in the window/session phase after Qt is ready.

Phase 08 cleanup is deliberately narrow:

- only files/directories under UNITI `temp_dir`, `session_dir`, and `log_dir` are candidates;
- only known UNITI prefixes/record formats are accepted;
- active session IDs and live process records are retained;
- age thresholds are seven days for temp/session artifacts and thirty days for logs;
- at most 200 entries are inspected and at most 100 removed per startup; and
- recovery journals and search spill files outside these owned cleanup roots are never deleted by this phase.

Each process creates `session_dir/<uuid>/session.json` with schema, PID, start time, and build identity. This prevents temp/session collisions between UNITI instances.

## Application CLI

`uniti.app.application` parses arguments before importing PySide6:

```text
uniti [file ...]
uniti --self-check [--deep] [--json]
uniti --version
```

Normal launch validates runtime ownership, dependencies, paths, and schemas but never invokes pip. An invalid environment reports the explicit bootstrap/repair command and exits with the matching lifecycle code.

`--version` prints display and package versions without Qt. `--deep` and `--json` require `--self-check`. CLI usage errors use exit code `2`.

## Self-check design

`uniti.app.self_check` defines:

- `CheckStatus`: pass, fail, or skip;
- `CheckResult`: name, status, duration, safe summary, structured details;
- `SelfCheckReport`: mode, identity, results, overall status, and exit code;
- `SelfCheckRunner`: ordered fast/deep execution; and
- human and JSON renderers.

Fast mode checks:

- supported runtime and ownership marker;
- declared/installed dependency versions, imports, and `pip check`;
- application path existence/writability;
- setup/settings schema readability;
- a third-party `regex` compile/search sanity case;
- memory/resource calibration;
- bounded filesystem capabilities; and
- PySide6/Qt availability and version.

Deep mode adds temporary functional checks for:

- UTF-8 and Windows-1252;
- UTF-16 LE/BE and UTF-32 LE/BE with and without applicable BOM detection fixtures;
- LF, CRLF, and CR insertion/conversion;
- mmap and explicit fallback `ByteSource` reads;
- invalid-byte preservation;
- third-party regex search and replacement;
- streaming atomic save/reopen;
- recovery journal creation and replay; and
- offscreen Qt application/view construction, clipboard, and input-method availability.

Deep checks reuse/refactor the existing headless smoke primitives where doing so preserves their current public result contract. All generated data lives under a temporary directory and is removed unless an explicit diagnostic retention option is added in a later milestone.

Default output is concise human-readable text. `--json` emits a stable JSON object containing all check results. Both formats avoid secrets and document content. A failed check returns the most specific lifecycle exit code represented by the report.

## Diagnostics integration

`diagnostics_snapshot()` gains an optional startup/setup snapshot argument. `application.py` passes the completed `StartupContext` snapshot into `UNITIMainWindow`, which passes it to the diagnostics dialog. Diagnostics do not re-run probes or read ambient global state.

New diagnostics sections include:

- install/environment identity and ownership;
- dependency versions/fingerprint;
- last bootstrap and startup stage/status;
- schema versions;
- resource calibration;
- filesystem capabilities;
- Qt/font/clipboard/IME/display capabilities; and
- current session ID.

Existing document diagnostics remain unchanged.

## Failure taxonomy

| Exit code | Meaning |
|---:|---|
| `0` | success |
| `1` | unexpected internal failure |
| `2` | CLI usage error |
| `10` | unsupported or missing host/runtime Python |
| `11` | unsafe or mismatched environment ownership |
| `12` | missing, incompatible, or broken dependencies |
| `13` | application path, persisted state, or schema failure |
| `14` | deep/functional self-check failure |
| `15` | GUI/Qt/platform startup failure |

Expected errors are translated at their ownership boundary. User output contains the failed phase, safe cause, and exact remediation. Tracebacks remain in bounded startup logs for internal unexpected failures only and are never stored in the JSON diagnostics snapshot.

Partial managed environments are marked unhealthy and retained for explicit repair. Bootstrap never deletes them automatically.

## Testing strategy

All production behavior is developed test-first.

### Bootstrap tests

- candidate host discovery and version selection with mocked subprocesses;
- unsupported-host exit behavior;
- source-root and source/local path resolution on macOS, Windows, and Linux;
- safe source `.venv` adoption;
- application-local unmarked/mismatched refusal;
- marker lifecycle for missing, partial, healthy, and repaired environments;
- lock acquisition/live-owner/stale-owner behavior;
- exact pip command construction and the prohibition on bare/system pip;
- manifest selection for base/UI/dev extras;
- fingerprint stable/change cases;
- fast-path validation and explicit repair; and
- relaunch command/exit-code propagation.

Network and package installation are mocked in unit tests. Temporary real virtual environments validate marker/interpreter ownership without modifying the working `.venv`.

### Startup/state tests

- cross-platform path derivation and directory creation;
- schema-1 atomic state round trip;
- malformed-file preservation;
- legacy settings migration and future-schema refusal;
- exact phase order and illegal transition rejection;
- state/log updates after every phase;
- expected and unexpected failure translation;
- reverse-order service cleanup;
- bounded stale cleanup; and
- resource/capability serialization.

### CLI/self-check/diagnostics tests

- parse/usage/version behavior without Qt import;
- human and JSON fast reports;
- exit-code selection;
- deep encoding/EOL/mmap/fallback/regex/save/recovery checks;
- Qt-offscreen self-check when PySide6 is installed;
- startup snapshot inclusion in diagnostics; and
- preservation of existing document diagnostics.

### Acceptance and regression

- a fresh temporary checkout without `.venv` bootstraps using a supported host Python;
- source bootstrap creates `.venv`, installs from canonical metadata, and writes ownership/setup state;
- `uniti --self-check` succeeds;
- normal launch reaches the offscreen UI;
- a second launch/bootstrap uses the fingerprint fast path;
- malformed setup/settings files are preserved safely;
- unsupported Python and unsafe local targets fail without external mutation;
- the full pytest suite, `compileall`, `git diff --check`, import-boundary checks, headless smoke, and Qt-offscreen runtime tests pass.
